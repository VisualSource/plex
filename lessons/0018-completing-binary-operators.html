Lesson 18 — Completing the Binary Operator Set

compilerWATcomparisonslogical ops

The plex tokenizer and parser already handle >, >=, <=, !=, &&, ||, and %. They parse and type-check correctly. They just fall through to the default: return fmt.Errorf("unsupported operator") in the compiler. This lesson plugs those gaps — and uncovers a genuine bug in MemberAssignment along the way.

1. Comparison Operators in WAT

WAT has a full set of comparison instructions. For signed 64-bit integers (i64):

plexWAT instructionReturns
a < bi64.lt_si32
a > bi64.gt_si32
a <= bi64.le_si32
a >= bi64.ge_si32
a == bi64.eqi32
a != bi64.nei32

And for f64 (note: no _s suffix — floats don't have signed/unsigned variants):

plexWAT instructionReturns
a > bf64.gti32
a >= bf64.gei32
a <= bf64.lei32
a != bf64.nei32

The i32 return type quirk

Notice the "Returns" column: every comparison instruction, regardless of operand types, returns i32 — either 0 (false) or 1 (true). This is a deliberate WAT design choice: there is no boolean type in the type system. Booleans are just integers.

This is fine for if and while (which just pop an i32 condition), but it means you currently can't store a comparison result in a plex variable — the typechecker would call it an int (i64) but WAT left an i32 on the stack. Plex doesn't have a bool type yet, so this is a known limitation, not a bug to fix today.

WAT design note: Most ISAs have a similar property — ARM has condition flags, x86 has ZF/CF/etc., RISC-V has conditional branches but no explicit boolean register. WAT chose to standardise on i32 as the condition type for all control flow, keeping the type system simple.

In compiler.go, the existing BinaryExpression switch already has cases for +, -, *, /, <, and ==. You need to add the remaining six operators. The suffix logic follows the same pattern as the existing < and == cases: for integers, append _s to signed comparison instructions; for floats, no suffix.

// existing cases for reference:
case script.TokenType_LessThen:
    ltOp := prefix + ".lt"
    if prefix == "i32" || prefix == "i64" {
        ltOp += "_s"
    }
    c.emit(ltOp)
case script.TokenType_EqualEqual:
    c.emit(prefix + ".eq")  // eq has no _s suffix

The six new cases follow the same structure. != maps to .ne (no _s needed — equality and inequality are sign-agnostic at the bit level). >, >=, <= all need _s for integers.

While you're there, add % too — it maps to .rem_s for integers and .div doesn't apply for floats (WAT has no f64.rem; floating-point remainder is unusual, so you can error on it).

2. Logical Operators: && and ||

WAT has no logical AND or OR instructions. What it has are bitwise instructions: i32.and and i32.or. For booleans (0 and 1), bitwise and logical are equivalent:

aba && b (logical)a & b (bitwise)
0000
0100
1000
1111

Since WAT comparisons always produce 0 or 1, this works correctly whenever && and || are used to combine comparison results (which is the common case).

No short-circuit evaluation In most languages, a && b only evaluates b if a is true. In WAT with i32.and, both operands are pushed onto the stack before the instruction executes — there is no short-circuit. This means code like ptr != 0 && ptr.field > 0 would still dereference ptr even when it's null, because both sub-expressions are compiled and run before the and. Plex doesn't have pointers yet, so this won't bite you today. When it matters, you'd need to rewrite using nested if statements instead.

In the compiler, since both operands of &&/|| are comparison results (type: i32), always emit i32.and / i32.or regardless of the prefix:

case script.TokenType_AND:
    c.emit("i32.and")
case script.TokenType_OR:
    c.emit("i32.or")

3. The MemberAssignment Bug

Read the *script.MemberAssignment case in compiler.go carefully. It:

  1. Compiles the object → puts the struct's base pointer on the stack
  2. Looks up the field's offset in the struct definition
  3. Emits i32.const <offset> and i32.add → stack now has the field address
  4. Emits <type>.store

But a WAT store instruction pops two values from the stack: the address and the value to store. The generated code only has the address — the value to store is never compiled. The WAT would be invalid.

;; What the current code emits for point.x = 2.0
local.get $point → stack: [ptr]
i32.const 0 → stack: [ptr, 0]
i32.add → stack: [field-addr]
f64.store → TRAP: stack underflow — needs [addr, value], only has [addr]
;; What it should emit
local.get $point → stack: [ptr]
i32.const 0 → stack: [ptr, 0]
i32.add → stack: [field-addr]
f64.const 2.0 → stack: [field-addr, 2.0] ← THIS IS MISSING
f64.store → stack: [] ✓

The fix is a single line: call c.Compile(n.Value) immediately before the emit(store).

There's also a secondary issue: the existing code uses a local variable lookup (for _, i := range c.locals) to get the struct type name. But n.Object is an AstNode with a type already set by the typechecker. You can cast it to script.Expression and call GetType() directly — exactly what MemberAccess does. This is cleaner and handles cases where the object isn't a bare identifier (e.g., a method call result).

Check Your Understanding

1. i64.gt_s takes two i64 operands. What does it leave on the stack?

✅ An i32. All WAT comparison instructions return i32 (0 or 1) regardless of operand type. WAT has no boolean type — booleans are always represented as i32 values. The suffix _s describes how the operands are interpreted (signed), not the result type.

2. Why does != map to i64.ne (no _s suffix) while > maps to i64.gt_s?

✅ Equality and inequality test whether two bit patterns are identical. -1 in two's complement is 0xFFFFFFFF… — the same bit pattern interpreted as signed -1 or unsigned max. So equality is sign-agnostic and needs no _s/_u suffix. Greater-than comparison depends on sign: -1 > 0 when signed (true), but 0xFFFF… > 0 when unsigned (also true, for different reasons). For plex integers you want signed semantics, so _s.

3. Why must the value be compiled after the address computation in a struct field store?

✅ WAT's store instruction pops the address first (deeper in the stack), then the value (top of stack). So the sequence must be: compile the address expression → it lands deeper in the stack; compile the value expression → it lands on top; store pops both and writes. If you compiled value before address, the stack order would be wrong and WAT validation would fail.
