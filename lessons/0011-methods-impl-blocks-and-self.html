Lesson 11 – Methods, impl Blocks, and self

You've already wired up the scaffolding: impl Point { fn getX(): float { ... } } compiles to (func $__Point__getX (param $self i32) ...), and point.getX() compiles to a call $__Point__getX with the receiver injected as the first argument. This lesson is about understanding what you built — why each piece exists, where it could break, and how to extend it.

The mission is to learn compiler construction. The key insight in this lesson is one of the most important in language implementation:

Core idea

Methods are syntactic sugar for functions with a hidden first argument. There is no separate "method dispatch" machinery in our WAT output — just a function call with one extra parameter. Everything else is bookkeeping.

1. The uniform calling convention

WebAssembly has functions, not methods. A WAT function is identified by a single global name and takes a flat list of parameters. So when our language wants:

let point = Point(1, 1);
point.getX();

…the compiler has to translate that into something WASM understands. The translation is:

// Source                Compiled to (conceptually)
point.getX()          →   __Point__getX(point)
self.x                →   load_field(self, offset_of_x)

The point object becomes a regular argument. The method name getX becomes part of a longer global function name. This is the same trick C++ uses (name mangling), the same trick Go uses internally for method values, and the same trick Rust uses for trait methods.

Once you see methods as "functions with a hidden first arg and a decorated name", every other design choice in this lesson follows.

2. Why name mangling?

Suppose you have two structs:

struct Point { x: float; y: float; }
struct Rect  { w: float; h: float; }

impl Point { fn area(): float { return self.x * self.y; } }
impl Rect  { fn area(): float { return self.w * self.h; } }

Both area methods need to coexist in the WAT module's flat function namespace. If we emitted them both as (func $area ...), the second declaration would shadow the first — or more likely, wat2wasm would refuse to compile with a duplicate identifier error.

The fix: encode the receiver type into the function name.

Source name Mangled name ───────────────────────────────────── Point::area → __Point__area Rect::area → __Rect__area Point::getX → __Point__getX

Your scheme is __StructName__methodName (see line ~173 in compiler.go). This is fine for a learning compiler. Production compilers use more elaborate schemes that also encode parameter types (needed for overloading) — see Itanium C++ ABI mangling for a tour of the rabbit hole (spec).

Why double underscores?

Double underscores make collisions with user-defined function names unlikely — a user is unlikely to write fn __Point__area(). C++ reserves leading double-underscores for the implementation for the same reason. You could pick any separator that can't appear in a user identifier (e.g. . isn't allowed in WAT identifiers either, but $__ is more conventional).

3. Why structs became map[string]*structDef

You hit a subtle Go bug when wiring this up. The pre-pass registers each struct with an empty Methods slice. Later, when the impl block compiles, it wants to append to that slice:

def.Methods = append(def.Methods, method.Name)

With map[string]structDef (value), this doesn't work. Go's map lookup returns a copy. You'd be appending to a temporary that gets thrown away. The fix is to store pointers:

// before
structs map[string]structDef
// after
structs map[string]*structDef

Now c.structs[n.Name] returns the same pointer every time, and mutations through it are visible to subsequent lookups. This is one of the most common Go gotchas — see the Go spec on index expressions: "the value yielded by an indexed map expression is not addressable".

The mental model

If the pre-pass completely populated each struct (fields AND methods) before compilation began, you could keep value semantics. But the impl block mutates the struct during compilation — so you need a stable identity, which is what the pointer gives you.

4. The call-site lookup

When the compiler sees point.getX(), it has a FunctionCall whose Callee is a MemberAccess. The call-site logic (line ~377 in your compiler) does four things, in order:

  1. Find the receiver's type. typeofStruct(callee.Object) looks up point in c.locals and returns its Owner — the struct name. This is the dual of what Lesson 10 set up for field access.
  2. Validate the method exists. slices.Contains(def.Methods, callee.Field). If not, emit a compile error — better to fail at compile time than emit a call to a function WASM will reject at link time.
  3. Push the receiver as the first arg. c.Compile(callee.Object) — this emits local.get $point, leaving the i32 pointer on the WASM stack.
  4. Push the rest of the args, then call the mangled name.

Notice that steps 3 and 4 are exactly the same as a normal function call — the only difference is the implicit first argument. Once again: methods are functions with a hidden first arg.

5. The bugs you're sitting on

Your in-flight implementation has two real bugs. They don't fire on the trivial test case, but they will the moment you grow the language.

Bug 1: Methods is appended twice

Look at compiler.go lines ~148 and ~559. The same method name gets appended in both FunctionDeclaration and StructImplStatement:

// FunctionDeclaration (inside impl block)
d.Methods = append(d.Methods, n.Name)

// StructImplStatement (wrapping each method compile)
def.Methods = append(def.Methods, method.(*script.FunctionDeclaration).Name)

For a struct with method getX, def.Methods ends up as ["getX", "getX"]. Two consequences:

  • Memory grows linearly with the number of methods, for no reason.
  • The duplicate-method check (slices.Contains(d.Methods, n.Name)) is run before the second append, so it currently passes — but if you ever move that check, or use len(d.Methods) to mean something, it will misfire.

Bug 2: Single source of truth

The duplicate-name check and the method registration should live in one place. Two options:

  1. Keep it in FunctionDeclaration (eager — caught immediately as each method compiles) and remove the append from StructImplStatement.
  2. Move it to StructImplStatement as a pre-loop validation before compiling any method, and remove the append from FunctionDeclaration.

Option 1 is simpler — the method is already being compiled there, and you already have access to the struct definition. Option 2 is cleaner if you ever want a pre-pass over impl blocks (e.g. to support methods calling other methods on the same struct that are declared later in the impl block).

Task A — Fix the double-append

Pick option 1 or 2 above. Remove the redundant append. Add a second method to impl-struct.plex (e.g. getY) and verify the WAT output has each method registered exactly once. Inspect def.Methods in a debugger or with a temporary fmt.Println.

6. The interpreter's self vs the compiler's self

This is worth understanding because it crystallizes the difference between tree-walking and codegen.

In the interpreter (Lesson 4–6), calling point.getX() meant: push a new Environment, bind self to the point value in that environment, then evaluate the method body. self existed as a key in a Go map[string]Value.

In the compiler, self is a regular WASM local — slot 0 in the function's locals table. Nothing dynamic, nothing dictionary-based. The compiler emits (param $self i32) and adds a Local{Name: "self", Type: "i32", Owner: c.implBlock} to c.locals. From the body's perspective, self.x is no different from p.x where p is a parameter — Lesson 10's MemberAccess logic Just Works.

This is the payoff

You didn't have to write any new code to make self.x work — because self is just a local named "self". This is one of the quiet wins of using a uniform calling convention. Compare to languages that special-case this at every load site.

7. Stretch tasks

Task B — Methods with parameters and return values

Extend impl-struct.plex to add a distanceTo method:

impl Point {
    fn distanceTo(other: Point): float {
        // sqrt((self.x - other.x)^2 + (self.y - other.y)^2)
    }
}

You'll need sqrt as a builtin — for now, just compute the squared distance and skip the sqrt. The interesting part: the method takes a struct parameter (an i32 pointer), reads fields off both self and other, and returns a float.

Task C — A method calling another method

Add a method that calls another method on the same struct:

impl Point {
    fn getX(): float { return self.x; }
    fn doubleX(): float { return self.getX() * 2; }
}

Inside doubleX, the compiler sees self.getX(). Walk through your existing MemberAccess-inside-FunctionCall branch and trace what happens:

  • Does typeofStruct(self) resolve to "Point"? It should — you added self to c.locals with Owner: c.implBlock.
  • Is getX in def.Methods by the time doubleX is being compiled? This is the interesting question. If getX is declared after doubleX in the impl block, your current eager registration breaks down. If you went with option 1 in Task A, you may need a pre-pass over the impl block to register all method names before compiling any bodies.

This connects back to a general compiler pattern: two-pass compilation. The function declarations need to be visible before any of their bodies are compiled, so the compiler does a pass to collect signatures, then a pass to compile bodies. Crafting Interpreters covers this in the chapter on local variables for a similar reason (forward references).

Task D (deep) — A constructor method

Add a static method that doesn't take self — a constructor:

impl Point {
    fn origin(): Point { return Point(0, 0); }
}
// usage: let p = Point::origin();

This requires three things you don't have yet:

  1. A way to mark a method as not taking self (parser + AST change, or a convention like "no self parameter declared").
  2. A new call syntax Point::origin() in the parser (or reuse . and detect static at the call site).
  3. At the call site, recognise that the receiver is a type name rather than a value, and skip the self-injection step.

This is a stretch — don't do it unless you want to. But it's a great window into how languages distinguish instance methods, static methods, and free functions. Rust does this via the explicit self parameter; Java distinguishes static at the declaration; Python makes self a regular parameter but special-cases @staticmethod.

Q&A prompts

  • What would change in your design if methods could be polymorphic — e.g. a trait or interface that multiple structs implement? Where would dynamic dispatch happen, and what runtime representation would you need (vtable, fat pointer)?
  • The name-mangling scheme __Struct__method can't distinguish two methods with the same name but different parameter types (overloading). What's the smallest change to your scheme to support it? What problem does that create for the call site?
  • Your method check uses slices.Contains — O(n) per call. If a struct had 1000 methods, this would be a hotspot. What data structure would you switch to, and where in structDef would it live?
  • The interpreter pushed self into an Environment. The compiler makes it a WASM local. What's the equivalent in a register-based VM like the JVM or CPython bytecode? (Hint: look up the aload_0 JVM opcode.)
