Both are small fixes with high payoff.

1. The WAT If Format Bug

WAT has two text formats — and the compiler is mixing them.

Linear (stack) format uses keywords without parentheses and closes with end:

;; push condition first
local.get $n
i64.const 2
i64.lt_s
if           ;; pops condition from stack
  local.get $n
  return
end          ;; closes the if

Folded (S-expression) format uses parentheses and nests sub-expressions:

;; push condition first
local.get $n
i64.const 2
i64.lt_s
(if          ;; pops condition from stack
  (then
    local.get $n
    return
  )
)            ;; closes the (if

Your compiler currently emits if (linear keyword) followed by (then (folded keyword). wat2wasm sees if and expects the linear format, then finds ( where it expects body instructions — hence "unexpected token, expected end".

The fix is one character in the IfStatement case of compiler.go:

❌ Before

c.emit("if")
c.depth++
c.emit("(then")

✅ After

c.emit("(if")
c.depth++
c.emit("(then")

The rest of the if compiler (the (then ...) and closing )) is already correct for the folded format. (if still pops its condition from the stack — it just uses parentheses to open the block instead of the bare keyword.

After this change, wat2wasm accepts fib, and it returns the right answers:

fib(0)  = 0
fib(1)  = 1
fib(5)  = 5
fib(10) = 55

2. Unary Expressions

In plex, UnaryExpression covers two distinct things:

FormPostfixOperatorExample
Prefix unaryfalseTokenType_Minus-x
Prefix unaryfalseTokenType_Plus+x
Postfix incrementtrueTokenType_Incrmenti++
Postfix decrementtrueTokenType_Decrementi--

Prefix minus: the integer negation problem

Floating-point types have a direct negation instruction: f64.neg. Integer types do not. To negate an integer in WAT you compute 0 - x. But this creates an ordering problem on the stack — you need to push 0 before x, then subtract:

;; -x for f64: simple
local.get $x
f64.neg

;; -x for i64: push 0 first, then x, then subtract
i64.const 0
local.get $x     ;; x is pushed AFTER 0
i64.sub          ;; 0 - x

This means the integer case is structured differently from the float case in the compiler: for floats, you compile the operand then emit the instruction; for integers, you emit the zero-constant first, compile the operand, then subtract.

Postfix increment: the double-push pattern

The semantics of i++ (post-increment): evaluate to the old value, then increment. So let x = i++; gives x the old value of i, and i gets incremented.

On a stack machine, that looks like:

local.get $i → stack: [old] ← this will be the "result" value
local.get $i → stack: [old, old]
i64.const 1 → stack: [old, old, 1]
i64.add → stack: [old, new]
local.set $i → stack: [old] ← new value stored back, old remains

After these five instructions, the old value is on the stack (available to the caller), and i has been incremented. When used as a statement, the old value on the stack gets dropped by the drop logic you added in Lesson 16.

The implementation needs the variable name (to emit local.set $i). Since plex only allows increment/decrement on identifiers, you can type-assert the operand:

ident, ok := n.Operand.(*script.Identifier)
if !ok {
    return fmt.Errorf("compile: ++ / -- requires a variable, not %T", n.Operand)
}
Pre vs post: Pre-increment (++i) would yield the new value. In WAT you'd use local.tee for that: get, add 1, local.tee (stores AND leaves new value on stack). Plex only has postfix, so you don't need to implement this — but knowing the difference is useful when you read WAT generated by other compilers.

Check Your Understanding

1. Why can't you use f64.neg for integer negation?

✅ WAT's integer instruction set simply doesn't include a negate instruction. Integer arithmetic is add, sub, mul, div_s, etc. — no unary negate. You have to synthesize it as 0 - x. This is a common CPU ISA decision too: x86 has NEG but RISC-V integer has no unary negate either.

2. In the double-push pattern for i++, why is local.get $i emitted twice?

✅ The first local.get puts the old value on the stack where it will remain as the expression result (or be dropped). The second local.get puts another copy on the stack so the increment computation has something to work with without consuming the result copy.

3. The WAT if format uses (if not if. But the condition is still pushed separately — the (if doesn't take a sub-expression for its condition. Why is that valid?

✅ Whether you write if or (if, the condition is always the top of the stack at the point the instruction is evaluated. The folded/unfolded distinction only affects the syntax of the body (keywords vs parentheses). The operand stack mechanism is identical.
