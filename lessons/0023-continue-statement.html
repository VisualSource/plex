1. What continue does

continue skips the rest of the current loop body and jumps directly to the condition check for the next iteration. This plex program should sum only the even numbers from 0 to 9:

fn sum_evens(): i64 {
    let mut i: i64 = 0;
    let mut sum: i64 = 0;
    while i < 10 {
        i = i + 1;
        if (i % 2) != 0 {
            continue;   // skip odd numbers
        }
        sum = sum + i;
    }
    return sum;   // 2+4+6+8+10 = 30
}

That looks straightforward. But at the WAT level, how do you "jump back to the condition"?

2. The WAT secret: br behaves differently on block vs loop

WebAssembly has structured control flow — no arbitrary jumps, no labels on arbitrary instructions. The only branching constructs are block, loop, and if. The br instruction targets one of these by label.

The key rule
br to a block → exits the block (jumps forward to after the closing ))
br to a loop → restarts the loop (jumps backward to the opening (loop)

This is not a difference in instruction — it's the same br opcode. The target determines the direction. Look at how the plex compiler currently emits a while loop:

(block $block0          ← break targets this: exits the whole loop
  (loop $loop0           ← continue targets this: restarts from here
    <condition>
    i32.eqz
    br_if $block0        ← exit when condition is false

    <body statements>
        br $loop0           ← a continue; would emit exactly this
    </more body>

    br $loop0            ← unconditional restart at end of body
  )
)

A continue; statement compiles to exactly br $loop0 — the same instruction that's already emitted unconditionally at the end of every loop body. The only difference is that it fires earlier, in the middle of the body, skipping what follows.

break → br $block0

br $block0
; jumps PAST the loop:
; execution continues
; after the closing ) of block

continue → br $loop0

br $loop0
; jumps BACK to loop top:
; condition is re-evaluated
; next iteration begins

3. The existing label infrastructure

When the compiler enters a while loop it calls pushBreakLabel(). Look at what that already creates in compiler.go:

func (c *Compiler) pushBreakLabel() (string, string) {
    bl := fmt.Sprintf("$block%d", c.labelCount)   // for break
    ll := fmt.Sprintf("$loop%d", c.labelCount)    // for continue
    c.labelCount++
    c.breakStack = append(c.breakStack, bl)       // saved — break uses it
    return bl, ll
}

Both labels are already being created. ll is already used as the literal WAT label in the emitted output. The only missing piece is saving ll somewhere so ContinueStatement can reference it — just as bl is saved in breakStack.

And add the function (mirrors parseBreakStatement exactly):

func (p *Parser) parseContinueStatement() (AstNode, error) {
    start, _ := p.advance().Range()

    tok, err := p.expect(TokenType_Semicolon)
    if err != nil {
        return nil, err
    }

    _, end := tok.Range()

    return &ContinueStatement{
        Start: start,
        End:   end,
    }, nil
}

5a — compiler/structs.go: add continueStack alongside breakStack in the Compiler struct:

5b — compiler/compiler.go: update pushBreakLabel to also save ll, update popBreakLabel to pop it, and add currentContinueLabel:

func (c *Compiler) pushBreakLabel() (string, string) {
    bl := fmt.Sprintf("$block%d", c.labelCount)
    ll := fmt.Sprintf("$loop%d", c.labelCount)
    c.labelCount++
    c.breakStack    = append(c.breakStack,    bl)
    c.continueStack = append(c.continueStack, ll)  // ← new
    return bl, ll
}

func (c *Compiler) popBreakLabel() {
    c.labelCount--
    c.breakStack    = c.breakStack[:len(c.breakStack)-1]
    c.continueStack = c.continueStack[:len(c.continueStack)-1]  // ← new
}

func (c *Compiler) currentContinueLabel() string {  // ← new
    return c.continueStack[len(c.continueStack)-1]
}

5c — compiler/compiler.go: add the ContinueStatement compile case beside BreakStatement:

case *script.ContinueStatement:
    if len(c.continueStack) == 0 {
        return fmt.Errorf("continue outside of loop")
    }
    c.emit(fmt.Sprintf("br %s", c.currentContinueLabel()))
Why not use br_if? A continue is unconditional — control always transfers. br (not br_if) is correct. The if condition in plex source is already handled by the surrounding if statement's own block structure; by the time we compile the continue node, we're already inside the true branch.

func TestContinue(t *testing.T) {
    src := `
        fn sum_evens(): i64 {
            let mut i: i64 = 0;
            let mut sum: i64 = 0;
            while i < 10 {
                i = i + 1;
                if (i % 2) != 0 {
                    continue;
                }
                sum = sum + i;
            }
            return sum;
        }
    `

    validateByRun(t, src, []testRun{
        {
            fn:   "sum_evens",
            args: []uint64{},
            want: []uint64{30},
        },
    }, func(ctx context.Context, r wazero.Runtime) {})
}

Expected: the function returns 30 (= 2+4+6+8+10). Check the WAT snapshot — the continue; should appear as a bare br $loop0 inside the if block.

Also test that continue correctly interacts with nested loops — a continue inside the inner loop should only restart the inner loop, not the outer one. The stack-based label system handles this automatically.
