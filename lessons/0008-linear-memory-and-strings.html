Lesson 8 – Linear Memory and Strings

Your compiler handles numbers and control flow. But plex also has strings, arrays, and structs — none of which fit in an f64. This lesson explains how WASM handles complex types, and gets you emitting strings from the compiler.

1. The problem: WASM only knows four types

At the instruction level, WASM has exactly four value types: i32, i64, f32, f64. There is no string type, no pointer type, no array type. Everything more complex than a number lives in linear memory.

Linear memory is a flat, byte-addressable array that grows in 64 KiB pages. Your code reads and writes it using load/store instructions. An i32 on the stack is just a byte offset into that array — a raw address. The WASM runtime itself has no idea whether offset 42 holds the start of a string or a struct field; that interpretation is entirely up to your program.

byte offset: 0 1 2 3 4 5 6 7 8 ... memory: [ 'h' 'e' 'l' 'l' 'o' '\0' 5.0 (f64 across 8 bytes) ... ] ^ ^ string at offset 0 f64 stored at offset 6

Memory instructions

The main load/store instructions you'll use:

;; store a byte (i32 truncated to 8 bits) at address
i32.const 0      ;; address
i32.const 72     ;; value ('H')
i32.store8       ;; mem[0] = 72

;; load a byte from address
i32.const 0
i32.load8_u      ;; push mem[0] as unsigned i32

;; store an f64 at address (uses 8 bytes)
i32.const 8      ;; address
f64.const 3.14
f64.store        ;; mem[8..15] = 3.14

Every load/store takes an address (i32 on the stack) as its first operand, then the value to store (or leaves the loaded value on the stack).

2. Declaring memory in WAT

A module declares how many pages of memory it needs:

(module
  (memory 1)           ;; 1 page = 65,536 bytes
  (export "memory" (memory 0))  ;; optional: let the host read memory too
  ...
)

One page (65,536 bytes) is enough for anything reasonable in a teaching compiler. If your program needed dynamic growth you'd call memory.grow, but we won't need that here.

3. Static strings: the data section

The simplest way to put strings into memory is to lay them out at compile time using a (data ...) declaration. The assembler writes the bytes into memory before the program even starts running.

(module
  (memory 1)
  (data (i32.const 0) "hello\00")   ;; writes 6 bytes starting at offset 0
  (data (i32.const 6) "world\00")   ;; writes 6 bytes starting at offset 6

  (func $main
    i32.const 0   ;; address of "hello"
    call $print   ;; host function that reads from memory
  )
)

Notice what the string value becomes in the instruction stream: just an i32.const with its offset. The string data isn't on the stack — only its address is.

The two-pass strategy

To compile string literals you need their addresses before you emit any instructions, because the data section comes first in the WAT output. The cleanest approach is a two-pass compiler:

  1. Pass 1 (collect) — walk the entire AST looking for *script.StringLiteral nodes. Record each unique string and assign it a byte offset.
  2. Pass 2 (emit) — emit the module header, the memory declaration, the data sections, then compile all functions normally. When you hit a StringLiteral in Pass 2, look up its offset and emit i32.const <offset>.

Why not a single pass?

You could buffer all function output in a strings.Builder and prepend the header later — that's a valid one-pass approach. Two passes are conceptually cleaner for a teaching compiler because each pass has a single clear purpose.

4. Implementation

New fields on Compiler

Add a string table to track which strings you've seen and their offsets:

type stringEntry struct {
    value  string
    offset int
}

type Compiler struct {
    out     strings.Builder
    locals  []string
    depth   int
    strings []stringEntry  // collected in pass 1
    dataPtr int            // next free byte in static data area
}

Pass 1: collectStrings

Walk the AST and record every *script.StringLiteral. Null-terminate each one so C-style host functions (like a WASI print) can read them:

func (c *Compiler) collectStrings(node script.AstNode) {
    switch n := node.(type) {
    case *script.Program:
        for _, s := range n.Stmts { c.collectStrings(s) }
    case *script.FunctionDeclaration:
        c.collectStrings(n.Body)
    case *script.Block:
        for _, s := range n.Stmts { c.collectStrings(s) }
    case *script.IfStatement:
        c.collectStrings(n.Condition)
        c.collectStrings(n.Body)
        if n.Else != nil { c.collectStrings(n.Else) }
    case *script.WhileStatement:
        c.collectStrings(n.Condition)
        c.collectStrings(n.Body)
    case *script.ReturnStatement:
        if n.Value != nil { c.collectStrings(n.Value) }
    case *script.VariableDeclaration:
        c.collectStrings(n.Init)
    case *script.FunctionCall:
        for _, a := range n.Args { c.collectStrings(a) }
    case *script.StringLiteral:
        // null-terminate: length = len(value) + 1
        c.strings = append(c.strings, stringEntry{value: n.Value, offset: c.dataPtr})
        c.dataPtr += len(n.Value) + 1
    }
}

Compiling StringLiteral

In the main Compile switch, look up the offset and push it as an i32:

case *script.StringLiteral:
    for _, entry := range c.strings {
        if entry.value == n.Value {
            c.emit(fmt.Sprintf("i32.const %d", entry.offset))
            return nil
        }
    }
    return fmt.Errorf("compile: string %q not in table", n.Value)

Emitting the module header

Update CompileProgram to run the collect pass first, then emit the memory declaration and data sections before the functions:

func CompileProgram(program *script.Program) (string, error) {
    c := &Compiler{}
    c.collectStrings(program)

    c.emit("(module")
    c.depth++

    if len(c.strings) > 0 {
        c.emit("(memory 1)")
        c.emit(fmt.Sprintf("(export \"memory\" (memory 0))"))
        for _, entry := range c.strings {
            // escape the string for WAT: backslash → \\, quote → \"
            escaped := strings.ReplaceAll(entry.value, "\\", "\\\\")
            escaped = strings.ReplaceAll(escaped, "\"", "\\\"")
            c.emit(fmt.Sprintf("(data (i32.const %d) \"%s\\00\")", entry.offset, escaped))
        }
    }

    for _, stmt := range program.Stmts {
        if err := c.Compile(stmt); err != nil {
            return "", err
        }
    }
    c.depth--
    c.emit(")")
    return c.out.String(), nil
}

5. Calling a host print function

Your WASM module doesn't know how to print — that's the host's job (Node.js, the browser, a Go runtime). You wire them together with an import.

In WAT, declare the import at the top of the module:

(import "env" "print_str" (func $print_str (param i32)))

This says: "I expect the host to provide a function named print_str in the env namespace. It takes one i32 (the string offset) and returns nothing."

Then in Node.js, you provide that function when instantiating the module:

const memory = new WebAssembly.Memory({ initial: 1 });

const imports = {
  env: {
    print_str(offset) {
      // read null-terminated string from WASM memory
      const bytes = new Uint8Array(memory.buffer);
      let str = "";
      while (bytes[offset] !== 0) str += String.fromCharCode(bytes[offset++]);
      console.log(str);
    }
  }
};

const { instance } = await WebAssembly.instantiate(bytes, imports);

The memory must be shared

The host's print_str reads from the same WebAssembly.Memory object that the module uses. If you export the memory from the module (as shown above) and use it as the shared memory in the import object, both sides see the same bytes. If you don't share the object, the host reads from a different buffer — it sees garbage.

6. What this unlocks

Once memory exists, arrays and structs follow the same pattern — they're just blobs of bytes at known offsets. An array is: 4 bytes for the length (i32), then N × element-size bytes for the elements. A struct is: the fields laid out sequentially with known offsets (a "struct layout").

All the load/store logic your interpreter did implicitly (putting values in a Go map) the compiler now does explicitly with byte offsets. Same logical operation; completely different implementation.
