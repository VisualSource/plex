Introduction to Code Generation

From evaluating trees to emitting WebAssembly

The Mindset Shift

The interpreter walks the AST and computes results in Go memory. A compiler walks the same AST and emits instructions that a different machine will later execute. The tree traversal is identical — what changes is what you do at each node.

Interpreter — eval NumberLiteral
// computes immediately
case *NumberLiteral:
    f, _ := strconv.ParseFloat(n.Value, 64)
    return NumberValue{V: f}, nil
Compiler — compile NumberLiteral
// emits an instruction
case *NumberLiteral:
    c.emit("f64.const", n.Value)
    return nil
The key insight
The recursive structure of your AST maps directly to the order in which you emit instructions. The compiler is just Eval with return value replaced by emit instruction.

WebAssembly: a Stack Machine

WebAssembly is a stack machine. Every instruction either pushes a value onto an implicit stack or pops operands and pushes a result. There are no visible registers — just the stack.

Trace through 1 + 2 * 3. The AST puts * deeper (higher precedence), so the compiler visits it first:

f64.const 1 → [ 1 ]
f64.const 2 → [ 1, 2 ]
f64.const 3 → [ 1, 2, 3 ]
f64.mul → [ 1, 6 ]
f64.add → [ 7 ]

The postorder traversal of the AST is the instruction sequence. You emit left operand, then right operand, then the operator — which is exactly the order recursive compile functions produce them.

WAT: the Text Format

WebAssembly has a human-readable text format called WAT. You'll generate this first — it's debuggable, and wazero can run it after converting to binary with wat2wasm, or you can use a Go WAT parser. Here's what a compiled plex function looks like:

;; plex source: fn add(a: int, b: int): int { return a + b; }
(module
  (func $add (param $a f64) (param $b f64) (result f64)
    local.get $a
    local.get $b
    f64.add)
  (export "add" (func $add))
)
Types: the first hard problem
WASM is statically typed: every value is i32, i64, f32, or f64. Plex uses dynamic values. For a first pass: compile all plex numbers to f64. This is exactly what early JavaScript engines did. Structs, arrays, and strings require WASM linear memory — that's Lesson 7.

The Compiler Struct

The compiler needs to track state that Eval didn't: which locals are declared in the current function, and what output we're building. A simple struct handles both:

type Compiler struct {
    out    strings.Builder
    locals []string // param and let names in current function
    depth  int       // indentation
}

func (c *Compiler) emit(parts ...string) {
    c.out.WriteString(strings.Repeat("  ", c.depth))
    c.out.WriteString(strings.Join(parts, " "))
    c.out.WriteRune('\n')
}

func CompileProgram(program *script.Program) (string, error) {
    c := &Compiler{}
    c.emit("(module")
    c.depth++
    for _, stmt := range program.Stmts {
        if err := c.Compile(stmt); err != nil {
            return "", err
        }
    }
    c.depth--
    c.emit(")")
    return c.out.String(), nil
}

Compiling Expressions

Each expression case emits its children first, then its own instruction — postorder, just like the stack trace above:

case *script.NumberLiteral:
    c.emit("f64.const", n.Value)

case *script.Identifier:
    c.emit("local.get", "$"+n.Value)

case *script.BinaryExpression:
    if err := c.Compile(n.Left); err != nil { return err }
    if err := c.Compile(n.Right); err != nil { return err }
    switch n.Operator {
    case script.TokenType_Plus:  c.emit("f64.add")
    case script.TokenType_Minus: c.emit("f64.sub")
    case script.TokenType_Star:  c.emit("f64.mul")
    case script.TokenType_Div:   c.emit("f64.div")
    case script.TokenType_LessThen: c.emit("f64.lt")
    case script.TokenType_EqualEqual: c.emit("f64.eq")
    default: return fmt.Errorf("unsupported operator: %v", n.Operator)
    }

Compiling Functions

A function declaration emits a WAT func block. Parameters become WASM locals. Local variables declared with let become mutable locals declared at the top of the function.

case *script.FunctionDeclaration:
    // build param signature: (param $a f64) (param $b f64)
    params := strings.Builder{}
    c.locals = []string{}
    for _, p := range n.Params {
        param := p.(*script.Parameter)
        params.WriteString(fmt.Sprintf(" (param $%s f64)", param.Name))
        c.locals = append(c.locals, param.Name)
    }

    result := ""
    if n.ReturnType != nil {
        result = " (result f64)"
    }

    c.emit(fmt.Sprintf("(func $%s%s%s", n.Name, params.String(), result))
    c.emit(fmt.Sprintf("(export \"%s\" (func $%s))", n.Name, n.Name))
    c.depth++

    // first pass: collect let declarations so we can emit (local $x f64) headers
    for _, local := range collectLocals(n.Body) {
        c.emit(fmt.Sprintf("(local $%s f64)", local))
    }

    if err := c.Compile(n.Body); err != nil { return err }
    c.depth--
    c.emit(")")

case *script.ReturnStatement:
    if n.Value != nil {
        if err := c.Compile(n.Value); err != nil { return err }
    }
    c.emit("return")

case *script.VariableDeclaration:
    if err := c.Compile(n.Init); err != nil { return err }
    c.emit("local.set $" + n.Name)

case *script.AssignmentExpression:
    if err := c.Compile(n.Value); err != nil { return err }
    c.emit("local.set $" + n.Name)
Why collect locals first?
In WASM, all local variables must be declared at the top of the function before any instructions. But in plex, let can appear anywhere in the body. A pre-pass walks the block collecting all VariableDeclaration names so you can emit their (local $x f64) declarations up front.

collectLocals — the pre-pass

func collectLocals(node script.AstNode) []string {
    var names []string
    switch n := node.(type) {
    case *script.Block:
        for _, s := range n.Stmts {
            names = append(names, collectLocals(s)...)
        }
    case *script.VariableDeclaration:
        names = append(names, n.Name)
    case *script.IfStatement:
        names = append(names, collectLocals(n.Body)...)
        if n.Else != nil { names = append(names, collectLocals(n.Else)...) }
    case *script.WhileStatement:
        names = append(names, collectLocals(n.Body)...)
    }
    return names
}

Compiling Control Flow

WASM has structured control flow — no goto, no arbitrary jumps. if and loops use block syntax:

case *script.IfStatement:
    if err := c.Compile(n.Condition); err != nil { return err }
    c.emit("(if")
    c.depth++
    c.emit("(then")
    c.depth++
    if err := c.Compile(n.Body); err != nil { return err }
    c.depth--
    c.emit(")")
    if n.Else != nil {
        c.emit("(else")
        c.depth++
        if err := c.Compile(n.Else); err != nil { return err }
        c.depth--
        c.emit(")")
    }
    c.depth--
    c.emit(")")

case *script.WhileStatement:
    // WASM loops: (block (loop ... br_if 1 ... br 0))
    // br 0 = branch to loop top; br_if 1 = break out of block
    c.emit("(block")
    c.depth++
    c.emit("(loop")
    c.depth++
    if err := c.Compile(n.Condition); err != nil { return err }
    c.emit("i32.eqz")   // invert: exit if condition false
    c.emit("br_if 1")  // jump out of block if condition false
    if err := c.Compile(n.Body); err != nil { return err }
    c.emit("br 0")     // jump back to loop top
    c.depth--
    c.emit(")") // end loop
    c.depth--
    c.emit(")") // end block
Structured control flow is not a limitation
WASM deliberately has no goto. The (block (loop ...)) pattern is how every loop compiles. br 0 means "branch to the start of the innermost enclosing loop." br_if 1 means "branch out of the block one level up if condition is true." The numbers are depth indices, not labels. See the WASM spec for the formal model.
