Lesson 10 – Struct Layout and Field Access

Arrays were the first heap-allocated type. Structs are the second — and the conceptual leap is small. Where an array uses a sequential index to find elements, a struct uses compile-time field offsets. The runtime arithmetic is almost identical.

But before structs, there's a small bug to fix from Lesson 9.

0. Quick fix: clear(c.tempArrayVars)

In FunctionDeclaration you call clear(c.tempArrayVars) after compiling the body. Go's clear zeros all elements but does not change len — so the next function with arrays will find stale length, and the pop c.tempArrayVars[len(c.tempArrayVars)-1] will return "".

Fix: reset the slice to empty after each function.

// instead of: clear(c.tempArrayVars)
c.tempArrayVars = c.tempArrayVars[:0]

This keeps the underlying array (no allocation) but sets len back to zero.

1. Struct layout

A struct is a block of bytes in memory. Each field occupies a fixed-size slot at a known offset from the base address. The compiler determines those offsets once, at compile time, and uses them every time a field is read or written.

For a struct with all f64 fields (8 bytes each):

struct Point { x: float; y: float; } offset 0: [x: f64] 8 bytes offset 8: [y: f64] 8 bytes total size = 16 bytes

For mixed types:

struct Rect { x: float; y: float; w: float; h: float; } offset 0: [x: f64] 8 bytes offset 8: [y: f64] 8 bytes offset 16: [w: f64] 8 bytes offset 24: [h: f64] 8 bytes total size = 32 bytes

The offset of each field is the sum of the sizes of all preceding fields. For a teaching compiler where everything is either f64 (8 bytes), i64 (8 bytes), i32 (4 bytes), or a pointer (i32, 4 bytes), you can compute this with a running total.

2. The struct registry

The compiler needs to know the layout of every struct before it can compile field access. Add a registry of struct definitions:

type StructField struct {
    Name   string
    Type   string // WASM type
    Offset int    // byte offset from struct base
}

type StructDef struct {
    Name   string
    Fields []StructField
    Size   int // total bytes
}

type Compiler struct {
    // ... existing fields ...
    structs map[string]StructDef
}

Initialize it in CompileProgram alongside the other setup.

Registering a struct

When the compiler encounters a *script.StructStatement, it should register the struct and then not emit any WAT — structs have no runtime representation at the declaration site. They only take up space when constructed.

func (c *Compiler) registerStruct(n *script.StructStatement) {
    var fields []StructField
    offset := 0
    for _, f := range n.Fields {
        param := f.(*script.Parameter)
        wasmType := resolveType(param.Type)
        size := sizeOf(wasmType)
        fields = append(fields, StructField{
            Name:   param.Name,
            Type:   wasmType,
            Offset: offset,
        })
        offset += size
    }
    c.structs[n.Name] = StructDef{Name: n.Name, Fields: fields, Size: offset}
}

You need a helper that maps a WASM type to its byte size:

func sizeOf(wasmType string) int {
    switch wasmType {
    case "f64", "i64":
        return 8
    case "f32", "i32":
        return 4
    default:
        return 8 // default to 8 (pointer-sized on 64-bit host, but i32 in WASM)
    }
}

Task A — Register structs in a pre-pass

Add a collectStructs method that walks the program and calls registerStruct for every *script.StructStatement. Call it from CompileProgram before the main compile loop, so struct definitions are always available before any function tries to construct or access them.

In the Compile switch, add a case for *script.StructStatement that just calls registerStruct and returns — no WAT emitted.

3. Struct construction

In plex, you construct a struct by calling its name as a function: Point(1.0, 2.0). In the interpreter, FunctionCall checked whether the callee was a StructType and handled it specially. The compiler does the same thing — check the struct registry first.

The construction sequence:

  1. Allocate struct.Size bytes with $alloc.
  2. For each field (in order), compile the corresponding argument and store it at base + field.Offset.
  3. Leave the base address on the stack.

This is almost identical to ArrayLiteral — allocate, write fields, return pointer. The difference is that field offsets come from the struct definition, not a uniform stride.

Task B — Compile struct construction

In the *script.FunctionCall case, before emitting call $name, check whether the callee identifier matches a registered struct:

case *script.Identifier:
    if def, ok := c.structs[callee.Value]; ok {
        // struct construction — same temp-var pattern as ArrayLiteral
        // alloc def.Size bytes
        // tee into temp local
        // for each field: local.get tmp, i32.const offset, i32.add, compile arg, TYPE.store
        // local.get tmp  (leave pointer on stack)
    } else {
        c.emit("call $" + callee.Value)
    }

You'll need another temp variable — you can reuse the same tempArrayVars mechanism, or add a dedicated tempStructVars slice. Simpler: unify them into a single tempVars slice since the purpose is the same (hold a heap pointer temporarily).

4. Field access: MemberAccess

Reading p.x compiles to: compute the address of the field, then load.

;; p.x where p is i32 pointer to a Point, x is at offset 0
local.get $p
i32.const 0     ;; field offset
i32.add
f64.load        ;; load an f64

For p.y (offset 8):

local.get $p
i32.const 8
i32.add
f64.load

The compiler looks up the field name in the struct definition to find the offset. The tricky part: how does the compiler know what struct type p holds?

Right now, your typeOf returns "i32" for any pointer — it doesn't track which struct type an i32 points to. For field access you need the struct name, not just "i32".

The minimal solution: a local type table

Extend Local with an optional struct name:

type Local struct {
    Name       string
    Type       string // WASM type
    StructName string // set when Type == "i32" and it points to a struct
}

When you collect locals for a variable declaration whose initialiser is a struct construction call, record the struct name. Then in *script.MemberAccess, look up the local's struct name to find the field definition.

Task C — Compile MemberAccess

Add *script.MemberAccess to Compile:

case *script.MemberAccess:
    // 1. compile the object expression (pushes i32 base address)
    if err := c.Compile(n.Object); err != nil {
        return err
    }
    // 2. find which struct type the object is
    structName := c.structNameOf(n.Object)
    def, ok := c.structs[structName]
    if !ok {
        return fmt.Errorf("compile: unknown struct %q for member access", structName)
    }
    // 3. find the field offset
    for _, field := range def.Fields {
        if field.Name == n.Field {
            c.emit(fmt.Sprintf("i32.const %d", field.Offset))
            c.emit("i32.add")
            c.emit(field.Type + ".load")
            return nil
        }
    }
    return fmt.Errorf("compile: struct %q has no field %q", structName, n.Field)

You'll need structNameOf(node AstNode) string — a helper that, given an expression node, returns the struct name it evaluates to. For an *Identifier, look it up in c.locals and return its StructName.

5. Field assignment: MemberAssignment

Writing p.x = 5.0 is a store instead of a load. The pattern: compute the field address, compile the right-hand value, store.

;; p.x = 5.0
local.get $p
i32.const 0     ;; offset of x
i32.add
f64.const 5.0
f64.store

Task D (stretch) — Compile MemberAssignment

Same lookup pattern as MemberAccess, but emit TYPE.store instead of TYPE.load, with the value compiled after the address calculation.

6. End-to-end test

Write a plex program and compile it, then verify the WAT with wat2wasm:

struct Point { x: float; y: float; }

fn make_point(x: float, y: float): Point {
    return Point(x, y);
}

fn get_x(p: Point): float {
    return p.x;
}

Expected WAT (roughly):

(module
  (memory 1)
  (global $heapPtr (mut i32) (i32.const 0))
  ...
  (func $make_point (param $x f64) (param $y f64) (result i32)
    i32.const 16      ;; sizeof Point
    call $alloc
    local.tee $tmp

    f64.store

Q&A prompts

  • What happens if two struct fields have different sizes — say one i32 and one f64? Does the layout calculation still work?
  • In C, compilers add padding between fields to keep them aligned to their natural size (a f64 at byte offset 4 would be misaligned). Does WASM require this? What does f64.store do with an unaligned address?
  • How would you handle impl blocks — methods on a struct — in the compiler? The interpreter injected self into the environment. What's the equivalent in WASM?
