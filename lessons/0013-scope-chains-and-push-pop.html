Lesson 13 – Scope Chains: The Push/Pop Pattern

Your type checker has a working Scope chain. The data structure is right. The bug is one missing step: when you enter a function body, you never tell the checker "look in this scope now." Variable lookups in the body fall through to the global scope and fail on every argument.

This lesson teaches the push/pop pattern — the universal way type checkers (and interpreters) track which scope is "current" as they recurse into nested constructs.

1. How your scope chain already works

Your Scope struct is a linked list of maps. Each node points to its parent. Lookup walks up the chain until it finds the name or exhausts the list:

func (s *Scope) Get(ident string) *script.Type {
    if t, ok := s.vars[ident]; ok {
        return t              // found here
    }
    if s.parent == nil {
        return nil            // exhausted
    }
    return s.parent.Get(ident) // try parent
}

This is the textbook environment model — the same structure used in every Lisp interpreter ever written, in Go's own scoping rules, and in Crafting Interpreters §11. The design is correct. What's missing is the pointer discipline on c.scope.

2. The bug in your current code

In typecheck.go, the FunctionDeclaration case populates fn.Scope with the parameters — but then calls checkStmt(n.Body) without switching c.scope:

case *script.FunctionDeclaration:
    fn := c.funcs[n.Name]

    for _, arg := range n.Params {
        t := c.checkExpression(arg)
        fn.Args[arg.Name].Type = t
        fn.Scope.vars[arg.Name] = t   // ✓ args go into fn.Scope
    }

    c.checkStmt(n.Body)              // ✗ c.scope is still the GLOBAL scope
    // Body tries c.scope.Get("x") → looks in global → not found → error

fn.Scope has the right data. c.scope just doesn't point at it. Every Identifier lookup inside the body calls c.scope.Get(...), which is still global.

3. The fix: push before, pop after

The pattern is three lines, always in the same order:

// 1. Save the current scope
prev := c.scope

// 2. Push the new scope as current
c.scope = newScope

// ... recurse into the body ...

// 3. Pop back to the saved scope
c.scope = prev

Applied to your FunctionDeclaration case:

case *script.FunctionDeclaration:
    c.checkExpression(n.ReturnType)
    fn := c.funcs[n.Name]

    for _, arg := range n.Params {
        t := c.checkExpression(arg)
        fn.Args[arg.Name].Type = t
        fn.Scope.vars[arg.Name] = t
    }

    prev := c.scope          // save
    c.scope = fn.Scope       // push
    c.checkStmt(n.Body)
    c.scope = prev           // pop

That's the entire fix. Three lines. The recursion now sees the function's scope, and parent-chain lookup reaches the global scope automatically because fn.Scope was created with newScope(c.scope) in collectSignatures.

Why save and restore instead of just navigating with parent?

After checking the body you need to return to exactly where you were, not just "one level up". If functions are ever nested — or if you later add closures — the parent chain doesn't give you a reliable way back. Saving and restoring the pointer is O(1) and immune to nesting depth.

4. When to push a new scope

The rule is: any construct that introduces a new binding lifetime needs its own scope. For plex right now:

ConstructCreate new scope?Why
Function body Yes — already in FuncInfo.Scope Parameters and locals must not leak to callers
Block (if/else/while body) Yes — not yet done Variables declared in an if branch must not outlive it
Individual expression No Expressions don't declare variables
Top-level Program Global scope only — already done The root; has no parent

For blocks (if/for/while), the same push/pop pattern applies — but you create the scope on the fly instead of looking it up from FuncInfo:

case *script.Block:
    prev := c.scope
    c.scope = newScope(c.scope)    // fresh child scope
    for _, stmt := range n.Stmts {
        c.checkStmt(stmt)
    }
    c.scope = prev

Variable declarations inside that block call c.scope.Set(...), which writes to the new child. When the block ends, the child scope is simply abandoned — Go's GC cleans it up. Variables in the block are invisible to the outer scope because lookup only walks up the chain, never down.

Shadowing falls out for free

If an inner scope has the same name as an outer one, Get returns the inner binding first because it searches from the innermost scope outward. You don't need special shadowing logic — the chain order handles it.
