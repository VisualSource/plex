Lesson 12 – Type Checking as a Separate Pass

Your compiler currently mixes type checking into code generation. The checks are scattered across typeOf, typeofStruct, the BinaryExpression case, the VariableDeclaration case, the MemberAccess case — and so on. This lesson is about lifting that work into a separate compiler pass.

This is one of the most important architectural moves in compiler construction. Once you see it, you start seeing it everywhere — LLVM has dozens of passes, GCC has hundreds, Rust's compiler has a strict sequence (parse → name resolution → HIR → type check → MIR → codegen). The discipline of "do one job per pass" is what makes those compilers comprehensible at scale.

Core idea

A type checker is just a tree-walking interpreter that produces types instead of values. Same shape as your interpreter from Lesson 4. Same recursion. Different output type.

1. Why separate the pass?

Right now, your codegen does two jobs at once: check that the program is valid and emit WAT. Mixing them has four concrete costs:

ProblemWhat it looks like in your code
Half-compiled output on errors If BinaryExpression errors at line ~107 with "type mismatch", you've already emitted the LHS WAT into c.out. The transaction mechanism (startTransaction/writeTransaction) is a workaround for exactly this — it shouldn't be needed.
One error per compile Your Compile returns the first error. A real compiler reports all type errors so the user can fix them in batches.
No type information across the AST typeOf at line 591 returns "unknown" for anything it doesn't handle, and FunctionCall hardcodes "f64" (line 633) with a TODO. There's no place that authoritatively knows what type each expression has, so checks degrade to "give up".
Codegen can't be retargeted If you ever wanted to emit, say, native ARM or LLVM IR instead of WAT, you'd have to re-port all the type checks too. With a separate pass, codegen for a new target reads a pre-checked AST and emits — nothing else.

2. What a "pass" actually is

A compiler pass is a function that takes the AST and either returns a transformed AST, a list of errors, or both. There's no magic — it's the visitor pattern from Lesson 4 with a different return type.

Source │ ▼ [Parse] → AST │ ▼ [Type check] → AST (or typed AST, or error list) ← we're adding THIS pass │ ▼ [Codegen] → WAT

Each pass is conceptually independent. Each can be unit-tested in isolation — you can give the type checker a hand-crafted AST and assert it produces the expected error, without ever running the parser or the codegen.

See Bob Nystrom's Resolving and Binding chapter — his resolver pass is structurally identical to a type checker (walks AST, maintains scopes, doesn't emit anything, reports errors).

3. The current scattered state — an inventory

Before refactoring, see the surface area. Here's everything in your compiler that does type work:

Notice the pattern: every one of these has to recompute type information that should already be known. The pass computes it once, attaches it to the AST, and codegen reads.

4. The design

Create a new package internal/script/typecheck with a single entry point:

package typecheck

func Check(program *script.Program) error {
    c := &Checker{
        structs: make(map[string]*StructInfo),
        funcs:   make(map[string]*FuncInfo),
        scope:   newScope(),
    }
    c.collectSignatures(program)
    return c.checkProgram(program)
}

The shape of Checker mirrors Compiler, but holds type information rather than emission state:

type Checker struct {
    structs map[string]*StructInfo  // struct name → fields + methods
    funcs   map[string]*FuncInfo    // function name → param types + return type
    scope   *Scope                  // current variable type bindings (stack of maps)
    errors  []error                 // accumulate, don't bail
}

type Scope struct {
    parent *Scope
    vars   map[string]Type
}

And a small Type representation — enough to express what plex has:

type Type struct {
    Kind     TypeKind  // Int, Float, String, Array, Struct, Void, Unknown
    Element  *Type     // for Array: the element type
    Struct   string    // for Struct: the struct name
}

Why not use Go's string like the current compiler does?

Strings are fine for "i32" / "f64". They fall apart for compound types: an "array of Points" can't be expressed as a single string without parsing it back out. A small struct type composes naturally — Type{Kind: Array, Element: &Type{Kind: Struct, Struct: "Point"}}. This is the same reason real compilers have a real Type data structure (see Rust's Ty).

Two-pass structure

The checker itself runs in two phases:

  1. Collect signatures. Walk the program; for every StructStatement, register fields. For every FunctionDeclaration, register param/return types. For every StructImplStatement, register methods. No checking yet — just enough to make forward references work.
  2. Check expressions and statements. Walk the program a second time. For each expression, compute its type. For each statement, verify the types of its parts. Accumulate errors in c.errors.

This is the same pattern that lets your impl block call methods declared later in the same block (Lesson 11, Task C). Forward references are cheap when you have a separate pass.

5. Annotating the AST

This is the part that pays the largest dividend. You have two options:

Option 1: Side table Checker keeps map[script.AstNode]Type Codegen calls checker.TypeOf(node) for every read Option 2: Embedded annotation Add a Type field to every expression AST node Checker sets it; codegen reads it directly

Option 1 is non-invasive (no AST changes), but slow (map lookup per node) and awkward (codegen needs the checker around). Option 2 is the standard approach. Add to your AST:

// In internal/script/ast.go (or wherever expression types live)

type Expression interface {
    AstNode
    GetType() *Type      // returns nil if not yet checked
    SetType(*Type)
}

// Then on each concrete expression node:
type NumberLiteral struct {
    Value string
    Type_ *Type   // set by the checker
}
func (n *NumberLiteral) GetType() *Type { return n.Type_ }
func (n *NumberLiteral) SetType(t *Type) { n.Type_ = t }

This is called a "decorated AST" or "typed AST" — the AST carries the typing decisions forward. See the Crafting Interpreters AST chapter for the underlying visitor design.

The dependency direction

Once codegen reads types off the AST, codegen requires that the checker has already run. Enforce this at the entry point:

func CompileProgram(p *script.Program) (string, error) {
    if err := typecheck.Check(p); err != nil {
        return "", err
    }
    // ... compile with confidence ...
}

This is how every production compiler works. The codegen never asks what the type is — it has already been computed.

6. The minimal first cut

Don't try to move everything at once. Pick the smallest scattered check and move it.

Task A — Extract BinaryExpression type checking

The cleanest place to start. Today, compiler.go:89–108 does:

  • Call typeOf(Left)
  • Call typeOf(Right)
  • Pick a prefix (with the "unknown" fallback hack)
  • Error if mismatch
  • Emit the operator

Refactor it to: just emit the operator, using the type already stamped on the AST node.

Steps:

  1. Create internal/script/typecheck/checker.go with a stub Check function and a minimal Checker struct.
  2. Add Type_ fields and GetType/SetType methods to NumberLiteral, Identifier, and BinaryExpression.
  3. Implement checkExpression(expr) *Type in the checker for those three nodes. For BinaryExpression: check left, check right, verify they match, set the node's type to the operand type. Return the type.
  4. In CompileProgram, call typecheck.Check(p) before c.prepass(p) and c.Compile(p).
  5. In BinaryExpression codegen, replace the typeOf calls with n.GetType().WasmName() (a method on your Type that returns "i32"/"i64"/"f32"/"f64").
  6. Delete the old typeOf's BinaryExpression case — it's now dead code.

Run impl-struct.plex end-to-end. Output should be byte-identical to before. That's the validation: the refactor preserved behaviour while relocating the work.

7. Building out the checker

Task B — Extract typeofStruct and generalise it

The current typeofStruct (line 568) only handles *Identifier. That's why a.b.c would break — you can't ask "what's the struct type of a.b?" today.

In the checker, checkExpression(*MemberAccess) returns the field's type, and along the way records that the receiver is a struct. Field access of a struct that has another struct field becomes a recursive call: check the receiver, get its (struct) type, look up the field in that struct, return the field's type.

Implement MemberAccess in the checker. Then update codegen to read offsets off the typed AST instead of recomputing.

Task C — Error accumulation

Make the checker collect errors instead of bailing on the first one:

func (c *Checker) error(node script.AstNode, format string, args ...any) {
    c.errors = append(c.errors, fmt.Errorf(format, args...))
}

At the end of Check, if len(c.errors) > 0, join them and return the combined error. Then write a test that has three type errors in one program and assert all three are reported.

This is one of the biggest UX wins of a separate pass — a user-facing compiler that reports all errors at once feels dramatically better.

Task D (deep) — Function calls and return types

Move function-call checking into the pass:

  1. Verify the function exists.
  2. Verify argument count matches parameter count.
  3. Verify each argument's type matches the corresponding parameter's type.
  4. Set the call's type to the function's declared return type.

This is what typeOf(*FunctionCall) on line 632 should have been doing all along (it currently hardcodes f64). Once this works, you can check that the return value of a function is used in a context that accepts it — a real type check, finally.

Also: walk the function body and ensure every ReturnStatement's value matches the declared return type. This is the kind of cross-AST check that's painful in mixed codegen and trivial in a dedicated pass.

8. What this enables next

Once you have a real type-check pass, several future lessons become straightforward:

  • Generics / parametric polymorphism. The checker has somewhere to do substitution. Without a pass, there's nowhere to even start.
  • Type inference (Hindley-Milner style). Inference is a constraint-solving problem the checker accumulates and solves. See HM for the classical algorithm, or PAPL's chapter for a gentler intro.
  • Exhaustiveness checking. If you add match expressions later, the checker verifies every variant is handled. Codegen never sees a non-exhaustive match.
  • Borrow checking / linear types. The Rust-style "you can't use this variable after it's been moved" check is a separate analysis pass. Builds on type checking.

Q&A prompts

  • Your interpreter (Lesson 4) and your type checker have the same shape — both walk the AST, both maintain a scoped environment, both recurse on subexpressions. What's the category-theoretic name for this shape? (Hint: catamorphism, fold.) Could you write a generic visitor that both your interpreter and your checker use?
  • In Rust, the type checker runs after name resolution but before the borrow checker — three separate passes. Why couldn't they be one? What would go wrong if borrow checking ran before type checking?
  • Your checker has a forward-reference problem: a function body can call another function declared later in the same file. You solved it with a two-phase checker (collect signatures, then check bodies). What if you had mutually recursive types — struct A { b: B } and struct B { a: A }? Does your design handle that? What's the simplest fix?
  • The current compiler propagates "unknown" as a type, and uses an "unknown picks the other side" rule in BinaryExpression. Why is this dangerous? Construct a small plex program that should be a type error but currently compiles cleanly because of this rule.
