Lesson 49 – arr.append in the Binary Backend

Previous: Lesson 48 – Ternary Expressions and Type Casts

The binary backend handles arr.len() but not arr.append(elem). append mutates the array in place — it writes a new element at the next slot and increments the stored length. Two things make it interesting to implement:

  1. It needs a synthetic temporary local to hold the array pointer (not declared in source)
  2. It requires careful address arithmetic on linear memory

Array Memory Layout — Quick Recap

From Lesson 40, an int[] of length 3 at address ptr looks like this:

ptr+0 [ len: i32 = 3 ] ← 4 bytes, length field ptr+4 [ elem[0]: 8 bytes ] ptr+12 [ elem[1]: 8 bytes ] ptr+20 [ elem[2]: 8 bytes ] ptr+28 ← write_addr for append (ptr + 4 + len*8)

To append a fourth element: write it at ptr + 4 + len*elemSize, then increment the length stored at ptr.

Element sizes

Plex typeElement size (bytes)Store opcode
int, i64, f64, float8i64.store / f64.store
i32, bool, string, array, struct4i32.store

The Synthetic Local Problem

The address arithmetic uses the array pointer twice (once to compute the write address, once to update the length). Rather than walk the callee expression twice — which would double all side effects — the encoder saves the pointer to a synthetic local with local.tee.

The challenge: WASM binary format requires the locals vector to appear before the function body bytes. But we only know we need a synthetic local when we encounter the append call during the body walk.

section.go:encodeCodeEntry already solves this with a deliberate two-phase approach: 

// Walk first so synthetic locals land in enc.localTypes BEFORE
// we serialise the locals vec.
if err := enc.walk(f.Body); err != nil { return nil, err }

body = AppendULEB128(body, uint32(len(enc.localTypes)))
for _, vt := range enc.localTypes {
    ...
}
body = append(body, enc.buf...)  // body comes AFTER locals vec

So: walk happens first, then the locals vector is serialised. Any addSyntheticLocal calls during the walk accumulate into enc.localTypes just in time. The addSyntheticLocal helper already exists in body.go: 

func (b *bodyEncoder) addSyntheticLocal(vt byte) uint32 {
    idx := uint32(len(b.locals))
    b.locals[fmt.Sprintf("__synth_%d", idx)] = idx
    b.localTypes = append(b.localTypes, vt)
    return idx
}
Key insight: The walk-before-encode trick is the enabling pattern for all inline code generation that needs temporaries. You will use addSyntheticLocal again for arr.remove (next lesson), and you could use it for any future built-in that needs scratch space.

The Full Append Sequence

Here is the full stack trace for arr.append(elem) where arr is int[] (elemSize = 8):

phase 1: save pointer, compute write address walk(callee.Object) → [ptr] local.tee $arr → [ptr] saves to local, keeps on stack local.get $arr → [ptr, ptr] i32.load align=2 offset=0 → [ptr, len] i32.const <elemSize> → [ptr, len, 8] i32.mul → [ptr, len*8] i32.const 4 → [ptr, len*8, 4] i32.add → [ptr, offset] offset = 4 + len*8 local.get $arr → [ptr, offset, ptr] i32.add → [ptr, write_addr] phase 2: store the element walk(arg[0]) → [ptr, write_addr, elem] i64.store align=3 offset=0 → [ptr] write_addr and elem consumed phase 3: increment length local.get $arr → [ptr, ptr] local.get $arr → [ptr, ptr, ptr] i32.load align=2 offset=0 → [ptr, ptr, len] i32.const 1 → [ptr, ptr, len, 1] i32.add → [ptr, ptr, new_len] i32.store align=2 offset=0 → [ptr] ptr is the address, new_len the value
Why is there a stray [ptr] at the end? The original local.tee pushed ptr on the stack but the store sequences consumed additional copies via local.get. The initial ptr sits underneath everything and is never explicitly popped. Since append has type void, the block walker doesn't emit OpDrop. This is valid WASM: at a return or function-end, the validator checks only the topmost return-count values — values below are unreachable from that point and are not a validation error.

Implementation Task

Task — one helper, one case

1. Add an elemSizeOf helper in body.go (or inline it — your call):

func elemSizeOf(t *script.Type) uint32 {
    switch t.Kind {
    case script.TypeKind_I64, script.TypeKind_Int,
         script.TypeKind_F64, script.TypeKind_Float:
        return 8
    default:
        return 4  // i32, bool, pointers (struct/array/string)
    }
}

2. In the array method switch inside FunctionCall → MemberAccess → TypeKind_Array, replace the default: return error with an "append" case:

case "append":
    arr := b.addSyntheticLocal(ValI32)

    // save ptr, keep on stack
    if err := b.walk(callee.Object); err != nil { return err }
    b.buf = append(b.buf, OpLocalTee)
    b.buf = AppendULEB128(b.buf, arr)

    // compute write_addr = ptr + 4 + len*elemSize
    eType := objType.Element
    eSize := elemSizeOf(eType)
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, arr)
    b.buf = append(b.buf, OpI32Load)
    b.buf = AppendULEB128(b.buf, 2)
    b.buf = AppendULEB128(b.buf, 0)
    b.buf = append(b.buf, OpI32Const)
    b.buf = AppendULEB128(b.buf, eSize)
    b.buf = append(b.buf, OpI32Mul)
    b.buf = append(b.buf, OpI32Const, 4)
    b.buf = append(b.buf, OpI32Add)
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, arr)
    b.buf = append(b.buf, OpI32Add)

    // store the new element
    if err := b.walk(n.Args[0]); err != nil { return err }
    stOp, stAlign := storeOpcode(eType.Kind)
    b.buf = append(b.buf, stOp)
    b.buf = AppendULEB128(b.buf, uint32(stAlign))
    b.buf = AppendULEB128(b.buf, 0)

    // increment length at ptr
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, arr)
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, arr)
    b.buf = append(b.buf, OpI32Load)
    b.buf = AppendULEB128(b.buf, 2)
    b.buf = AppendULEB128(b.buf, 0)
    b.buf = append(b.buf, OpI32Const, 1)
    b.buf = append(b.buf, OpI32Add)
    b.buf = append(b.buf, OpI32Store)
    b.buf = AppendULEB128(b.buf, 2)
    b.buf = AppendULEB128(b.buf, 0)
    return nil

Watch the order: the walk(callee.Object) call in the append case comes after addSyntheticLocal, not before. The synthetic local must be allocated first so its index is stable when later local.tee/local.get opcodes reference it.

One more thing: the existing array method dispatch pre-walks all args before the method switch. The append case walks n.Args[0] itself at the right point in the instruction stream. Delete or skip the pre-walk for the "append" case to avoid walking the argument twice. The cleanest approach: move the arg pre-walk inside the "len" case (the only one that currently needs it evaluated before the object). Or restructure so append is a separate branch before the default arg pre-walk.

func TestEndToEnd_ArrayAppend(t *testing.T) {
    src := `
        fn grow(): int {
            let arr: int[] = [1, 2, 3];
            arr.append(4);
            return arr.len();
        }
        fn grow_read(): int {
            let arr: int[] = [10, 20];
            arr.append(30);
            return arr[2];
        }
        fn grow_twice(): int {
            let arr: int[] = [1];
            arr.append(2);
            arr.append(3);
            return arr[0] + arr[1] + arr[2]; // 1 + 2 + 3 = 6
        }
    `
    runOne(t, src, "grow",       nil, 4)
    runOne(t, src, "grow_read",  nil, 30)
    runOne(t, src, "grow_twice", nil, 6)
}

grow_twice verifies that appending multiple times works correctly — each append must see the current length, not a stale value.

Why Pre-walking Args Breaks Append

The current array dispatch code pre-walks all n.Args before entering the method switch. This made sense for "len" (which ignores args) but breaks "append": the argument must be on the stack after the write address, not before.

Stepping back: this is a general tension in compiler dispatch code. When you handle multiple operations through a single switch, the argument evaluation order matters and varies per case. The clean fix is not to pre-evaluate args for the whole switch — evaluate them inside each case, exactly when needed.
