(b) Inverted implName check in helpers.go

The condition that prepends the implicit self param to methods is reversed:

if implName == "" {                // ← wrong: this fires for top-level fns
    params = append(params, ValI32)
}

It should be the opposite — top-level functions get no self; methods do:

if implName != "" {                // ← correct
    params = append(params, ValI32)
}

Symmetrically in collectSignatures: when iterating over methods inside *StructImplStatement, you're passing m.Name as the implName. It should be n.Name — the struct's name. Otherwise the symbol comes out as __methodName__methodName, and (once the cleanup in (a) is applied) the implicit-self check still won't work because the per-method name is non-empty but not the struct.

        ...

Re-run wasm-objdump -x after these fixes; a struct with one method should show one type with two params (the first being i32 self), and any top-level function should now have its declared params only.

3. The Function section

The Function section (id 3) is comically simple: for each function, say which Type-section entry holds its signature. Since lesson 25 emits one type per function in declaration order with no dedup, function i's typeidx is just i.

[id=03] [size] vec(typeidx)

For a program with three functions, the Function section body is literally 03 00 01 02 — count of 3, followed by indices 0, 1, 2.

Task 1 — add encodeFunctionSection to section.go 
func encodeFunctionSection(sigs []funcSig) []byte {
    var body []byte
    body = AppendULEB128(body, uint32(len(sigs)))
    for i := range sigs {
        body = AppendULEB128(body, uint32(i))   // typeidx == funcidx (no dedup)
    }
    return section(SectionFunction, body)
}

4. The Code section anatomy

The Code section (id 10) holds the actual bytecode. It's a vec(code) where each code entry is:

[size : uleb128]                ; total bytes of locals + body
[locals : vec((count, valtype))] ; RLE-grouped local declarations
[body : instr*]                  ; opcodes
[0x0B : end]                     ; terminator — part of body in the size count

Three things to internalise here:

  1. The size is doubly nested. Each code entry has its own size, and the whole Code section has its own size in the wrapper. You'll build the inner one by encoding the entry's bytes to a temporary buffer and prefixing len(buf).
  2. Locals are run-length encoded. If you have three consecutive i64 locals followed by two i32 locals, the encoding is two groups: (3, 0x7E), (2, 0x7F) — not five separate entries. The decoder reads vec_count groups; the total number of locals is the sum of the counts. This matters for naming/indexing: locals are indexed flatly by their position in the (params ++ locals) sequence, even though they're grouped in the encoding.
  3. Function params are NOT in the locals vec. Params live in the Type section's functype. The Code section's locals only contains additional locals declared inside the function body. But for local.get/set, the indices count params first, then locals — so a function with 2 params and one i32 local would refer to the local as index 2.
Every body ends with 0x0B The end opcode (0x0B) terminates every function body. It's also the terminator for block, loop, and if instructions (you'll meet those in lesson 30). It's how the decoder knows where structured constructs close — no length prefix on individual instructions.

5. Your first six opcodes

This lesson keeps the opcode set minimal — just enough to compile the simplest function imaginable, like fn forty_two(): i64 { return 42; }. Lesson 28 adds the rest (binary operators, locals, function calls).

ByteMnemonicDescription & immediates
0x0BendTerminator — closes a function body, block, loop, or if. No immediate.
0x0FreturnReturns the top of the stack as the function result. No immediate.
0x20local.getPush the value of local idx. Immediate: 1× uleb128 local index.
0x41i32.constPush a constant. Immediate: 1× signed LEB128 i32.
0x42i64.constPush a constant. Immediate: 1× signed LEB128 i64.
0x44f64.constPush a constant. Immediate: 8 raw little-endian IEEE-754 bytes (not LEB128).
i*.const uses signed LEB128 — f*.const does not Integer constants in WASM are signed-LEB128-encoded so that negative literals don't blow up to 5 bytes. Float constants are raw little-endian IEEE-754 bytes (4 for f32, 8 for f64). Mixing these up is the most common new-emitter bug — every spec example will look "the same" but the encoding rule differs.
Why is there both return and end? end closes a structured-control block. return early-exits the function. A function body whose final expression already has the right type can omit return — the stack value is taken as the result when end is reached. Plex always emits an explicit return in the WAT backend, and we'll do the same in the binary backend for consistency.

6. The expression walker

The skeleton mirrors what the WAT backend's Compile switch does in compiler.go, but instead of c.emit("i64.const", n.Value) we append bytes. The recursion structure is identical.

Task 2 — create internal/script/compiler/binary_wasm/opcodes.go 
package binary_wasm

const (
    OpEnd      byte = 0x0B
    OpReturn   byte = 0x0F
    OpLocalGet byte = 0x20
    OpI32Const byte = 0x41
    OpI64Const byte = 0x42
    OpF64Const byte = 0x44
)
Task 3 — create the body emitter in binary_wasm/body.go 
package binary_wasm

import (
    "encoding/binary"
    "fmt"
    "math"
    "strconv"

    "github.com/VisualSource/plex/internal/script"
)

type bodyEncoder struct {
    buf []byte
}

func (b *bodyEncoder) walk(node script.AstNode) error {
    switch n := node.(type) {

    case *script.Block:
        for _, s := range n.Stmts {
            if err := b.walk(s); err != nil {
                return err
            }
        }

    case *script.NumberLiteral:
        t := n.GetType()
        if t == nil {
            return fmt.Errorf("no type on number %s", n.Value)
        }
        switch t.Kind {
        case script.TypeKind_I32:
            v, _ := strconv.ParseInt(n.Value, 10, 32)
            b.buf = append(b.buf, OpI32Const)
            b.buf = AppendSLEB128(b.buf, v)
        case script.TypeKind_Int, script.TypeKind_I64:
            v, _ := strconv.ParseInt(n.Value, 10, 64)
            b.buf = append(b.buf, OpI64Const)
            b.buf = AppendSLEB128(b.buf, v)
        case script.TypeKind_Float, script.TypeKind_F64:
            v, _ := strconv.ParseFloat(n.Value, 64)
            b.buf = append(b.buf, OpF64Const)
            var raw [8]byte
            binary.LittleEndian.PutUint64(raw[:], math.Float64bits(v))
            b.buf = append(b.buf, raw[:]...)
        default:
            return fmt.Errorf("unsupported number type %s", t.Kind)
        }

    case *script.ReturnStatement:
        if n.Value != nil {
            if err := b.walk(n.Value); err != nil {
                return err
            }
        }
        b.buf = append(b.buf, OpReturn)

    default:
        return fmt.Errorf("binary_wasm: unhandled AST node %T (extend the walker in body.go)", n)
    }
    return nil
}

The default error is deliberately noisy — it tells you exactly which node type to handle next when you encounter a richer plex file. Each new node added in later lessons fits the same pattern: recurse on children, then append the corresponding opcode bytes.

Task 4 — encode one code entry, then the whole Code section, in binary_wasm/section.go 
func encodeCodeEntry(f *script.FunctionDeclaration) ([]byte, error) {
    var body []byte

    // Locals — empty for now. Lesson 28 fills this from f.Body's
    // VariableDeclaration nodes, RLE-grouped by valtype.
    body = AppendULEB128(body, 0)

    // The instructions themselves.
    enc := &bodyEncoder{}
    if err := enc.walk(f.Body); err != nil {
        return nil, err
    }
    body = append(body, enc.buf...)

    // Every body terminates with `end`.
    body = append(body, OpEnd)

    // The entry is its own length-prefixed sub-record:
    var entry []byte
    entry = AppendULEB128(entry, uint32(len(body)))
    entry = append(entry, body...)
    return entry, nil
}

func encodeCodeSection(funcs []*script.FunctionDeclaration) ([]byte, error) {
    var body []byte
    body = AppendULEB128(body, uint32(len(funcs)))
    for _, f := range funcs {
        entry, err := encodeCodeEntry(f)
        if err != nil {
            return nil, err
        }
        body = append(body, entry...)
    }
    return section(SectionCode, body), nil
}

    }
    out = append(out, code...)
}

Section order matters: Type, then Function, then Code. The spec lays this out in §5.5. The runtime relies on this ordering to know what Function entries refer to.

7. Verification

Write the smallest possible plex source file:

// dist/forty_two.plex
fn forty_two(): i64 {
    return 42;
}

Build and inspect:

go run ./cmd/plexc -file ./forty_two.plex -target wasm-bin
wasm-objdump -x ./dist/forty_two.wasm   # show sections
wasm-objdump -d ./dist/forty_two.wasm   # disassemble bodies

Expected (with -d):

Code Disassembly:

000020 <forty_two>:
 000022: 42 2a                      | i64.const 42
 000024: 0f                         | return
 000025: 0b                         | end

Notice the byte sequence: 42 is OpI64Const, 2a is the SLEB128 encoding of 42, 0f is OpReturn, 0b is OpEnd. Now diff against the WAT backend's output:

# Generate WAT and binary side by side
go run ./cmd/plexc -file ./forty_two.plex -target wasm-wat
wat2wasm ./dist/forty_two.wat -o ./dist/forty_two_via_wat.wasm
diff <(xxd ./dist/forty_two.wasm) <(xxd ./dist/forty_two_via_wat.wasm)

The diff may show a few bytes — the WAT backend may include a name-debug Custom section that we're not emitting. That's expected. The Type, Function, and Code sections should be byte-identical.

The file is still not runnable wasm-objdump can disassemble it, but loading it in wazero will fail: there's no Export section yet, so even though forty_two exists inside the module, the host has no way to call it. That's the entirety of lesson 27. One small section, then the first real "hello world" of your binary backend.
