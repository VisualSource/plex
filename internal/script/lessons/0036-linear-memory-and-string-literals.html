Lesson 36 – Linear Memory and String Literals

Goal: emit a memory section and a data section, lay out string literals at known offsets, and make fn greet(): string { return "hello"; } produce an exported memory that the host can read.

Files you'll touch: opcodes.go · section.go · helpers.go · body.go · module.go · end_to_end_test.go

What WASM Calls "Memory"

WebAssembly modules can declare at most one linear memory: a contiguous, byte-addressable array of bytes, sized in 64 KiB pages. Code reads and writes it with i32.load and i32.store (and their typed cousins), using an i32 address. There is no garbage collector; the address space is the program's to manage.

SectionIDPurpose
Memory0x05Declares the memory's size limits (min/max in pages).
Data0x0BPreloads bytes at fixed offsets when the module is instantiated.
Export0x07You already build this — gains a new entry of kind 0x02 (memory).
Why preload bytes at instantiation? The data section is WASM's equivalent of .rodata in a binary. String literals don't appear at runtime out of thin air — the host writes them into linear memory once, when the module is instantiated, and the rest of the program just reads them. This makes string literals zero-cost at runtime (no allocator, no copy).

String Layout

Match the WAT compiler's layout (compiler.go:1086-1099): each string is laid out as a 4-byte little-endian length followed by the raw UTF-8 bytes. A "string" in plex is therefore an i32 pointer to the length-prefix byte. Reading the string is reading 4 bytes for the length, then that many bytes after.

Memory layout of "hello" placed at offset 0:

05@0
00@1
00@2
00@3
'h'@4
'e'@5
'l'@6
'l'@7
'o'@8

The "value" of the string literal "hello" at the WASM level is the i32 0 — the address of the length-prefix byte. A second literal "world" would sit at offset 9 (right after 'o') and its value would be the i32 9.

Length prefix, not null terminator. Plex strings carry their length explicitly. This is the same choice as Pascal strings and the bedrock of Go strings — O(1) length, safe with embedded zero bytes. C-style null-terminated strings would also work but require a scan to compute length.

Section Encodings

Memory section (id 5)

The body is a vector of memories. We always emit exactly one memory with a minimum of one page and no maximum. The flags byte selects the limits form: 0x00 means "min only", 0x01 means "min and max".

; memory section, 1 memory, min=1 page, no max 05 ; section id 03 ; section body length (3 bytes) 01 ; one memory entry 00 ; limits flag: min only 01 ; min = 1 page

Data section (id 11)

A vector of data segments. Each active segment has:

  1. A memory index (ULEB128) — always 0 since there's only one memory.
  2. An offset expression — a constant i32.const N followed by end.
  3. A byte vector — ULEB128 length followed by the raw bytes.
; data section with one segment for "hello" at offset 0 0B ; section id .. ; section body length 01 ; one data segment 00 ; memory index 0 41 00 0B ; offset expr: i32.const 0; end 09 ; vec length: 9 bytes (4 length + 5 chars) 05 00 00 00 ; little-endian length prefix = 5 68 65 6C 6C 6F ; "hello"
The offset expression is a real WASM expression. Not a raw integer — a constant initialiser instruction stream terminated by end. This is the same shape as globals and element segments use. For now you only ever emit OpI32Const, <leb>, OpEnd — three bytes plus the LEB.

Export entry for memory

To let the host read memory, add an export of kind 0x02 (memory) referring to memory index 0:

06 ; name length: 6 "memory" ; name bytes 02 ; kind: memory 00 ; memory index 0

Step 2 — Collect strings

Add to helpers.go a pass that walks the AST and assigns each unique string literal a stable offset. Keep it simple — a slice plus a name→offset map. Strings are pooled (de-duplicated) so identical literals share storage:

type stringEntry struct {
    value  string
    offset uint32
}

type stringTable struct {
    entries []stringEntry
    byValue map[string]uint32
    next    uint32
}

func (st *stringTable) add(v string) uint32 {
    if off, ok := st.byValue[v]; ok {
        return off
    }
    off := st.next
    st.entries = append(st.entries, stringEntry{v, off})
    if st.byValue == nil {
        st.byValue = map[string]uint32{}
    }
    st.byValue[v] = off
    st.next += uint32(4 + len(v))
    return off
}

func collectStrings(p *script.Program) *stringTable {
    st := &stringTable{}
    var walk func(script.AstNode)
    walk = func(n script.AstNode) {
        switch v := n.(type) {
        case *script.StringLiteral:
            st.add(v.Value)
        case *script.Program:
            for _, s := range v.Stmts { walk(s) }
        case *script.FunctionDeclaration:
            walk(v.Body)
        case *script.Block:
            for _, s := range v.Stmts { walk(s) }
        case *script.ReturnStatement:
            if v.Value != nil { walk(v.Value) }
        case *script.VariableDeclaration:
            if v.Init != nil { walk(v.Init) }
        case *script.BinaryExpression:
            walk(v.Left); walk(v.Right)
        case *script.IfStatement:
            walk(v.Condition); walk(v.Body)
            if v.Else != nil { walk(v.Else) }
        case *script.WhileStatement:
            walk(v.Condition); walk(v.Body)
        case *script.FunctionCall:
            for _, a := range v.Args { walk(a) }
        }
    }
    walk(p)
    return st
}
Walking is conservative. Don't worry about hitting every AST node — anything you miss simply won't pool its strings, and at worst the test won't find one. The cases above cover everything the current binary backend already compiles.

Step 3 — Encode the memory section

In section.go:

func encodeMemorySection() []byte {
    var body []byte
    body = AppendULEB128(body, 1)   // one memory
    body = append(body, 0x00)        // limits flag: min only
    body = AppendULEB128(body, 1)   // min = 1 page
    return section(SectionMemory, body)
}

Step 4 — Encode the data section

func encodeDataSection(st *stringTable) []byte {
    var body []byte
    body = AppendULEB128(body, uint32(len(st.entries)))
    for _, e := range st.entries {
        body = AppendULEB128(body, 0)              // memory index 0
        body = append(body, OpI32Const)            // offset expr begin
        body = AppendSLEB128(body, int64(e.offset))
        body = append(body, OpEnd)                  // offset expr end

        // bytes: 4-byte LE length prefix + raw bytes
        n := len(e.value)
        bytes := []byte{byte(n), byte(n >> 8), byte(n >> 16), byte(n >> 24)}
        bytes = append(bytes, e.value...)

        body = AppendULEB128(body, uint32(len(bytes)))
        body = append(body, bytes...)
    }
    return section(SectionData, body)
}

Step 6 — Handle *script.StringLiteral in walk

The encoder needs access to the string table at the time it walks function bodies. The simplest threading: store it on the bodyEncoder and pass through newBodyEncoder, parallel to how funcIndices is plumbed.

case *script.StringLiteral:
    off, ok := b.strings.byValue[n.Value]
    if !ok {
        return fmt.Errorf("string %q not in table", n.Value)
    }
    b.buf = append(b.buf, OpI32Const)
    b.buf = AppendSLEB128(b.buf, int64(off))
    return nil

Step 7 — Wire it all into CompileProgram

In module.go:

strings := collectStrings(node)

if len(strings.entries) > 0 {
    exports = append(exports, exportEntry{name: "memory", kind: ExportMemory, idx: 0})
}

// ... existing emission of type, function, export, code sections ...

if len(strings.entries) > 0 {
    out = append(out, encodeMemorySection()...)
    out = append(out, encodeDataSection(strings)...)
}
Section order matters. The WASM binary format mandates a fixed order: type, import, function, table, memory, global, export, start, element, code, data. The validator rejects out-of-order sections. Memory (5) must precede export (7); data (11) goes last. Pass strings into encodeCodeSection so function bodies can resolve string literals — and emit the memory section before the export section.

The cleanest sequence:

type (1) function (3) memory (5) ; new export (7) ; now includes memory export code (10) data (11) ; new

Step 8 — The test

The existing runOne helper compares a single uint64 return. For strings we want to inspect memory. Add a new test that calls the function, reads the returned i32 as a pointer, then reads the prefixed bytes from memory:

func TestEndToEnd_StringLiteral(t *testing.T) {
    src := `
        fn greet(): string {
            return "hello";
        }
    `
    ast, err := script.Parse(strings.NewReader(src))
    if err != nil { t.Fatal(err) }
    wasm, err := binary_wasm.CompileProgram(ast)
    if err != nil { t.Fatal(err) }

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)
    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    got, err := mod.ExportedFunction("greet").Call(ctx)
    if err != nil { t.Fatalf("call: %v", err) }

    ptr := uint32(got[0])
    mem := mod.Memory()

    lenBytes, _ := mem.Read(ptr, 4)
    n := uint32(lenBytes[0]) | uint32(lenBytes[1])<<8 | uint32(lenBytes[2])<<16 | uint32(lenBytes[3])<<24
    if n != 5 { t.Fatalf("length = %d, want 5", n) }

    data, _ := mem.Read(ptr+4, n)
    if string(data) != "hello" {
        t.Fatalf("data = %q, want %q", string(data), "hello")
    }
}
go test ./internal/script/compiler/binary/... -run TestEndToEnd_StringLiteral -v

The full suite should still pass — runs that don't use strings won't emit memory or data sections, so nothing changes for them.

What You Just Built

Three new concepts landed at once:

  • Compile-time data placement. The compiler decides where each string lives before any code runs. Offsets are baked into i32.const instructions and into the data section's offset expressions.
  • Module-level state shared with bodies. The string table is built once and threaded into every bodyEncoder — the same threading pattern as funcIndices from lesson 32.
  • The host as an inspection point. Until now, every test could see what the WASM did through its return value alone. Now the test reaches into linear memory — the same channel through which a real browser or runtime would read a result.

What's Next

  • String length and indexing. Now that strings live in memory, s.len() compiles to i32.load at the pointer; s[i] to i32.const 4; i32.add; i32.const i; i32.add; i32.load8_u. Tiny code, big unlock — and you already added OpI32Load.
  • Heap and arrays. Strings are static (data section); arrays are dynamic and need a bump allocator and a heap-pointer global. Lesson 9 covered this for the WAT backend.
  • Struct layout. Once the heap is live, structs are just typed offsets from a base pointer.
