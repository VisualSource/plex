2. The section wrapper

Every section, regardless of id, has the same outer layout:

[id : 1 byte] [size : uleb128] [body : size bytes]

The size field counts only the bytes of the body, not the id or size itself. This is what makes the format streamable: an engine can skip a section it doesn't care about (custom sections, especially) by reading the id, reading the length, and seeking past it. No nested parsing required to know where the next section starts.

One helper, every section Every future lesson appends one more section. Write the wrapper once, write its body in each lesson. The wrapper itself never changes.
Task 1 — section helper in binary/section.go 
package binary

const (
    SectionType     = 1
    SectionImport   = 2
    SectionFunction = 3
    SectionMemory   = 5
    SectionGlobal   = 6
    SectionExport   = 7
    SectionCode     = 10
    SectionData     = 11
)

// section returns [id, uleb128(len(body)), body...]
func section(id byte, body []byte) []byte {
    out := []byte{id}
    out = AppendULEB128(out, uint32(len(body)))
    return append(out, body...)
}

3. The vec(T) primitive

The spec uses one notation everywhere: vec(T). It means a uleb128 count followed by that many Ts. There's no separator, no terminator — the count tells the decoder when to stop. The Type section, for example, is a vec(functype); each functype contains a vec(valtype) for parameters and another vec(valtype) for results.

It's so universal that thinking in terms of vec rather than "a length and then some bytes" makes the spec much easier to read. See §5.1.3 Vectors.

4. Encoding value types and function types

A value type (valtype) is a single byte:

ByteTypeplex source
0x7Fi32i32, bool, string, array, struct (pointers)
0x7Ei64i64, int
0x7Df32f32
0x7Cf64f64, float

The plex compiler already does this mapping in helpers.go — getWasmType returns the WAT-string version ("i64"); you need the byte version. The mapping is identical otherwise.

A function type (functype) is the tag byte 0x60 followed by two vecs:

0x60 vec(valtype)params vec(valtype)results

Worked example — the signature of a plex function fn add(a: i64, b: i64): i64:

60
functype tag
02
uleb128: 2 params
7E 7E
i64, i64
01
uleb128: 1 result
7E
i64

Total: 7 bytes for a binary-form signature. (Currently WebAssembly MVP allows at most one result; multi-value, enabled in modern engines, lifts this — but the encoding shape is unchanged: just a longer vec.)

Void return → empty vec, not absent vec A plex function with no ReturnType has an empty result vec — one byte of 0x00 (the count), zero valtype bytes after it. Don't omit the vec entirely. The decoder counts bytes.

5. Walking the AST for signatures

You need every function the program declares. In plex's AST that means:

  • Top-level *script.FunctionDeclaration nodes in Program.Stmts
  • Methods inside *script.StructImplStatement.Methods — each is also a *FunctionDeclaration, but a method has an implicit self: i32 prepended to its params (see how the WAT compiler does this in compiler.go:264-268)
Task 2 — value-type helper in binary/types.go 
package binary

import "github.com/VisualSource/plex/internal/script"

const (
    ValI32 byte = 0x7F
    ValI64 byte = 0x7E
    ValF32 byte = 0x7D
    ValF64 byte = 0x7C
)

func valType(t *script.Type) byte {
    switch t.Kind {
    case script.TypeKind_Int, script.TypeKind_I64:
        return ValI64
    case script.TypeKind_Float, script.TypeKind_F64:
        return ValF64
    case script.TypeKind_F32:
        return ValF32
    default:
        // i32, bool, string, array, struct, void → all i32-shaped (void
        // is filtered upstream so it never reaches here)
        return ValI32
    }
}
Task 3 — collect signatures in binary/module.go

Walk Program.Stmts in order. For each function (top-level or method) build a functype. Keep them in declaration order — that order is the type index, and lesson 26 will look up by index.

type funcSig struct {
    name     string     // "add" or "__Vec2__length"
    params   []byte     // encoded valtype bytes
    results  []byte
}

func collectSignatures(p *script.Program) ([]funcSig, error) {
    var out []funcSig
    for _, stmt := range p.Stmts {
        switch n := stmt.(type) {
        case *script.FunctionDeclaration:
            sig, err := signatureOf(n, "")
            if err != nil {
                return nil, err
            }
            out = append(out, sig)
        case *script.StructImplStatement:
            for _, m := range n.Methods {
                sig, err := signatureOf(m, n.Name)
                if err != nil {
                    return nil, err
                }
                out = append(out, sig)
            }
        }
    }
    return out, nil
}

func signatureOf(f *script.FunctionDeclaration, implName string) (funcSig, error) {
    var params []byte
    if implName != "" {
        params = append(params, ValI32)   // implicit self
    }
    for _, p := range f.Params {
        t := p.GetType()
        if t == nil {
            return funcSig{}, fmt.Errorf("no type on param %s", p.Name)
        }
        params = append(params, valType(t))
    }

    var results []byte
    if f.ReturnType != nil {
        results = append(results, valType(f.ReturnType.GetType()))
    }

    name := f.Name
    if implName != "" {
        name = fmt.Sprintf("__%s__%s", implName, f.Name)
    }
    return funcSig{name: name, params: params, results: results}, nil
}
Task 4 — emit the Type section

The Type section body is vec(functype). Each functype is 0x60 vec(params) vec(results):

func encodeTypeSection(sigs []funcSig) []byte {
    var body []byte
    body = AppendULEB128(body, uint32(len(sigs)))    // outer vec count
    for _, s := range sigs {
        body = append(body, 0x60)                          // functype tag
        body = AppendULEB128(body, uint32(len(s.params)))
        body = append(body, s.params...)
        body = AppendULEB128(body, uint32(len(s.results)))
        body = append(body, s.results...)
    }
    return section(SectionType, body)
}
Task 5 — wire it into CompileProgram 
func CompileProgram(node script.AstNode) ([]byte, error) {
    prog, ok := node.(*script.Program)
    if !ok {
        return nil, fmt.Errorf("root node is not *Program")
    }

    sigs, err := collectSignatures(prog)
    if err != nil {
        return nil, err
    }

    var out []byte
    out = append(out, magic...)
    out = append(out, version...)
    if len(sigs) > 0 {
        out = append(out, encodeTypeSection(sigs)...)
    }
        // later: function, code, export, …
    return out, nil
}

6. Verification

Pick a small plex file with a handful of typed functions — internal/script/compiler/testdata/bool_test.wat tells you what plex source looks like in WAT; use one of the .plex files in your test data (or write one inline). Then:

go run ./cmd/plexc -file my.plex -target wasm-bin
wasm-objdump -x ./dist/my.wasm

Expected output (something like):

Section Details:

Type[3]:
 - type[0] (i64, i64) -> i64
 - type[1] () -> i64
 - type[2] (i32, i64) -> ()

The number of types should equal the number of functions in the source, and each signature should match. If wasm-objdump complains about an invalid file, run with -d to get the dump up to the failure point — usually a uleb128 size that doesn't match the body length.

The file is not yet runnable Loading this .wasm in a runtime (e.g. wazero) will fail validation: declaring types is fine, but as soon as we add the Function section (lesson 26), it must be paired with a Code section of the same length. Right now wasm-objdump just inspects the bytes — it doesn't require a complete, valid module. Use -x, not -d, for inspection at this stage.
About deduplication Two functions with the same signature share a type. A real production emitter dedupes — only one functype entry per unique signature, with each function pointing to the right index. We're not doing that yet. Each function gets its own type entry; the indices are simply 0, 1, 2, … in declaration order. This is wasteful but correct, and the simpler indexing makes lesson 26 (Function + Code) much easier to write. We'll add a dedup pass after the whole pipeline runs end-to-end.
