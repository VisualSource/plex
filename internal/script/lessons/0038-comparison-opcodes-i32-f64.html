The Signed/Unsigned Asymmetry

Integer comparisons come in two flavours — _s and _u. Float comparisons don't. Why?

The bit pattern alone is ambiguous for integers. The 32-bit value 0xFFFFFFFF is -1 read as signed, 4294967295 read as unsigned. Their orderings are different: -1 < 0 signed, but 0xFFFFFFFF > 0 unsigned. So the WASM spec needs two opcodes per ordering comparison — one per interpretation. eq and ne don't need this split because equality is bit-equality regardless of sign interpretation.
IEEE 754 floats have built-in sign. The sign bit is the highest bit of the encoding; the format is inherently signed. There is no "unsigned f64" interpretation. So f64.lt, f64.gt, etc. are unique — there's no need (or way) to split.

Plex types integers as signed (its built-in i32 and i64 are signed). So you map plex's < to i32.lt_s / i64.lt_s, not the unsigned variants. If plex ever grows a u32 type, that's a future lt_u arm.

Implementation

Step 1 — Add the new opcodes

Edit opcodes.go. The i32 block already has eq/ne; add the four ordering ops next to them:

OpI32Eq  byte = 0x46
OpI32Ne  byte = 0x47
OpI32LtS byte = 0x48
OpI32GtS byte = 0x4A
OpI32LeS byte = 0x4C
OpI32GeS byte = 0x4E

And the f64 block — currently arithmetic only. Add the six comparisons:

OpF64Eq byte = 0x61
OpF64Ne byte = 0x62
OpF64Lt byte = 0x63
OpF64Gt byte = 0x64
OpF64Le byte = 0x65
OpF64Ge byte = 0x66

Step 2 — Extend cmpOpcode

Both type arms grow. The i32 arm fills in the four ordering ops:

case script.TypeKind_I32:
    switch op {
    case script.TokenType_EqualEqual:
        return OpI32Eq, nil
    case script.TokenType_NotEqual:
        return OpI32Ne, nil
    case script.TokenType_LessThen:
        return OpI32LtS, nil
    case script.TokenType_GreaterThen:
        return OpI32GtS, nil
    case script.TokenType_LessThenOrEqual:
        return OpI32LeS, nil
    case script.TokenType_GreaterThenOrEqaul:
        return OpI32GeS, nil
    }

And add a new f64 arm:

case script.TypeKind_F64, script.TypeKind_Float:
    switch op {
    case script.TokenType_EqualEqual:
        return OpF64Eq, nil
    case script.TokenType_NotEqual:
        return OpF64Ne, nil
    case script.TokenType_LessThen:
        return OpF64Lt, nil
    case script.TokenType_GreaterThen:
        return OpF64Gt, nil
    case script.TokenType_LessThenOrEqual:
        return OpF64Le, nil
    case script.TokenType_GreaterThenOrEqaul:
        return OpF64Ge, nil
    }

What This Lesson Cleared Up

  • Symmetry of the comparison table. Every primitive type now has a full ordering surface (well — i32 is signed-only and bool is just AND/OR, but every plex source program that types checks now also compiles).
  • The signed/unsigned distinction is encoding-level, not arithmetic-level. i32.lt_s and i32.lt_u are different opcodes because the comparison question changes depending on the interpretation. Add/sub/mul don't need the split because two's complement makes them bit-identical for both signs.
  • Floats are intrinsically signed. No f64.lt_u exists. The sign bit is part of the value, not a label applied externally.

Knowledge Check

Quiz

1. Why is there an i32.lt_s and an i32.lt_u, but only one f64.lt?

2. Why do i32.eq and i32.ne not need signed/unsigned variants like lt does?

3. The codegen dispatches comparisons via the operand type, not the result type. Why does that matter here?

4. near_one(1.0) returns 1 because 1.0 >= 0.99 && 1.0 <= 1.01 evaluates to true. Which short-circuit semantics matter here?
