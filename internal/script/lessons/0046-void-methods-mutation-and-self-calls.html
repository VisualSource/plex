Lesson 46 – Void Methods, Mutation, and Self-Calls

Goal: prove that self.field = ... mutation and self.other() chains work — and fix a subtle bug in the function epilogue that makes void methods trap on exit.

Files you'll touch: section.go · end_to_end_test.go · typecheck.go

Bug First: The Void Trap

Open section.go and find encodeCodeEntry. Notice these two lines at the end of every function body:

body = append(body, enc.buf...)
body = append(body, OpUnreachable)
body = append(body, OpEnd)

The OpUnreachable (0x00) was added as a WASM validator trick. For a non-void function, code paths that return a value always end in a return opcode. After return, control never reaches OpUnreachable — but the WASM validator is happy because unreachable is polymorphic: it satisfies any type requirement.

The trap For a void method like fn translate(dx: f64, dy: f64) { self.x = self.x + dx; ... }, there is no return statement. Execution falls through the body, hits OpUnreachable, and traps at runtime.

The fix is one condition: only emit OpUnreachable when the function has results:

if len(sig.results) > 0 {
    body = append(body, OpUnreachable)
}
body = append(body, OpEnd)

Void functions fall through to OpEnd with an empty stack — exactly what WASM expects for a () → () function.

Why Mutation Already Works

Think about what self.x = self.x + dx means to the compiler:

// MemberAssignment(Object=Identifier("self"), Field="x", Value=...) walk(Identifier("self")) → local.get 0 ; i32 ptr walk(self.x + dx) → f64.load ... ; load x + local.get 2 ; dx + f64.add f64.store offset=0 → writes result back to field

self is just locals[0] — the i32 pointer threaded in by newBodyEncoder when sig.isMethod = true. The MemberAssignment walker from lesson 44 takes any expression as the object and emits a store at the field's compile-time offset. No new codegen needed.

Why Self-Calls Already Work

self.area_approx() inside another method is a FunctionCall whose callee is a MemberAccess(Object=Identifier("self"), Field="area_approx"). The binary walker's dispatch branch:

  1. Resolves the object type from Identifier("self").GetType() → the struct type.
  2. Pushes the receiver: walk(callee.Object) → local.get 0.
  3. Pushes each arg.
  4. Calls __Circle__area_approx by its funcidx.

p.area_approx() and self.area_approx() generate identical opcodes — the only difference is whether the receiver comes from a named variable or local 0.

The Typechecker Fix

There is also a pre-existing bug in the typechecker's collectSignatures. Open typecheck.go and find the *script.StructImplStatement case:

// Before fix — method args not registered during collectSignatures:
for _, fn := range n.Methods {
    def.Methods[fn.Name] = newFuncInfo(c.scope)
}

Because methodInfo.Args was never populated here, method.GetArgsInOrder() returned [], so checkArgs validated 0 expected args for every method call — silently accepting calls with the wrong number of arguments.

The fix pre-registers param positions (types are filled later by checkFunction):

for _, fn := range n.Methods {
    methodInfo := newFuncInfo(c.scope)
    for i, arg := range fn.Params {
        methodInfo.Args[arg.Name] = &orderedItem{Pos: i}
    }
    def.Methods[fn.Name] = methodInfo
}
Why not types too? Types are resolved by checkExpression, which needs the full type-checking context. collectSignatures runs first as a lightweight pre-pass to register names and arities. Types are backfilled by checkFunction during the main pass. This is the same two-phase pattern used for free functions.

What's Next

  • Heap allocator factoring. You now have four call sites that bump-allocate: string literals, array literals, struct constructors, and (if you ever add closures) captured environments. The skeleton is identical each time: bump __heap_ptr, populate with stores, leave base pointer. A helper emitHeapAlloc(size uint32) (tmp uint32) is worth extracting once you feel the repetition.
  • Global struct instances. Can you declare a top-level let g = MyStruct(1.0, 2.0)? Currently globals are only numbers. A struct global would be an i32 global holding a heap pointer initialised in a module-level start function (or just emitted at the top of the first function that uses it).
  • Returning structs from functions. fn make(): Point { return Point(1.0, 2.0); } — the Point is allocated on the heap, and the i32 pointer is the return value. Should already work — confirm with a test.
