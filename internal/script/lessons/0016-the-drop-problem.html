Lesson 16 — The Drop Problem: Stack-Balanced Code Generation

compilerWATstack machinevalidation

Compile this plex program right now:

fn main(){
    1 + 1;
}
go run ./cmd/plexc -file cmd/plexc/src/simple.plex

The WAT output looks fine — clean, readable. Now validate it:

wat2wasm cmd/plexc/dist/simple.wat -o /tmp/simple.wasm
simple.wat:1:45: error: type mismatch at end of function,
    expected [] but got [i64]

The compiler produced invalid WebAssembly. A program that would never execute. This is the drop problem.

1. WebAssembly Is a Stack Machine

A WebAssembly function body is a sequence of instructions operating on an implicit value stack. Every instruction either pushes values onto it, pops values from it, or does both.

InstructionPopsPushes
i64.const 5—i64
i64.addi64, i64i64
local.set $xi64—
call $getX (returns f64)paramsf64
dropany (1 value)—

At the end of a function, the stack must contain exactly the function's declared return values — nothing more, nothing less. For a (func $main) with no result, the stack at exit must be empty.

WebAssembly validators check this statically before execution. There is no "run it and see".

The result of 1 + 1 is computed and left on the stack. Nobody consumes it. The function ends with one value on the stack when it declared zero. The validator rejects it.

2. Expression vs Statement Context

In plex (and most languages), the same syntax can appear in two different positions:

  • Expression context: the value is used — let x = point.getX();
  • Statement context: the value is discarded — point.getX();

In expression context, the caller consumes the value. In statement context, no one does — the value must be explicitly dropped.

The plex parser doesn't create an ExpressionStatement wrapper node. It returns the expression itself as the statement. So when the compiler's Block case iterates over n.Stmts, it sees a raw *FunctionCall or *BinaryExpression with no indication that it's in statement position.

3. The drop Instruction

WAT has exactly one instruction for this: drop. It pops one value from the stack and discards it, regardless of type.

❌ Invalid

(func $main
  i64.const 1
  i64.const 1
  i64.add
  ;; i64 is left on stack
  ;; function expects []
)

✅ Valid

(func $main
  i64.const 1
  i64.const 1
  i64.add
  drop
  ;; stack is now empty
  ;; function expects []
)

4. Where to Emit the Drop

The fix lives in the compiler's Block case. After compiling each statement, check: did it push a value that nobody is going to consume?

The logic you need:

  1. Does the statement implement script.Expression (i.e., does it have a type)?
  2. Is that type non-nil and non-void?
  3. If both yes: emit drop.
case *script.Block:
    for _, stmt := range n.Stmts {
        if err := c.Compile(stmt); err != nil {
            return err
        }
        // If the statement left a value on the stack, discard it
        if expr, ok := stmt.(script.Expression); ok {
            t := expr.GetType()
            if t != nil && t.Kind != script.TypeKind_Void {
                c.emit("drop")
            }
        }
    }

This works because the AST hierarchy is precise about what is an Expression:

Node typeImplements Expression?Needs drop?
FunctionCallyesyes, if return type is non-void
BinaryExpressionyesyes
MemberAccessyesyes
ArrayAccessyesyes
TernaryExpressionyesyes
AssignmentExpressionnono — compiler ends with local.set
MemberAssignmentnono — compiler ends with .store
IfStatementnono
WhileStatementnono

Two special cases to be aware of

VariableDeclaration implements Expression (it has GetType()) — but the compiler ends VariableDeclaration with local.set, which already consumes the value. Emitting an extra drop here would be wrong — you'd be trying to drop when the stack is already empty.

ReturnStatement also implements Expression. But after compiling return, the function exits. Any drop after it would be unreachable dead code.

You need to exclude both from the drop logic. There are two clean approaches:

Option A — explicit exclusion:

switch stmt.(type) {
case *script.VariableDeclaration, *script.ReturnStatement:
    // compiler already balances stack for these
default:
    if expr, ok := stmt.(script.Expression); ok {
        t := expr.GetType()
        if t != nil && t.Kind != script.TypeKind_Void {
            c.emit("drop")
        }
    }
}

Option B — check type after compiling (equivalent, more compact):

if expr, ok := stmt.(script.Expression); ok {
    t := expr.GetType()
    if t != nil && t.Kind != script.TypeKind_Void {
        switch stmt.(type) {
        case *script.VariableDeclaration, *script.ReturnStatement:
            // already balanced
        default:
            c.emit("drop")
        }
    }
}
Design observation: The fact that VariableDeclaration implements Expression is a bit accidental — it got GetType()/SetType() so the typechecker could annotate it, but it doesn't produce a value in the stack-machine sense. This is a common friction point: the AST interface hierarchy and the stack discipline don't always align. The explicit exclusion is the honest way to handle it.

5. Verifying with wat2wasm

After the fix, you can use wat2wasm as a ground-truth validator. It parses and validates WAT against the WebAssembly spec before converting to binary:

go run ./cmd/plexc -file cmd/plexc/src/simple.plex
wat2wasm cmd/plexc/dist/simple.wat -o /tmp/simple.wasm
# should produce no output (success)

go run ./cmd/plexc -file cmd/plexc/src/impl-struct.plex
wat2wasm cmd/plexc/dist/impl-struct.wat -o /tmp/impl-struct.wasm
# should produce no output (success)

If wat2wasm is happy, you know the output is structurally valid WebAssembly — which is a stronger guarantee than "it compiles".

Check Your Understanding

1. A plex void function calls another void function: printResult();. After the fix, does it emit drop?

✅ No drop. FunctionCall.GetType() returns a Void type. The check t.Kind != TypeKind_Void is false, so no drop is emitted. The stack stays balanced automatically.

2. Why can't you emit drop after compiling a VariableDeclaration?

✅ The compiler ends VariableDeclaration with local.set $name which pops the initializer value. The stack is already empty. Emitting drop after that would try to pop from an empty stack — another WAT validation error.

3. In what sense is this fix "type-directed"?

✅ The compiler reads expr.GetType() — the type the typechecker annotated on the node — to decide if a value is on the stack. If the type is void, no value was pushed. If it's non-void, one was. This is another payoff of the annotated AST.
