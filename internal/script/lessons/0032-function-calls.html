Lesson 32 – Function Calls: call funcidx

Goal: compile square(a) + square(b) to valid WASM binary. By the end, sum_squares(3, 4) = 25 — the 3-4-5 triangle, proven by your compiler.

Files you'll touch: opcodes.go · body.go · module.go · section.go · end_to_end_test.go

The Big Idea: The Stack Is the Calling Convention

WASM function calls have no hidden complexity: push the arguments onto the value stack left-to-right, then emit call funcidx. The engine pops the arguments, runs the callee, and pushes the return value (if any). Your recursive walk already does everything needed — just emit each argument expression in order, then emit the call.

; sum_squares(3, 4) → square(3) + square(4) ; square(a): walk arg 'a', then call 20 00 ; local.get 0 (a) stack: [a] 10 00 ; call 0 (square) stack: [a*a] ; square(b): walk arg 'b', then call 20 01 ; local.get 1 (b) stack: [a*a, b] 10 00 ; call 0 (square) stack: [a*a, b*b] ; add the results 7C ; i64.add stack: [a*a + b*b] 0F ; return

The only non-obvious thing is the funcidx: WASM identifies functions by their position in the function section (0-indexed), not by name. So before emitting any bytecode, you need a map from function name to its index — built once from the sigs slice you already have.

InstructionEncodingStack effect
call funcidx0x10 + ULEB128 u32pops N args, pushes 0 or 1 result
Names don't exist at runtime. The WASM binary format has no symbol table for internal calls. Names → indices is a compile-time-only mapping. The export section (which you built in lesson 27) is the one place names appear — but only for functions the host wants to call from outside.

Threading the Function Index Map

The change touches the data flow from CompileProgram down to bodyEncoder. Here's the full path:

CompileProgram → collectSignatures // already returns []funcSig with .name fields → build funcIndices // NEW: map[string]uint32 from sigs[i].name → i → encodeCodeSection(funcs, sigs, funcIndices) → encodeCodeEntry(f, sig, funcIndices) → newBodyEncoder(f, sig, funcIndices) → b.funcIndices = funcIndices

The map itself is tiny — one allocation, shared read-only across all function bodies.

Step 3 — Handle *script.FunctionCall in walk

The AST node is FunctionCall{Callee AstNode, Args []AstNode}. For direct calls, Callee is an *script.Identifier. Walk each argument in order (left-to-right), then emit call:

case *script.FunctionCall:
    for _, arg := range n.Args {
        if err := b.walk(arg); err != nil {
            return err
        }
    }
    id, ok := n.Callee.(*script.Identifier)
    if !ok {
        return fmt.Errorf("unsupported callee type %T", n.Callee)
    }
    idx, ok := b.funcIndices[id.Value]
    if !ok {
        return fmt.Errorf("unknown function %s", id.Value)
    }
    b.buf = append(b.buf, OpCall)
    b.buf = AppendULEB128(b.buf, idx)
    return nil

Step 5 — Write the test

Add to end_to_end_test.go. Two functions where the second calls the first — and the result is provable by the Pythagorean theorem:

func TestEndToEnd_FunctionCall(t *testing.T) {
    src := `
        fn square(x: i64): i64 {
            return x * x;
        }
        fn sum_squares(a: i64, b: i64): i64 {
            return square(a) + square(b);
        }
    `
    runOne(t, src, "sum_squares", []uint64{3, 4}, 25)   // 3²+4²=25
    runOne(t, src, "sum_squares", []uint64{5, 12}, 169) // 5²+12²=169=13²
    runOne(t, src, "square",      []uint64{7},      49)  // direct call too
}

Run with:

go test ./compiler/binary/... -run TestEndToEnd -v

What About the Function Index Order?

The index assigned to a function is its position in sigs, which is the order collectSignatures encounters it in the AST — i.e., source order. So in the test above, square gets index 0 and sum_squares gets index 1. The call 0 inside sum_squares correctly refers to square.

Forward references work fine. WASM validates function indices at module load time, not at parse time. A function can call another that appears later in the source — as long as the index is correct when the module is instantiated. Your map is built from the complete sigs slice before any body is encoded, so forward references are handled automatically.

What's Next

  • Recursion — function calls already support it (a function can call itself by its own index). A fib(n) test would confirm it.
  • Call expressions as statements — if FunctionCall appears as a statement whose result is discarded, the unused return value needs a drop (0x1A) to keep the stack balanced. The WASM validator will reject unbalanced stacks.
