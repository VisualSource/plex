Lesson 41 – Array Length and Indexing

Goal: read what lesson 40 wrote. arr.len() and arr[i] both reduce to "compute an address, run a typed load". Two new AST cases, three new opcodes, one new arithmetic pattern.

Files you'll touch: opcodes.go · helpers.go · body.go · end_to_end_test.go

Part 1 — arr.len()

This is the easy half: arr.len() is mechanically identical to s.len() from lesson 37. The array's pointer points at the length prefix; load four bytes, sign-extend to i64, done.

walk(arr) ; → i32 base 28 02 00 ; i32.load align=2 offset=0 → i32 length AC ; i64.extend_i32_s → i64 length
The same byte sequence as s.len(). Strings and arrays share their length-prefix-at-offset-0 layout by design, which means their .len() codegen is one shape, dispatched on object type. The MemberAccess arm from lesson 37 just gains an array case parallel to the string one.

The typechecker already reports arr.len() as Int (see typecheck.go:362-368), so the function signature will declare i64 return and the validator is satisfied after extend_i32_s.

Part 2 — arr[i]

The arithmetic is the interesting bit. The element you want lives at address base + 4 + i * elemSize. Four numeric facts conspire to make the code sequence non-trivial:

  1. base is i32 (it's a memory address).
  2. i is i64 — plex's integer literals and identifiers default to Int, which is i64.
  3. elemSize is a compile-time constant.
  4. The + 4 displacement can ride along inside the load's memarg, saving an instruction.

Putting them together:

walk(arr) ; → i32 base walk(i) ; → i64 idx stack: [base, i64_idx] A7 ; i32.wrap_i64 stack: [base, i32_idx] 41 elemSize ; i32.const elemSize stack: [base, i32_idx, sz] 6C ; i32.mul stack: [base, i32_idx*sz] 6A ; i32.add stack: [base + i32_idx*sz] OP align 04 ; typed.load offset=4 → element value on stack
Why i32.wrap_i64? Memory addresses in 32-bit WASM are i32. The index is i64. Without the wrap, you have an i64 on the stack and the validator rejects i32.mul below it. The narrowing is also semantically reasonable: any index beyond 2³¹ is meaningless given the 4 GiB memory limit anyway.
Element typeLoad opcodeNatural align
i32i32.load (0x28)2
i64 / inti64.load (0x29)3
f64 / floatf64.load (0x2B)3

Same dispatch shape as the store family from lesson 40 — element type picks both the opcode and the alignment hint.

Implementation

Step 1 — Opcodes

Add to opcodes.go (i32.load is already there from lesson 36):

OpI64Load    byte = 0x29
OpF64Load    byte = 0x2B
OpI32WrapI64 byte = 0xA7

Step 2 — loadOpcode helper

Mirror the storeOpcode helper from lesson 40. In helpers.go:

func loadOpcode(k script.TypeKind) (op byte, align uint32) {
    switch k {
    case script.TypeKind_I32:
        return OpI32Load, 2
    case script.TypeKind_I64, script.TypeKind_Int:
        return OpI64Load, 3
    case script.TypeKind_F64, script.TypeKind_Float:
        return OpF64Load, 3
    default:
        return OpI32Load, 2 // pointer-as-i32
    }
}

Step 3 — Add the array case to arr.len() dispatch

In [body.go]'s FunctionCall arm — specifically the *script.MemberAccess branch you wrote in lesson 37 — extend the type switch:

switch objType.Kind {
case script.TypeKind_String:
    // ... existing s.len() implementation ...
case script.TypeKind_Array:
    switch callee.Field {
    case "len":
        if err := b.walk(callee.Object); err != nil {
            return err
        }
        b.buf = append(b.buf, OpI32Load)
        b.buf = AppendULEB128(b.buf, 2) // align
        b.buf = AppendULEB128(b.buf, 0) // offset
        b.buf = append(b.buf, OpI64ExtendI32S)
        return nil
    default:
        return fmt.Errorf("array has no method %s", callee.Field)
    }
default:
    return fmt.Errorf("method calls on %s not supported", objType.Kind)
}

Notice this is byte-for-byte identical to the string case — same load, same extend. A future cleanup could factor them out into one arm that handles "anything with a length prefix at offset 0". Don't do that today; collapse only after the third sibling appears.

Step 4 — Wire *script.ArrayAccess in walk

The AST node is ArrayAccess{Target, Index, type_} (see ast_nodes.go:254-263). type_ is the element type (set by the typechecker at typecheck.go:296-315).

case *script.ArrayAccess:
    elemType := n.GetType()
    if elemType == nil {
        return fmt.Errorf("array access has no element type")
    }

    elemSize := elemSizeOf(elemType.Kind)
    loadOp, loadAlign := loadOpcode(elemType.Kind)

    // base address
    if err := b.walk(n.Target); err != nil {
        return err
    }
    // index (i64), narrowed for address arithmetic
    if err := b.walk(n.Index); err != nil {
        return err
    }
    b.buf = append(b.buf, OpI32WrapI64)

    // index * elemSize
    b.buf = append(b.buf, OpI32Const)
    b.buf = AppendSLEB128(b.buf, int64(elemSize))
    b.buf = append(b.buf, OpI32Mul)

    // base + (i * elemSize)
    b.buf = append(b.buf, OpI32Add)

    // load at +4 (skip the length prefix)
    b.buf = append(b.buf, loadOp)
    b.buf = AppendULEB128(b.buf, loadAlign)
    b.buf = AppendULEB128(b.buf, 4)
    return nil
No bounds check today. arr[100] on a 3-element array reads garbage from beyond the array's bytes (or, if it crosses a page boundary, traps with "out of bounds memory access"). Real languages emit a bounds-check sequence here; plex doesn't yet. A future lesson can add a cmp + branch pair before the load.

    src := `
        fn three(): int {

func TestEndToEnd_ArrayIndex(t *testing.T) {
    src := `
        fn first(): int {
            let arr = [10, 20, 30];
            return arr[0];
        }
        fn middle(): int {
            let arr = [10, 20, 30];
            return arr[1];
        }
        fn last(): int {
            let arr = [10, 20, 30];
            return arr[2];
        }
        fn sum_all(): int {
            let arr = [10, 20, 30];
            return arr[0] + arr[1] + arr[2];
        }
    `
    runOne(t, src, "first",   nil, 10)
    runOne(t, src, "middle",  nil, 20)
    runOne(t, src, "last",    nil, 30)
    runOne(t, src, "sum_all", nil, 60)
}

If the empty-array case errors: the typechecker may need an explicit annotation (let arr: int[] = [];) because it can't infer the element type from zero elements. If it still fails the typecheck, drop the empty case — the `three` case alone proves length works.

The Shape You Just Pinned

You can now write loops like this end-to-end:

fn total(): int {
    let arr = [1, 2, 3, 4, 5];
    let i: int = 0;
    let sum: int = 0;
    while i < arr.len() {
        sum = sum + arr[i];
        i = i + 1;
    }
    return sum;
}

That's a non-trivial program — array construction, indexed reads, length-comparison-as-loop-bound — entirely from plex source, compiled to bytecode the host can run. The binary backend has earned its name.

Knowledge Check

Quiz

1. Why is i32.wrap_i64 needed in the array-indexing sequence?

2. The +4 to skip the length prefix is encoded in the load's memarg, not as a separate i32.add. Why?

3. arr.len() and s.len() compile to identical bytecode. What does that say about the array and string layouts?

4. arr[100] on a 3-element array. What happens today?

What's Next

  • Mutating array elements — arr[i] = x is a MemberAssignment-shaped node that compiles to the same address arithmetic followed by a typed store. The store is in your opcode table already.
  • Bounds checks — emit i32.lt_u idx, len before the load; trap or branch on failure. Adds three instructions per access — cheap relative to the load itself.
  • Strings, but more — the binary backend currently treats string indexing as "returns a string", not a byte. Aligning that with reality (or building a separate string.byte_at(i)) is its own lesson.
  • Struct literals — same allocator pattern as arrays, but per-field offsets from a layout table instead of i * elemSize.
