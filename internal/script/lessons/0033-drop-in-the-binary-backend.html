Lesson 33 – Drop in the Binary Backend

Goal: make a statement-position call like square(5); compile to valid WASM. By the end, a call whose return value is discarded leaves the stack balanced — no validator errors, no leaked values.

Files you'll touch: opcodes.go · body.go · end_to_end_test.go

This is the same conceptual lesson as Lesson 16 — The Drop Problem, but for the binary backend. You already solved this for the WAT compiler. Today is about recognising the same bug recurring in a new context and porting the fix.

Warm-up: Recursion Was Free

Before we get to the bug, a small celebration. Lesson 32's design — building funcIndices from the complete sigs slice before any body is encoded — quietly handed you recursion for free. Add this test to end_to_end_test.go and watch it pass without a line of new code in body.go:

func TestEndToEnd_Recursion(t *testing.T) {
    src := `
        fn fib(n: i64): i64 {
            if n < 2 { return n; }
            return fib(n - 1) + fib(n - 2);
        }
    `
    runOne(t, src, "fib", []uint64{0},  0)
    runOne(t, src, "fib", []uint64{1},  1)
    runOne(t, src, "fib", []uint64{10}, 55)
}
go test ./internal/script/compiler/binary/... -run TestEndToEnd_Recursion -v
Why this works. When the encoder walks the body of fib, it looks up fib in b.funcIndices. The map was built from all signatures up front, so fib's own index is already there. The validator accepts the self-reference at module-load time — there is no "function not yet defined" error in WASM the way there is in some single-pass C compilers.

The Bug: a Latent Stack Leak

Now break the compiler. Add this test — it should work, but won't:

func TestEndToEnd_CallAsStatement(t *testing.T) {
    src := `
        fn square(x: i64): i64 {
            return x * x;
        }
        fn warmup(n: i64): i64 {
            square(n);          // result discarded — pure waste, but legal
            return n + 1;
        }
    `
    runOne(t, src, "warmup", []uint64{10}, 11)
}
go test ./internal/script/compiler/binary/... -run TestEndToEnd_CallAsStatement -v

Expected failure — something like:

module[0].function[1]: invalid function: ...
    type mismatch: ... has 1 value(s) ... expected 0

The validator is telling you the function body has a leftover i64 on the stack that nobody consumed. You introduced it the moment you added OpCall.

Why It Happens

Every instruction in WASM has a known stack effect. A function whose declared result is i64 must end with exactly one i64 on the stack — nothing more, nothing less.

local.get n
i64 (n)
→
call square
i64 (n*n) ← leaked
→
local.get n / i64.const 1 / i64.add
i64 (n*n)
i64 (n+1)
→
return
i64 leftover!

The FunctionCall node doesn't know whether its result will be consumed. The parent does. When a call appears inside return foo(...) or x = foo(...) or foo(bar()), the parent consumes the value naturally. When it appears as a top-level statement in a Block, nothing does.

InstructionEncodingStack effect
drop0x1Apops 1 value of any type
The pattern. When a statement is itself an expression that produces a value, emit drop after it. Walking Block.Stmts is the right place to decide this: the parent of every statement is a Block, and the Block case in walk already iterates them.

This is the exact same fix the WAT compiler uses in compiler.go (the case *script.Block arm). Port the logic.

Implementation

Step 1 — Add the opcode

In opcodes.go, add the parametric instruction group:

OpDrop byte = 0x1A

Per the spec, drop is in the parametric instructions group — instructions that operate on the stack without caring about value types.

Step 2 — Extend the Block case in walk

Open body.go. The current *script.Block case walks each statement and stops. Add a post-walk check: if the statement satisfies script.Expression, has a non-void type, and isn't already a consumer (variable declaration, assignment, return), emit drop:

case *script.Block:
    for _, s := range n.Stmts {
        if err := b.walk(s); err != nil {
            return err
        }
        if expr, ok := s.(script.Expression); ok {
            t := expr.GetType()
            if t != nil && t.Kind != script.TypeKind_Void {
                switch s.(type) {
                case *script.VariableDeclaration, *script.AssignmentExpression, *script.ReturnStatement:
                    // already consume their value via local.set / return
                default:
                    b.buf = append(b.buf, OpDrop)
                }
            }
        }
    }
    return nil
Why exclude VariableDeclaration and AssignmentExpression? Both already emit a local.set after their RHS, which itself pops the value. Adding drop on top would pop the next value down — corrupting the stack instead of cleaning it. ReturnStatement is excluded because return consumes its operand by transferring it to the caller.

Step 3 — Re-run the test

go test ./internal/script/compiler/binary/... -run TestEndToEnd_CallAsStatement -v

Should now print --- PASS. And run the full suite one more time to confirm nothing else broke:

go test ./internal/script/compiler/binary/... -v

The Shape of Stack Discipline

Notice that the binary backend now follows the same rule the WAT compiler does, expressed in the same place (the Block case). The shape of correct codegen for a stack machine is invariant across textual and binary backends — only the byte encoding differs.

This is one of the satisfying realisations of compiler construction: the IR isn't the WAT, and it isn't the bytes — it's the stack discipline itself. WAT is just one notation for it; LEB128-encoded opcodes are another.
