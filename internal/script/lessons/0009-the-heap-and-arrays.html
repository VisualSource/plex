Lesson 9 – The Heap and Arrays

You have type-aware locals, string addresses, and a working type resolver. Before this lesson is over you will have arrays in WASM — real, indexable arrays that live in linear memory at runtime. To get there, you need two things: a mutable global heap pointer, and the arithmetic to lay out and index an array's bytes.

1. First: fix the TODO you left in BinaryExpression

Your resolveType correctly maps int → i64, but BinaryExpression still always emits f64.add, f64.lt, etc. Now that locals carry types, this inconsistency will cause WASM validation errors as soon as you mix integer variables with arithmetic.

The WASM operator names are symmetric — just swap the prefix:

plex/WASM typeaddsubmuldivless-thanequal
f64f64.addf64.subf64.mulf64.divf64.ltf64.eq
f32f32.addf32.subf32.mulf32.divf32.ltf32.eq
i64i64.addi64.subi64.muli64.div_si64.lt_si64.eq
i32i32.addi32.subi32.muli32.div_si32.lt_si32.eq

The _s suffix on integer divide and less-than means "signed" — plex numbers are signed, so always use the signed variants.

Task A — Type-aware BinaryExpression

The compiler needs to know the type of the operands to pick the right operator prefix. The cleanest approach: add a helper method typeOf(node AstNode) string that inspects the node and returns the WASM type string. Then use it in the binary expression case.

func (c *Compiler) typeOf(node script.AstNode) string {
    switch n := node.(type) {
    case *script.NumberLiteral:
        if strings.Contains(n.Value, ".") {
            return "f64"
        }
        return "i64"
    case *script.Identifier:
        for _, l := range c.locals {
            if l.Name == n.Value {
                return l.Type
            }
        }
        return "f64" // fallback
    case *script.BinaryExpression:
        return c.typeOf(n.Left) // type propagates from left operand
    case *script.FunctionCall:
        return "f64" // TODO: look up return type from function table
    default:
        return "f64"
    }
}

Then in the BinaryExpression case, determine the prefix before the operator switch:

prefix := c.typeOf(n.Left)
switch n.Operator {
case script.TokenType_Plus:
    c.emit(prefix + ".add")
case script.TokenType_Minus:
    c.emit(prefix + ".sub")
case script.TokenType_Star:
    c.emit(prefix + ".mul")
case script.TokenType_Div:
    divOp := prefix + ".div"
    if prefix == "i32" || prefix == "i64" {
        divOp += "_s"
    }
    c.emit(divOp)
case script.TokenType_LessThen:
    ltOp := prefix + ".lt"
    if prefix == "i32" || prefix == "i64" {
        ltOp += "_s"
    }
    c.emit(ltOp)
case script.TokenType_EqualEqual:
    c.emit(prefix + ".eq")
...
}

Make sure your existing compiler tests still pass after this change.

Why left operand determines the type

In a well-typed expression, both sides of a binary operator should have the same type. Using the left operand's type as the "result type" is a simplification that works for homogeneous expressions. A full compiler would resolve the type of both sides and report a type error if they differ — that's a future lesson.

2. WASM globals

A mutable global is a named value that persists across function calls, visible to all functions in the module. It's declared at the module level:

(global $heap_ptr (mut i32) (i32.const 1024))

The (mut i32) says it's a mutable i32. The initial value is 1024 — we reserve the first 1 KiB for static data (string literals, etc.).

Reading and writing it:

global.get $heap_ptr    ;; push current heap_ptr onto stack
global.set $heap_ptr    ;; pop top of stack → store in heap_ptr

This is the only state in WASM that survives between calls without going through memory. Locals disappear when the function returns; the global lives until the module is destroyed.

3. The bump allocator

A bump allocator (also called an arena allocator) is the simplest possible heap: a pointer that only ever moves forward. To allocate N bytes:

  1. Read the current heap pointer → that's your allocated address.
  2. Add N to the heap pointer.
  3. Write the new value back.
  4. Return the original address.

In WAT, a helper function for this:

(func $alloc (param $size i32) (result i32)
  (local $ptr i32)
  global.get $heap_ptr    ;; push current heap_ptr
  local.set $ptr          ;; ptr = heap_ptr
  global.get $heap_ptr
  local.get $size
  i32.add
  global.set $heap_ptr    ;; heap_ptr += size
  local.get $ptr          ;; return original ptr
)

There is no free. Memory is never reclaimed. For a teaching compiler this is fine — most programs run, produce output, and exit. Garbage collection is a lesson for another day.

Why start the heap at 1024?

Your static data (string literals) starts at offset 0. If you start the heap at 0 too, a heap allocation would overwrite your string data. 1024 bytes gives plenty of room for static data without needing to track exactly how many bytes the data section used. If your static data ever grows past 1024 bytes, you'd bump this number up — or better, calculate it from c.dataPtr rounded up to a nice alignment.

4. Array layout in memory

An array needs to store two things: how many elements it has (the length), and the elements themselves. The standard layout is a header followed by data:

offset + 0: [length: i32] 4 bytes offset + 4: [element 0: f64] 8 bytes offset + 12: [element 1: f64] 8 bytes offset + 20: [element 2: f64] 8 bytes ... total size = 4 + (N × 8) bytes for an f64 array

So for an array [1.0, 2.0, 3.0], you allocate 4 + 3×8 = 28 bytes, write 3 at the base, write 1.0 at base+4, 2.0 at base+12, 3.0 at base+20, and push the base address.

The store instructions

;; write an i32 to memory: i32.store takes (addr, value)
local.get $ptr
i32.const 3        ;; length = 3
i32.store          ;; mem[$ptr] = 3

;; write an f64 to memory: f64.store takes (addr, value)
local.get $ptr
i32.const 4        ;; offset past the length header
i32.add            ;; address of element 0
f64.const 1.0
f64.store          ;; mem[$ptr + 4] = 1.0

5. Compiling ArrayLiteral

The *script.ArrayLiteral node has a slice of element expressions. To compile it:

  1. Calculate the total size: 4 + len(elements) × 8 bytes.
  2. Call $alloc to get a base address.
  3. Store the local variable pointing to that address.
  4. Write the length header at base + 0.
  5. For each element, compile the element expression and store it at base + 4 + (i × 8).
  6. Push the base address (the "value" of the array literal is a pointer).

Task B — Implement arrays

Three things to do:

1. Add the $alloc function and the global to CompileProgram. Emit them when memory is needed (you already have the len(c.strings) > 0 guard — extend it to also cover arrays, or emit memory unconditionally).

c.emit("(global $heap_ptr (mut i32) (i32.const 1024))")
c.emit("(func $alloc (param $size i32) (result i32)")
c.depth++
c.emit("(local $ptr i32)")
c.emit("global.get $heap_ptr")
c.emit("local.set $ptr")
c.emit("global.get $heap_ptr")
c.emit("local.get $size")
c.emit("i32.add")
c.emit("global.set $heap_ptr")
c.emit("local.get $ptr")
c.depth--
c.emit(")")

2. Add *script.ArrayLiteral to the collectLocals / collectStrings passes. Recurse into element expressions so nested strings and locals are found.

3. Add *script.ArrayLiteral to Compile.

case *script.ArrayLiteral:
    elemSize := 8  // f64 element size in bytes
    totalSize := 4 + len(n.Elements)*elemSize

    // allocate memory, capture base address in a temp local
    // (you'll need a fresh temp local — consider a helper that generates "$tmp0", "$tmp1", etc.)
    c.emit(fmt.Sprintf("i32.const %d", totalSize))
    c.emit("call $alloc")
    // store address, then work with it...
    // write length header, then each element

The tricky part: after calling $alloc, the address is on the stack. To use it multiple times (once for the length write, once per element), you need to local.tee it into a temporary local — local.tee stores a value and also leaves it on the stack, unlike local.set which consumes it.

c.emit("local.tee $tmp")    ;; stores addr AND leaves it on stack
c.emit("i32.const 3")
c.emit("i32.store")         ;; writes length

;; element 0
c.emit("local.get $tmp")
c.emit("i32.const 4")
c.emit("i32.add")           ;; addr + 4
// compile element 0 expression
c.emit("f64.store")

You'll need to track how many temp locals you've emitted and declare them at the function top (same way you declare regular locals). A simple approach: add a tmpCount int field to Compiler and generate $tmp0, $tmp1, etc., resetting per function.

6. Array element access

Reading arr[i] in WASM means: compute the byte offset, then load from memory.

;; load arr[i] where arr is an i32 pointer, i is an i64
;; byte offset = 4 + i * 8
local.get $arr     ;; base address (i32)
i32.const 4
i32.add            ;; skip length header
local.get $i
i32.wrap_i64       ;; convert i64 index to i32 (needed for address arithmetic)
i32.const 8
i32.mul            ;; i * 8
i32.add            ;; base + 4 + i*8
f64.load           ;; load the f64 element

Notice i32.wrap_i64 — if your index is an i64 (which it would be if declared as int), address arithmetic requires i32. The wrap instruction truncates the i64 to i32, which is safe as long as arrays aren't billions of elements long.

Task C (stretch) — Implement ArrayAccess

Add *script.ArrayAccess to Compile. Remember from the parser that ArrayAccess.Object is the array expression and ArrayAccess.Field is the index expression (the naming is swapped from what you'd expect — this was noted as a known issue in the parser).

7. What you've built

After this lesson your compiler handles the full value model:

  • Numbers → f64/i64/i32 on the WASM stack, arithmetic via typed operators
  • Strings → i32 addresses into the static data section
  • Arrays → i32 addresses into heap-allocated memory, length header + elements

Structs follow the same pattern as arrays — a pointer to a block of bytes, with known field offsets instead of a length header and indexed elements. That's Lesson 10.
