Lesson 56 – Logical NOT (!)

Previous: Lesson 55 – Break and Continue

Adding ! to plex is the minimal example of a full-stack feature: one operator, seven files, one new concept at each layer. The WASM opcode already exists in opcodes.go — all the work is wiring.

The Compiler Pipeline

Every new language feature must clear every stage:

Tokenizertokenizer.go
Parserast.go
Type checkertypecheck.go
WAT codegencompiler.go
Binary codegenbody.go

Plus one token definition file that feeds both the tokenizer and parser.

Stage 1 – Token Definition

tokens.go defines every token type. Add TokenType_Not after TokenType_NotEqual: 

// in the const iota block
TokenType_NotEqual
TokenType_Not         // !  (standalone, not !=)

And in the String() switch:

case TokenType_Not:
    return "!"

And in the tokenSymbol map in ast.go:

TokenType_Not: "!",

Stage 2 – Tokenizer

tokenizer.go already handles !: when the next character is = it emits TokenType_NotEqual. If it's not =, it currently falls through to default, hitting ErrUnexpectedCharacter. Replace the fallthrough with an explicit emit: 

case '!':
    next, err := t.isNext('=')
    if err != nil {
        return nil, err
    }
    if next {
        start := NewPosition(t.col, t.row)
        if err := t.stream.Discard(1); err != nil {
            return nil, err
        }
        t.row++
        t.tokens = append(t.tokens, NewDataToken(TokenType_NotEqual, start, NewPosition(t.row, t.col)))
        continue
    }
    // NEW: standalone ! is TokenType_Not
    t.tokens = append(t.tokens, NewDataToken(TokenType_Not, NewPosition(t.col, t.row), NewPosition(t.col, t.row)))
    continue    // was: fallthrough
Disambiguation at lex time. The tokenizer decides ! vs != by peeking one character ahead. The parser never sees a raw ! — it only sees TokenType_Not or TokenType_NotEqual. This is the standard lookahead-1 pattern used for every two-character operator (==, &&, ||, etc.).

Stage 3 – Parser

! is a prefix unary operator, so it belongs in parseUnary() in ast.go. The existing code already handles - and +; add ! to the same condition: 

// was: if tt == TokenType_Minus || tt == TokenType_Plus
if tt == TokenType_Minus || tt == TokenType_Plus || tt == TokenType_Not {
    op := p.advance()
    operand, err := p.parseUnary()
    ...
    return &UnaryExpression{ Operator: op.IsToken(), Operand: operand.(Expression), ... }, nil
}

The resulting AST node is a UnaryExpression with Operator = TokenType_Not. No new AST node type needed.

Stage 4 – Type Checker

In typecheck.go, the UnaryExpression case currently just propagates the operand's type unchanged. That's wrong for !: it requires a bool operand and always returns bool. 

case *script.UnaryExpression:
    t := c.checkExpression(n.Operand)
    if n.Operator == script.TokenType_Not {
        if t == nil || t.Kind != script.TypeKind_Bool {
            c.error(n, fmt.Errorf("! requires a bool operand, got %s", t))
        }
        result := &script.Type{Kind: script.TypeKind_Bool}
        n.SetType(result)
        return result
    }
    n.SetType(t)
    return t

Stage 5 – WAT Codegen

In compiler.go, the UnaryExpression case handles + and -. Add !: 

case n.Operator == script.TokenType_Not && !n.Postfix:
    operand, err := c.compileExpr(n.Operand)
    if err != nil { return "", err }
    return operand + "\ni32.eqz", nil

Stage 6 – Binary Codegen

In body.go, the UnaryExpression case handles + and -. Add !: 

case *script.UnaryExpression:
    if n.Operator == script.TokenType_Plus {
        return b.walk(n.Operand)
    }
    if n.Operator == script.TokenType_Not {
        if err := b.walk(n.Operand); err != nil {
            return err
        }
        b.buf = append(b.buf, OpI32Eqz)
        return nil
    }
    if n.Operator != script.TokenType_Minus { ... }

The WASM Opcode: i32.eqz

i32.eqz (opcode 0x45) pops one i32, pushes 1 if it was 0, pushes 0 otherwise. It's "equals zero". Since plex booleans are i32 (false=0, true=1):

Input (i32)i32.eqz outputMeaning
01!false = true
10!true = false
any non-zero0truthy → !truthy = false

OpI32Eqz = 0x45 is already defined in opcodes.go — it's the same instruction used to invert the while-loop condition: condition; i32.eqz; br_if (exit).

Quick Check

Why does the tokenizer need to peek one character ahead when it sees !?

! and != share the same first character. Peeking at the next char disambiguates them at lex time, so the parser only ever sees one of two unambiguous token types.

What does i32.eqz return when its input is 1?

eqz = "equals zero". Input 1 is not zero, so it returns 0. That's !true = false. ✓

Why does adding ! to the typechecker require more than just propagating the operand type?

!42 would be a type error in plex. The typechecker is the right place to reject it before codegen tries to emit i32.eqz on an i64 value.

What precedence level does ! belong to in the parser?

All prefix operators (-x, +x, !x) bind tighter than binary operators. They live in parseUnary, above postfix and below cast/power.

Test to Write

func TestEndToEnd_Not(t *testing.T) {
    src := `
        export fn not_true(): bool  { return !true; }
        export fn not_false(): bool { return !false; }
        export fn double_not(x: bool): bool { return !!x; }
        export fn not_eq(a: i64, b: i64): bool { return !(a == b); }
    `
    runOne(t, src, "not_true",  nil, 0)           // !true  = false
    runOne(t, src, "not_false", nil, 1)           // !false = true
    runOne(t, src, "double_not", []uint64{1}, 1) // !!true = true
    runOne(t, src, "double_not", []uint64{0}, 0) // !!false = false
    runOne(t, src, "not_eq", []uint64{3, 3}, 0)  // !(3==3) = false
    runOne(t, src, "not_eq", []uint64{3, 4}, 1)  // !(3==4) = true
}

The double_not and not_eq cases are the most interesting: !! checks that two i32.eqz instructions cancel out, and !(a==b) checks that ! correctly wraps a comparison result.

WAT compiler note. If you're not sure what the WAT compiler's UnaryExpression handler looks like, search for TokenType_Minus in compiler.go — the ! case should slot in right alongside it.

Why This Matters

Adding ! is a template for every future operator. The same seven-file pattern applies to ++, ** (power), bitwise NOT, etc. Once you've done it once with the simplest possible operator, you know exactly what's required.
