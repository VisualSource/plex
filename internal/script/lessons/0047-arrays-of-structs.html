Lesson 47 – Arrays of Structs

Goal: fix a latent bug in the struct-constructor codegen that makes [Point(1.0, 2.0), ...] fail with a WASM type mismatch — then make arrays of structs fully operational.

Files you'll touch: body.go · end_to_end_test.go

How Arrays of Structs Work (in Theory)

Every struct value is a heap pointer — an i32 that points to the first byte of the struct's fields. An array of structs is therefore an array of i32 pointers, with each 4-byte slot holding one heap address.

Memory layout for [Point(1.0, 2.0), Point(10.0, 20.0)]: heap offset 0: [ 2 ][ptr_A][ptr_B] ← array: i32 len + 2 i32 pointers (12 bytes) | | | +→ offset 12: [ 10.0 f64 ][ 20.0 f64 ] ← Point B +→ offset 28: [ 1.0 f64 ][ 2.0 f64 ] ← Point A (allocated first, stored second)

The element type is TypeKind_Struct → elemSizeOf returns 4 (pointer width). loadOpcode / storeOpcode for struct → i32.load / i32.store with align 2. Everything follows from machinery already in place.

The Bug: Double-Walking Args

Open body.go and find the *script.FunctionCall → *script.Identifier case. You'll see:

// BEFORE (buggy):
for _, arg := range n.Args {    // ← outer walk: pushes args onto stack
    b.walk(arg)
}

if layout, ok := b.structs[callee.Value]; ok {
    return b.walkStructConstructor(layout, n.Args)  // ← walks args AGAIN internally
}

For a plain call like let p = Point(3.0, 4.0) this is usually harmless — the extra f64 values land below the result and get swept away when return sets the validator into "unreachable" mode. But inside an array literal:

// Array element loop emits: local.get arrTmp, walk(el), i32.store offset=N
// With the bug, walk(Point(1.0, 2.0)) leaves this on the WASM stack:
[i32_arrTmp, f64(1.0), f64(2.0), i32_struct_ptr]
//                 ↑ leaked from the outer walk, never consumed

// i32.store then tries to pop [address, value]:
// value = i32_struct_ptr ✓  address = f64(2.0) ✗  → WASM validator: "expected i32, but was f64"
Why did existing tests pass? After a return instruction, the WASM validator enters "unreachable" mode and accepts anything until end. Leaked stack values that sit below the function's return value are never inspected. The bug was only observable when struct constructors were nested inside other expressions (like array element slots) where the leaked values interfere with a subsequent instruction.

The Fix

Move the struct-constructor check before the generic arg-walk. walkStructConstructor already handles its own arguments:

// AFTER (correct):
if layout, ok := b.structs[callee.Value]; ok {
    return b.walkStructConstructor(layout, n.Args)
}

for _, arg := range n.Args {    // only reached for regular function calls
    b.walk(arg)
}

For struct constructors, the check fires first and returns immediately. The generic arg-walk is only reached for ordinary function calls. Four lines rearranged, nothing added.

Returning Structs from Functions

While we're here: does fn make(): Point { return Point(3.0, 4.0); } work? Yes — the struct is allocated on the heap; the function returns the i32 pointer as its result. The caller assigns it to a local and uses it normally. This required zero new code and was confirmed by a probe test before writing this lesson.

Parser Note: Array Type Annotations

If you try let pts: [Point] = [...], the parser reports "expected #ident, get [". The parser's type-annotation path only handles plain identifiers, not array types. let pts = [...] (inferred type) works fine. The annotation parser can be extended later — pin this for when you want named types in signatures.
