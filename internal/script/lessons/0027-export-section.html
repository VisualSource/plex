1. Two lingering bugs

I read your lesson-26 output. Two small bugs that are silently lurking — fix before adding more on top.

(a) AppendUint64 silently zeroes every f64 constant — body.go:43

Current code:

var raw [8]byte
binary.LittleEndian.AppendUint64(raw[:], math.Float64bits(v))   // ✗
b.buf = append(b.buf, raw[:]...)

binary.LittleEndian.AppendUint64(s, v) returns a new slice — like Go's built-in append, it does not modify the slice you passed in. Since raw is a fixed-size array and raw[:] already has len == cap == 8, the function allocates a new backing array, writes the bytes there, and you throw it away. raw stays zero-filled, so every f64 literal in the emitted .wasm is 0.0.

The right primitive is PutUint64, which writes in place:

var raw [8]byte
binary.LittleEndian.PutUint64(raw[:], math.Float64bits(v))    // ✓
b.buf = append(b.buf, raw[:]...)

Worth a unit test: encode a body containing f64.const 1.0 and assert the byte sequence includes 44 00 00 00 00 00 00 F0 3F (1.0 in little-endian IEEE-754 is the trailing 8 bytes after the opcode).

(b) Methods still pass m.Name as implName — helpers.go:24

Currently signatureOf(m, m.Name) for methods. The implicit self check now fires correctly (any non-empty string makes implName != "" true), but the generated symbol name is __methodName__methodName instead of the WAT backend's __StructName__methodName (see compiler.go:289-294). Fix:

case *script.StructImplStatement:
    for _, m := range n.Methods {
        sig, err := signatureOf(m, n.Name)    // ← n.Name, not m.Name
        ...

Bug is dormant right now (we don't look up methods by name yet), but it'll surface in lesson 28 the instant you emit a function call to a method.

3. What "export" actually means

A WASM module is a black box. Type, Function, Code — everything you've built so far — describes what the module contains. None of it tells the host (the embedder, e.g. wazero) what it can do with it. Exports are the public surface of the module.

An export is a (name, kind, idx) triple. The name is the string the host uses to look something up. The kind is one of four things — function, table, memory, or global. The idx identifies which entry of that kind (so funcidx 0 means the first function in the module). Without an export, that funcidx is internally addressable (you can call it from another function in the module) but completely invisible to the outside world.

The WAT analog Look at compiler.go:319-321. The line (export "name" (func $name)) is what becomes a single Export-section entry in the binary. Plex currently exports every top-level function and no methods — that's the policy your binary backend should match.

4. Export section anatomy

[id=07] [size] vec(export)

And each export is:

[name : vec(byte)]   ; UTF-8 bytes, length-prefixed
[kind : 1 byte]      ; 0x00=func, 0x01=table, 0x02=mem, 0x03=global
[idx  : uleb128]     ; index into the appropriate index space

That's it. Three fields per export. The whole section can be just a few dozen bytes for a typical module. Worked example — exporting a function named add at funcidx 0:

03
name length (uleb128): 3
61 64 64
"add" as UTF-8
00
kind = func
00
funcidx = 0

Six bytes for one export. The export-name "add" happens to fit in a single uleb128 byte for its length; names longer than 127 bytes spill into two bytes for the length prefix, but the encoding rule is the same.

5. Encoding strings — the name type

WASM has no separate "string" type at the binary level. Anywhere a string appears — export names, import module/field, custom-section data — it's encoded as vec(byte): a uleb128 length, then UTF-8 bytes. The same primitive will be reused in lessons 29 (data segments — string literals into linear memory) and any future Import work.

Task 1 — add a name helper to section.go 
// encodeName encodes a Go string as a length-prefixed UTF-8 byte sequence —
// the WASM `name` type, identical in shape to vec(byte).
func encodeName(buf []byte, s string) []byte {
    buf = AppendULEB128(buf, uint32(len(s)))
    return append(buf, s...)
}

One-liner. But it'll appear in three more places before this is over — worth extracting now rather than inlining.

Task 3 — decide what to export

Mirror the WAT backend's behaviour: top-level *FunctionDeclaration nodes get exported with their declared name. Methods do not — they're internal.

You already collect funcs []*script.FunctionDeclaration in collectSignatures, but it mixes top-level functions and methods. The funcidx of an entry equals its position in that slice — so what you need now is "is this entry a top-level export, and if so what's its name?" Easiest path: track a parallel exports []exportEntry while you collect:

type exportEntry struct {
    name string
    kind byte
    idx  uint32
}

func collectSignatures(p *script.Program) (
    []funcSig, []*script.FunctionDeclaration, []exportEntry, error,
) {
    var sigs   []funcSig
    var funcs  []*script.FunctionDeclaration
    var exports []exportEntry

    for _, stmt := range p.Stmts {
        switch n := stmt.(type) {
        case *script.FunctionDeclaration:
            sig, err := signatureOf(n, "")
            if err != nil { return nil, nil, nil, err }
                        exports = append(exports, exportEntry{
                name: n.Name,
                kind: ExportFunc,
                idx:  uint32(len(funcs)),     // funcidx == position in funcs
            })
            sigs  = append(sigs,  sig)
            funcs = append(funcs, n)

        case *script.StructImplStatement:
            for _, m := range n.Methods {
                sig, err := signatureOf(m, n.Name)   // ← n.Name (bug fix from §1b)
                if err != nil { return nil, nil, nil, err }
                sigs  = append(sigs,  sig)
                funcs = append(funcs, m)
                // methods are NOT exported
            }
        }
    }
    return sigs, funcs, exports, nil
}
Task 4 — emit the Export section

Add to section.go:

func encodeExportSection(exports []exportEntry) []byte {
    var body []byte
    body = AppendULEB128(body, uint32(len(exports)))
    for _, e := range exports {
        body = encodeName(body, e.name)
        body = append(body, e.kind)
        body = AppendULEB128(body, e.idx)
    }
    return section(SectionExport, body)
}

7. Verification — the first real run

This is the moment the binary backend actually runs. Write a parallel test helper next to validateByRun, but skipping the wat2wasm shell-out and calling the binary backend directly:

Task 6 — compiler/binary/end_to_end_test.go 
package binary_wasm

import (
    "context"
    "strings"
    "testing"

    "github.com/tetratelabs/wazero"
    "github.com/VisualSource/plex/internal/script"
)

func TestEndToEnd_FortyTwo(t *testing.T) {
    src := `
        fn forty_two(): i64 {
            return 42;
        }
    `

    ast, err := script.Parse(strings.NewReader(src))
    if err != nil { t.Fatal(err) }

    wasm, err := CompileProgram(ast.(*script.Program))
    if err != nil { t.Fatal(err) }

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)

    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    got, err := mod.ExportedFunction("forty_two").Call(ctx)
    if err != nil { t.Fatalf("call: %v", err) }

    if got[0] != 42 {
        t.Fatalf("forty_two() = %d, want 42", got[0])
    }
}

Run it:

go test ./internal/script/compiler/binary/... -run TestEndToEnd_FortyTwo -v

If wazero's Instantiate errors, the message is usually precise — "section X has invalid Y" — and a hexdump of the offending region (xxd ./dist/forty_two.wasm) will tell you exactly which byte is wrong. Common failures:

  • "unexpected section id" → your sections are out of order. Type → Function → Export → Code.
  • "function count mismatch" → Function and Code sections have different vec counts.
  • "could not find export" → name UTF-8 bytes wrong, or kind/idx byte wrong, or the entire Export section is being skipped (len(exports) == 0 guard).
✓ The win When the test passes, your binary backend has done end-to-end what the WAT backend has been doing all along — taken plex source, produced a runnable .wasm, and executed it in a real runtime. No wat2wasm. No external tool. The bytes between version and EOF are entirely your code's work. Everything from here is more sections and more opcodes on the same foundation.
