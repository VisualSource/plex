1. The shape of a .wasm file

You've been emitting WAT — the human-readable text format — then piping it through wat2wasm to produce the binary. The binary format isn't a compressed version of the text: it's a structured, length-prefixed format made of sections. Every section has the same outer shape:

[section_id] [section_size] [section_body...]

That repeating pattern is the whole file, after an 8-byte header. The core spec § 5.5 Modules defines the section IDs:

IDSectionWhat's in it
0CustomNames, debug info, anything ignored by the engine
1TypeFunction signatures: (i32, i32) → i32
2ImportFunctions/globals imported from host
3FunctionFor each function, which type it has (index into Type)
4TableFunction tables (for call_indirect)
5MemoryLinear memory declarations (page count)
6GlobalModule-level globals + their init expressions
7ExportWhat's visible to the host (functions, memory, globals)
8StartOptional auto-run function
9ElementFunction-table initializers
10CodeThe actual bytecode of every function body
11DataInitial bytes copied into linear memory (string literals!)

Sections appear in this numeric order (custom sections can be sprinkled anywhere). Compare this to the plex compiler's current WAT output — every (func ...), (memory ...), (global ...), (export ...) form lands in one of these sections. The mapping is direct: WAT is a sugar for this layout.

2. The 8-byte module skeleton

The entire prelude of every .wasm file is fixed and identical:

00 61 73 6D
magic — ASCII \0asm (read left-to-right)
01 00 00 00
version — little-endian uint32, currently 1

That's it. An empty .wasm file is exactly these 8 bytes — and it's a perfectly valid WebAssembly module (one with no types, no functions, no exports). The runtime will load it; there's just nothing to do. See the binary module grammar.

Endianness trap The 4 magic bytes are written in source order — they spell \0asm when you read the file with xxd. The version is a little-endian u32, so version 1 appears as 01 00 00 00, not 00 00 00 01. Most fixed-width integers in WASM are little-endian. Most variable-width integers, by contrast, use LEB128 — next.

3. LEB128 — the encoding everything else uses

Almost every length, index, and count in a .wasm file is a LEB128-encoded integer. (Long name: Little Endian Base 128. Came from DWARF; reused by WASM.) Two variants exist — unsigned (uleb128) and signed (sleb128). Section sizes, vector lengths, type indices: unsigned. Things like i32.const immediates: signed.

The encoding rule for unsigned LEB128:

  1. Take the integer's bits, split into 7-bit groups, least-significant group first.
  2. For each group except the last, set the high bit to 1 (continuation).
  3. The last group has its high bit set to 0 (terminator).

So the value 0 encodes as a single byte 0x00. The value 624485 = 0x98765 = binary 10011000_01110110_0101, split into 7-bit groups (LSB first): 1100101, 0001110, 0100110. Flag the continuation bits: 0xE5, 0x8E, 0x26 — the canonical LEB128 example from the Wikipedia article.

Decimal → uleb128

0     → 00
63    → 3F           ; fits in 7 bits
127   → 7F
128   → 80 01        ; needs continuation
255   → FF 01
624485 → E5 8E 26

Decimal → sleb128

0    → 00
63   → 3F
64   → C0 00  ; sign-bit collides → 2 bytes
-1   → 7F     ; all-ones, sign-extended
-64  → 40
-65  → BF 7F
Why LEB128? Most integers in a wasm file are small (a count of 3 fields, a local index of 7, a section size of 142 bytes). Fixed 4-byte ints would waste 3 bytes on each. LEB128 uses 1 byte for values 0-127, 2 for 128-16383, and so on — paying only for the bits you need. The cost is decoders must loop bit-by-bit instead of reading a fixed-width word.

4. Implementation: a new binary sub-package

Leave the existing WAT-emitting compiler.go untouched. We're adding a parallel binary backend, not replacing it. This lets us run both side-by-side and diff outputs while building confidence.

Task 1 — create internal/script/compiler/binary/leb128.go

Two helpers — they will be used by every section in every future lesson:

package binary

func AppendULEB128(buf []byte, v uint32) []byte {
    for {
        b := byte(v & 0x7F)
        v >>= 7
        if v != 0 {
            buf = append(buf, b|0x80)   // continuation bit
        } else {
            return append(buf, b)        // final group, top bit clear
        }
    }
}

func AppendSLEB128(buf []byte, v int64) []byte {
    for {
        b := byte(v) & 0x7F
        signBit := b & 0x40
        v >>= 7                       // arithmetic shift in Go for signed
        done := (v == 0 && signBit == 0) ||
                (v == -1 && signBit != 0)
        if done {
            return append(buf, b)
        }
        buf = append(buf, b|0x80)
    }
}

The signed version's termination condition is the subtle one. You stop when the remaining bits are all-zero (positive) and the high bit of the last group is 0, OR all-ones (negative) and the high bit of the last group is 1. That guarantees the decoder can sign-extend correctly. See spec §5.2.2.

Task 2 — unit-test the encoders

Drop this into leb128_test.go — these are the canonical reference values:

func TestULEB128(t *testing.T) {
    cases := []struct {
        in   uint32
        want []byte
    }{
        {0,      []byte{0x00}},
        {63,     []byte{0x3F}},
        {127,    []byte{0x7F}},
        {128,    []byte{0x80, 0x01}},
        {624485, []byte{0xE5, 0x8E, 0x26}},
    }
    for _, c := range cases {
        got := AppendULEB128(nil, c.in)
        if !bytes.Equal(got, c.want) {
            t.Errorf("uleb(%d) = % x, want % x", c.in, got, c.want)
        }
    }
}

Mirror it for signed with {0, [00]}, {-1, [7F]}, {63, [3F]}, {64, [C0 00]}, {-64, [40]}, {-65, [BF 7F]}.

Task 3 — create internal/script/compiler/binary/module.go

The module entry point. For this lesson it only emits the 8-byte header:

package binary

import "github.com/VisualSource/plex/internal/script"

var magic   = []byte{0x00, 0x61, 0x73, 0x6D}   // "\0asm"
var version = []byte{0x01, 0x00, 0x00, 0x00}   // 1 (little-endian u32)

func CompileProgram(node script.AstNode) ([]byte, error) {
    var out []byte
    out = append(out, magic...)
    out = append(out, version...)
    // sections will be appended here in later lessons
    return out, nil
}
Task 4 — wire it into cmd/plexc/main.go

The flag -target wasm-bin is already declared but unhandled (the default branch reports unknown). Add the case:

5. Verification

Build and run it on any plex source file — the parser still runs end-to-end, the binary backend just ignores the AST for now:

go run ./cmd/plexc -file ./examples/hello.plex -target wasm-bin
xxd ./dist/hello.wasm

Expected output — exactly 8 bytes:

00000000: 0061 736d 0100 0000                       .asm....

Now confirm a real WASM toolchain agrees this is valid. The classic check is to round-trip through wasm-objdump (from wabt, the same package as wat2wasm):

wasm-objdump -h ./dist/hello.wasm

It should print the file's section table — empty, but the magic and version are recognised. A second confirmation: have wat2wasm compile an empty WAT module and diff the bytes:

echo "(module)" | wat2wasm - -o /tmp/empty.wasm
diff <(xxd /tmp/empty.wasm) <(xxd ./dist/hello.wasm)
# → no diff
The win You can now produce a .wasm file that any WebAssembly engine on Earth will accept. It does nothing — but the contract is established. Every later lesson appends a few more bytes between version and the end of the file.
