Lesson 44 – Structs: Construction, Field Read, Field Write

Goal: compile Point(3.0, 4.0) to a heap-allocated struct, read p.x and p.y, and overwrite them. The last big language feature still missing from the binary backend lands today.

Files you'll touch: opcodes.go (maybe) · helpers.go · body.go · module.go · structs.go · end_to_end_test.go

Plex's Struct Shape

Plex declares structs in the familiar way:

struct Point {
    x: f64;
    y: f64;
}

And constructs them with what looks like a function call — but is actually a positional constructor:

let p = Point(3.0, 4.0);
let x = p.x;     // read
p.y = 5.5;          // write

At the AST level Point(3.0, 4.0) parses as FunctionCall{Callee: Identifier "Point", Args: [3.0, 4.0]} — same shape as a function call. The typechecker (see typecheck.go:412-421) routes by name: if callee.Value matches a struct in c.structs, it types the expression as Struct{Point}. Otherwise it's a real function.

Field access uses the AST nodes you've already touched: p.x is a bare MemberAccess; p.x = 5 is a MemberAssignment.

Memory Layout

A struct has no header. Fields are packed in declaration order at byte offsets determined by their type sizes. For Point at heap offset 0:

f64 = 3.0 (x)@0..@7
f64 = 4.0 (y)@8..@15

The struct's runtime value is the i32 pointer to x's first byte. p.x is load offset=0, p.y is load offset=8. Field offsets are compile-time constants — the codegen knows them from the struct's layout table.

Contrast with arrays: arrays have a 4-byte length prefix because their length is runtime-known; structs don't because their layout is compile-time-fixed. p.x goes straight to memarg offset=0, no +4 skip.

The Struct Layout Table

Before any function body is encoded, the compiler walks the program's struct declarations and builds a layout table. For each struct, it records each field's name, type, and byte offset.

Add to structs.go:

type structField struct {
    name   string
    kind   script.TypeKind
    offset uint32
}

type structLayout struct {
    name   string
    fields []structField
    size   uint32   // total bytes
}

func (s *structLayout) findField(name string) (structField, bool) {
    for _, f := range s.fields {
        if f.name == name {
            return f, true
        }
    }
    return structField{}, false
}

And the collector in helpers.go:

func collectStructs(p *script.Program) map[string]*structLayout {
    out := map[string]*structLayout{}
    for _, stmt := range p.Stmts {
        decl, ok := stmt.(*script.StructStatement)
        if !ok {
            continue
        }
        layout := &structLayout{name: decl.Name}
        var offset uint32
        for _, p := range decl.Fields {
            ft := p.GetType().Kind
            sz := elemSizeOf(ft)
            layout.fields = append(layout.fields, structField{
                name: p.Name, kind: ft, offset: offset,
            })
            offset += sz
        }
        layout.size = offset
        out[decl.Name] = layout
    }
    return out
}
No padding. Fields are packed without alignment padding. For { a: i32; b: f64; } this means b sits at offset 4 — not naturally 8-byte aligned. WASM accepts unaligned loads (alignment is a hint, lesson 37), but for cross-engine portability of dense data, real compilers add padding. Pin it as a future improvement — today we keep the lesson tight.

Three Codegen Cases

(1) Constructor — Point(3.0, 4.0) via FunctionCall

The existing FunctionCall case has an Identifier arm that looks up b.funcIndices. Before that lookup, check whether the name resolves to a struct. If yes, dispatch to a constructor helper:

case *script.Identifier:
    if layout, ok := b.structs[callee.Value]; ok {
        return b.walkStructConstructor(layout, n.Args)
    }
    idx, ok := b.funcIndices[callee.Value]
    // ... existing call logic ...

The constructor mirrors the array allocator from lesson 40 — same six-instruction bump prologue, same synthetic local for the base:

func (b *bodyEncoder) walkStructConstructor(layout *structLayout, args []script.AstNode) error {
    tmp := b.addSyntheticLocal(ValI32)

    // bump: tmp = heapPtr; heapPtr += layout.size
    b.buf = append(b.buf, OpGlobalGet); b.buf = AppendULEB128(b.buf, 0)
    b.buf = append(b.buf, OpLocalTee);  b.buf = AppendULEB128(b.buf, tmp)
    b.buf = append(b.buf, OpI32Const);  b.buf = AppendSLEB128(b.buf, int64(layout.size))
    b.buf = append(b.buf, OpI32Add)
    b.buf = append(b.buf, OpGlobalSet); b.buf = AppendULEB128(b.buf, 0)

    // store each field at its layout offset
    for i, arg := range args {
        f := layout.fields[i]
        storeOp, storeAlign := storeOpcode(f.kind)

        b.buf = append(b.buf, OpLocalGet); b.buf = AppendULEB128(b.buf, tmp)
        if err := b.walk(arg); err != nil {
            return err
        }
        b.buf = append(b.buf, storeOp)
        b.buf = AppendULEB128(b.buf, storeAlign)
        b.buf = AppendULEB128(b.buf, f.offset)
    }

    // leave base pointer on the stack
    b.buf = append(b.buf, OpLocalGet); b.buf = AppendULEB128(b.buf, tmp)
    return nil
}
Notice the parallel with arrays. Allocate, store via memarg-offset, leave the pointer. The only differences from ArrayLiteral: no length prefix (no store length step), per-field storeOp (instead of one element-type-wide store), and per-field offset from the layout (instead of 4 + i*elemSize). The shared shape is the heap-allocation pattern; the layout-specific bits parametrise it.

(2) Field read — bare MemberAccess

Until today, *script.MemberAccess only appeared inside FunctionCall.Callee (lesson 37's s.len()). Now it appears bare in expression position. Add a new top-level case in walk:

case *script.MemberAccess:
    objExpr, ok := n.Object.(script.Expression)
    if !ok {
        return fmt.Errorf("member access object has no type")
    }
    objType := objExpr.GetType()
    if objType == nil || objType.Kind != script.TypeKind_Struct {
        return fmt.Errorf("member access on non-struct type")
    }
    layout, ok := b.structs[objType.Struct]
    if !ok {
        return fmt.Errorf("unknown struct %s", objType.Struct)
    }
    field, ok := layout.findField(n.Field)
    if !ok {
        return fmt.Errorf("struct %s has no field %s", layout.name, n.Field)
    }
    loadOp, loadAlign := loadOpcode(field.kind)

    if err := b.walk(n.Object); err != nil {
        return err
    }
    b.buf = append(b.buf, loadOp)
    b.buf = AppendULEB128(b.buf, loadAlign)
    b.buf = AppendULEB128(b.buf, field.offset)
    return nil

(3) Field write — MemberAssignment

The node exists in the AST and the typechecker already validates it (typecheck.go:636-657). Just add the codegen case:

case *script.MemberAssignment:
    objExpr, ok := n.Object.(script.Expression)
    if !ok {
        return fmt.Errorf("member assignment object has no type")
    }
    objType := objExpr.GetType()
    if objType == nil || objType.Kind != script.TypeKind_Struct {
        return fmt.Errorf("member assignment on non-struct type")
    }
    layout, _ := b.structs[objType.Struct]
    field, ok := layout.findField(n.Field)
    if !ok {
        return fmt.Errorf("struct %s has no field %s", layout.name, n.Field)
    }
    storeOp, storeAlign := storeOpcode(field.kind)

    if err := b.walk(n.Object); err != nil {
        return err
    }
    if err := b.walk(n.Value); err != nil {
        return err
    }
    b.buf = append(b.buf, storeOp)
    b.buf = AppendULEB128(b.buf, storeAlign)
    b.buf = AppendULEB128(b.buf, field.offset)
    return nil

The Allocator Pattern, Revisited

You've now implemented three variants of the same shape:

LessonConstructHeaderField/element offset
36String literal4-byte length(none — bytes follow)
40Array literal4-byte length4 + i * elemSize
44Struct literal(none)layout.fields[i].offset
The shape is "allocate, populate via memarg offsets, return base pointer". The only things that vary: whether there's a header, how offsets are computed, and how the stores are typed. A unified (b *bodyEncoder).emitHeapInit(size uint32, populators []populator) error would consume all three call sites — but resist factoring until the variation pattern stabilises with method-receiver structs and closures (potential future shapes).

Knowledge Check

Quiz

1. Why do structs have no length-prefix header, while arrays do?

2. Point(3.0, 4.0) is parsed as a FunctionCall, not a dedicated StructLiteral node. What does that mean for the binary backend?

3. p.x at offset 0 uses memarg offset=0 on a typed load. Why isn't p.x identical to "arr[0] with elemSize=8"?

4. The struct layout uses packed fields (no alignment padding). What's the cost?

What's Next

  • Methods (impl Point { fn dist(): f64 { ... } }). The struct-impl machinery is already in the typechecker. Codegen needs to: (a) compile each method as a function with a synthesised self: i32 first parameter, (b) name-mangle to __StructName__methodName, (c) handle method-call dispatch (p.dist() compiles to "push p, push args, call __Point__dist").
  • Field alignment padding. Round each field's offset up to its natural alignment before placing it. A two-line change in collectStructs; pin until it actually matters for performance.
  • Factor the allocator pattern. Three call sites now share "allocate N bytes, populate via memarg offsets, leave base pointer". When the fourth arrives (likely method receivers or closure environments), pull it into a helper.
