Lesson 39 – Globals and the Heap Pointer

Goal: emit a WASM global, initialise it to "one past the last byte of static data", and export it. This is the foundation arrays need — every alloc call will eventually bump this pointer.

Files you'll touch: opcodes.go · section.go · module.go · end_to_end_test.go

Where the Heap Begins

Linear memory in your module currently looks like this after instantiation (assuming one string literal "hello" at offset 0):

05@0
00@1
00@2
00@3
'h'@4
'e'@5
'l'@6
'l'@7
'o'@8
heap

Bytes 0..8 hold the string data. The very next byte (offset 9) is where the heap starts. Your stringTable already tracks this — st.next is exactly the first unused offset after the last string.

The heap pointer is the heap. There is no separate heap structure; just a single 32-bit address that says "the next allocation goes here". alloc(n) reads the pointer, advances it by n, and returns the original value. This is the simplest possible allocator — no free list, no fragmentation tracking, no GC. Everything lives until the module unloads.

What a WASM Global Is

A global in WASM is a typed, optionally-mutable, module-level variable. It's nothing fancier than that — just a single value slot, addressed by index, that survives across function calls. The full structure:

FieldEncodingFor our use
typevaltype byte0x7F (i32)
mutability1 byte: 0=const, 1=mut0x01 (mutable)
init expressionconstant instructions + endi32.const <heapStart> end
The init expression is the same shape as a data segment's offset. Both use the constant-expression form — a tiny instruction stream terminated by end. You already wrote one in lesson 36 for the data section's offset (0x41 <leb> 0x0B). The exact same three-byte pattern works for a global's initialiser. This is one of WASM's elegant uniformities: every place that needs a compile-time constant uses the same expression form.

The new opcodes

OpcodeByteOperandStack effect
global.get0x23globalidx (ULEB128)push the global's current value
global.set0x24globalidx (ULEB128)pop a value, write it to the global

You won't use global.get/set in lesson 39's code paths yet — that's lesson 40 (arrays) — but add them now to keep the opcode file complete.

Section Layout

Sections you already emit, with the new one in place:

type (1) function (3) memory (5) global (6) ; ← new export (7) code (10) data (11)

Global lives between memory (5) and export (7). The validator enforces this — get it wrong and you'll see "invalid section order", exactly the error from lesson 36's first run.

Implementation

Step 1 — Opcodes

Add to opcodes.go:

OpGlobalGet byte = 0x23
OpGlobalSet byte = 0x24

Step 2 — Section encoder

In section.go:

func encodeGlobalSection(heapStart uint32) []byte {
    var body []byte

    body = AppendULEB128(body, 1)         // one global

    body = append(body, ValI32)             // type: i32
    body = append(body, 0x01)               // mutability: mutable

    body = append(body, OpI32Const)         // init: i32.const heapStart
    body = AppendSLEB128(body, int64(heapStart))
    body = append(body, OpEnd)                // end of init expression

    return section(SectionGlobal, body)
}

SectionGlobal = 6 is already in section.go's constants block.

Step 3 — Wire into CompileProgram

Where you currently emit memory + data, also emit the global section and add an export for the heap pointer. The emission stays conditional on "the program uses memory" — i.e. len(strings.entries) > 0 — because no allocator is needed for memory-less programs:

strings := collectStrings(node)

if len(strings.entries) > 0 {
    exports = append(exports, exportEntry{name: "memory", kind: ExportMemory, idx: 0})
    exports = append(exports, exportEntry{name: "__heap_ptr", kind: ExportGlobal, idx: 0})
}

// ... existing type/function sections ...

if len(strings.entries) > 0 {
    out = append(out, encodeMemorySection()...)
    out = append(out, encodeGlobalSection(strings.next)...)
}

// ... export section, code section ...

if len(strings.entries) > 0 {
    out = append(out, encodeDataSection(strings)...)
}
Section ordering, again. Global (6) goes between memory (5) and export (7). If the validator rejects with "invalid section order", you've likely emitted globals after exports. The pattern in lesson 36 — emit memory before export, data after code — extends here naturally: emit globals immediately after memory.
Why strings.next is the right starting address. Your stringTable.add bumps next by 4 + len(value) for every literal added. So after collection, next is the byte index immediately after the last string's last byte. No alignment for now — when arrays of doubles arrive in a later lesson and 8-byte alignment matters, we'll round this up. Today's job is just "past the strings".

Step 4 — Test

The test asks wazero for the exported global and reads its current value. Add to end_to_end_test.go:

func TestEndToEnd_HeapPointer(t *testing.T) {
    src := `
        fn label(): string { return "hello"; }
    `
    ast, err := script.Parse(strings.NewReader(src))
    if err != nil { t.Fatal(err) }
    wasm, err := binary_wasm.CompileProgram(ast)
    if err != nil { t.Fatal(err) }

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)
    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    g := mod.ExportedGlobal("__heap_ptr")
    if g == nil { t.Fatalf("__heap_ptr not exported") }

    got := uint32(g.Get())
    // "hello" = 4 length bytes + 5 ASCII bytes = 9 bytes at offset 0.
    // Heap starts immediately after.
    if got != 9 {
        t.Fatalf("__heap_ptr = %d, want 9", got)
    }
}

func TestEndToEnd_HeapPointerMultipleStrings(t *testing.T) {
    src := `
        fn one(): string { return "hi"; }
        fn two(): string { return "world"; }
    `
    // "hi"    → 4 + 2 = 6 bytes at offset 0..5
    // "world" → 4 + 5 = 9 bytes at offset 6..14
    // heap starts at 15
    ast, _ := script.Parse(strings.NewReader(src))
    wasm, _ := binary_wasm.CompileProgram(ast)

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)
    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    got := uint32(mod.ExportedGlobal("__heap_ptr").Get())
    if got != 15 {
        t.Fatalf("__heap_ptr = %d, want 15", got)
    }
}

Run:

go test ./internal/script/compiler/binary/... -v
Mutability matters for the test. If you mark the global as immutable (0x00) instead of mutable (0x01), mod.ExportedGlobal returns a non-mutable handle, which is fine for `Get` but disallows future allocator writes. Mutable from the start — the allocator will need to write to it in lesson 40.

The Architectural Step You Just Took

Until now your WASM modules had only function-local mutable state — params and locals, scoped to a single body. With globals, the module gains module-level mutable state that survives between calls. That's the structural prerequisite for any allocator, garbage collector, instance counter, lazy-init cache, or any other "remembers something between calls" pattern.

The next lesson uses this for the cheapest possible payoff: a bump allocator inline at every array-construction site.

What's Next

  • Inline bump allocator and array literals. An ArrayLiteral compiles to: read heapPtr, save it locally, advance heapPtr by 4 + n*elemSize, store the length at the base, store each element after. A small but complete piece of dynamic memory management.
  • Array access and length. Once arrays exist, arr.len() is i32.load at the base (same shape as s.len() from lesson 37). arr[i] is base + 4 + i*elemSize followed by (i64|f64|i32).load.
  • Alignment. Today we use raw strings.next with no padding. Once arrays of doubles arrive, the heap start should round up to 8-byte alignment; otherwise f64.load/store takes the slow path on most engines. Easy fix — (strings.next + 7) & ~7 — to land when it actually matters.
