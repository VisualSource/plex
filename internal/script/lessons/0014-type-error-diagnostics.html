Lesson 14 — Type Error Diagnostics: Making Errors That Help

typecheckerdiagnosticserror design

Your typechecker can now catch real mistakes. But right now, when it does, it says this:

1:36-48:1 | was expecting return to be script.TypeKind but was given script.TypeKind

Both sides say the same thing. The error is technically correct — there is a mismatch — but it gives you zero information about what the actual types are. This is one of the most underrated problems in compiler construction: an error that doesn't help you fix anything is worse than no error.

In this lesson you will:

  • Understand why the message is broken (a Go format verb trap)
  • Add a String() method to your Type struct for rich type descriptions
  • Learn what makes a good type error message (and what makes a bad one)
  • Fix two cascading-error patterns that produce misleading second errors

1. The Bug: %T vs %v

Go's fmt package has several format verbs for printing values. Three are easy to confuse:

VerbWhat it printsExample for TypeKind_Float
%TThe Go type name of the variablescript.TypeKind
%vThe default value (calls String() if available)TypeKind_Float
%sThe string representation (calls String())TypeKind_Float

%T is for introspection — "what Go type is this variable?". When you write %T for a script.TypeKind, every single value of that type prints as script.TypeKind, because they all have the same Go type. The actual value is irrelevant to %T.

The fix in typecheck.go is to change %T → %s:

❌ Before

fmt.Errorf(
  "was expecting return to be %T but was given %T",
  c.expectedReturn.Kind,
  rt.Kind,
)

✅ After

fmt.Errorf(
  "was expecting return to be %s but was given %s",
  c.expectedReturn.Kind,
  rt.Kind,
)

This already works because TypeKind has a String() method. But we can do better.

2. The Type Struct Needs a String()

Your TypeKind.String() only describes the kind, not the full type. Consider what a user sees if their error involves an array or a nullable struct:

was expecting return to be TypeKind_Array but was given TypeKind_Struct

Which array? Which struct? The Type struct holds all that information — but there's no String() on it, so it never gets used in error messages.

Here's the gap. Your Type struct in types.go:

type Type struct {
    Kind     TypeKind  // e.g. TypeKind_Array
    Element  *Type     // set when Kind == TypeKind_Array
    Struct   string    // set when Kind == TypeKind_Struct
    Nullable bool
}

A good String() should produce human-readable output that mirrors what a user would write in plex source code:

Type valueGood String()
Kind: Intint
Kind: Floatfloat
Kind: Array, Element: {Kind: Int}int[]
Kind: Struct, Struct: "Point"Point
Kind: Array, Element: {Kind: Struct, Struct: "Point"}, Nullable: truePoint[]?
Principle: Error messages should use the language's own syntax, not the compiler's internal representation. int[] is what a plex developer wrote and recognizes — TypeKind_Array(element=TypeKind_Int) is noise.

3. Cascading Errors

When a typechecker hits one error, it often produces several more from the same root cause. This makes errors hard to read. Here's the pattern you have now:

fn main(){
    let point = Point(1, 1);  // ❌ int literal given where float expected
    point.getX();              // ❌ "unknown identifier: point"
}

The second error is fake. point is declared — but the init failed type-checking, so the variable was stored with a nil type. When the checker later looks it up, it gets nil and reports "unknown identifier".

This is called a cascading error. Rust's compiler, Elm's compiler, and the TypeScript compiler all invest heavily in suppressing these, because they obscure the real problem.

The underlying rule: if you store nil into a scope entry, any later use of that name will fail with a misleading message.

There are two common fixes:

  1. Sentinel type: Instead of nil, store a special TypeKind_Unknown type. Then propagate it silently — if either operand is Unknown, return Unknown without reporting a new error. (Your TypeKind_Unknown constant already exists for exactly this reason.)
  2. Early bail-out: After a type error in a statement, skip checking downstream statements that depend on it.

The sentinel approach is generally better because it keeps the checker running and can surface multiple independent errors in one pass.

4. What Makes a Good Type Error?

This is an active area of compiler research. Some principles from real compilers:

  • Show both sides: "expected X, got Y" is good. Missing either side is not.
  • Use source types: Write the types in the language's own syntax, not the implementation's internal names.
  • Point to the source: You're already doing this with positions in your TypeError.
  • First error wins: When cascading is a risk, report fewer errors, not more. The real error is usually the first one.
  • Don't editorialize: "was expecting X" is fine. "You made a mistake: was expecting X" is noise.

Rust and Elm are famous for their error messages. Elm in particular pioneered the idea that "compiler errors for humans" is a product feature worth investing in.

5. The Int/Float Literal Problem

The TestStructImpl test fails because it writes Point(1, 1), but Point expects float fields. Your checker infers 1 as TypeKind_Int, and 1.0 as TypeKind_Float. They don't match.

This is a real design question. Languages take different approaches:

LanguageApproach
GoUntyped numeric constants — 1 can satisfy float64 at the call site. Typed at the point of use.
RustType inference — the compiler infers the numeric type from context, but you must be explicit if inference can't resolve it.
TypeScriptStructural subtyping — numbers are just number. No int vs float distinction.
CImplicit widening — int silently promotes to double.
plex (now)Strict literal typing — 1 is always int, 1.0 is always float. No implicit conversion.

For plex targeting WebAssembly, strict literal typing is actually the right call: i32.const 1 and f64.const 1.0 are different instructions, and requiring the programmer to be explicit keeps the mapping from plex types to WAT types unambiguous. The fix for the test is to write Point(1.0, 1.0).

Design note: Your type system is "strict structural" — no implicit numeric widening, equality by structure. This is a conscious choice, not an oversight. It makes the compiler simpler and the compiler output predictable.

Check Your Understanding

1. You write fmt.Errorf("got type %T", myTypeKind). What does it print?

✅ The Go type name: script.TypeKind. %T prints the type of the variable, not its value. It ignores any String() method.

2. Why should you store TypeKind_Unknown instead of nil when a type-check fails?

✅ Both. A nil pointer causes panics if unchecked. And by propagating Unknown silently, you prevent fake "unknown identifier" errors that confuse the user about what actually went wrong.

3. Why does plex require 1.0 instead of allowing 1 where a float is expected?

✅ The WAT instruction set has separate i32.const, i64.const, f32.const, f64.const opcodes. The type must be resolved before code generation so the compiler knows which opcode to emit. Requiring explicit literals keeps that resolution trivial.
