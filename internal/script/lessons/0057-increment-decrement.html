Lesson 57 – Increment and Decrement (++ / --)

Previous: Lesson 56 – Logical NOT

x++ and x-- are already tokenized and parsed in plex — the parser produces a UnaryExpression{Operator: TokenType_Incrment, Postfix: true}. They have no codegen yet; the binary backend will error. This lesson adds them and introduces two new concepts: lvalues and local.tee.

What Is an Lvalue?

Every expression in a compiler is either an rvalue (a value you can read) or an lvalue (a storage location you can also write to). Addition, function calls, and literals are rvalues. Local variables, array slots, and struct fields are lvalues — they have an identity beyond their value.

++ and -- are read-modify-write operators: they read the current value, compute a new one, and write it back. This requires an lvalue operand. The type alone is not enough: 

x++        // ✓ — x is an lvalue (a named local)
(x + 1)++  // ✗ — x+1 is an rvalue; there is no location to write back to
arr[i]++   // not implemented here — requires array-write logic

In plex's binary backend, lvalue restriction means: the operand of ++/-- must be an *script.Identifier so the compiler can look up the local index and emit both a read and a write.

Lvalues in other compilers. C formalises lvalue rules in the language spec. LLVM SSA uses alloca for stack slots that can be written. WASM locals are the closest WASM equivalent to an lvalue — they have a persistent slot index you can both get and set.

The WASM Pattern: local.tee

local.tee n (opcode 0x22) writes the top-of-stack value into local n without consuming it. It's the read+write operation in one instruction:

; x++ on a local at index 2 (i64 type) local.get 2 stack: [x] i64.const 1 stack: [x, 1] i64.add stack: [x+1] local.tee 2 stack: [x+1] — also stores x+1 into local 2

After this sequence, local 2 holds x+1, and the stack holds x+1 — the new value is left for any parent expression to consume. If the statement discards the result (the drop in the Block handler fires), that's fine too.

These are pre-increment semantics, not postfix. The value left on the stack is the new value (x+1), not the original. True C-style postfix x++ would return the original: local.get x, then a second local to save the original, then compute and write x+1, then push the saved original. For statement use — which is by far the most common — the difference is invisible. We implement the simpler version and note the semantic shortcut.

Implementation: body.go

In the UnaryExpression case in body.go, add handling between the ! block and the - block: 

if n.Operator == script.TokenType_Incrment || n.Operator == script.TokenType_Decrement {
    id, ok := n.Operand.(*script.Identifier)
    if !ok {
        return fmt.Errorf("++ and -- require an identifier operand")
    }
    idx, ok := b.locals[id.Value]
    if !ok {
        return fmt.Errorf("unknown identifier %s", id.Value)
    }
    t := n.Operand.GetType()
    if t == nil {
        return fmt.Errorf("no type on operand of ++/--")
    }

    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, idx)

    switch t.Kind {
    case script.TypeKind_I64, script.TypeKind_Int:
        b.buf = append(b.buf, OpI64Const)
        b.buf = AppendSLEB128(b.buf, 1)
        if n.Operator == script.TokenType_Incrment {
            b.buf = append(b.buf, OpI64Add)
        } else {
            b.buf = append(b.buf, OpI64Sub)
        }
    case script.TypeKind_I32:
        b.buf = append(b.buf, OpI32Const, 1)
        if n.Operator == script.TokenType_Incrment {
            b.buf = append(b.buf, OpI32Add)
        } else {
            b.buf = append(b.buf, OpI32Sub)
        }
    default:
        return fmt.Errorf("++/-- not supported for type %s", t)
    }

    b.buf = append(b.buf, OpLocalTee)
    b.buf = AppendULEB128(b.buf, idx)
    return nil
}

Why No Typechecker Change Is Needed

The current typechecker propagates the operand's type unchanged for all UnaryExpression nodes. For x++, the type of the expression is the type of x — which is exactly what propagation gives. No change needed in typecheck.go.

The lvalue restriction (operand must be an Identifier) is enforced at codegen time rather than at typechecking time. This is a deliberate simplification — a production compiler would add an lvalue-checking pass after parsing so that (x+1)++ gives a clear error message rather than a codegen panic.

The collectLocals Gap

body.go's collectLocals walks the AST to pre-declare all local variables. It currently traverses VariableDeclaration, Block, WhileStatement, and IfStatement. It does not traverse UnaryExpression — but that's fine here: x++ doesn't introduce a new local, it mutates an existing one.

Lvalue Literacy

Why does (x + 1)++ fail even if x is an i64?

x+1 computes a temporary value on the WASM stack. There is no local index to write back to — the value exists only in the moment. An lvalue is a location; an rvalue is a value without a backing location.

What does local.tee n do that local.set n does not?

local.tee writes the top-of-stack to a local without consuming it. local.set pops and discards. The "tee" name is from the Unix tee command — split one stream to two destinations.

The implementation above gives x++ the semantics of returning the new value. What extra instruction sequence would true C-style postfix need?

True postfix: local.get x (save original), local.tee tmp, i64.const 1, i64.add, local.set x, local.get tmp. The saved original is what the expression evaluates to. This requires a synthetic local — the same addSyntheticLocal pattern used in string concat and array ops.

Where in the WASM instruction sequence does the lvalue restriction actually matter?

local.tee takes a local index. For an Identifier you can look up b.locals[name]. For an arbitrary expression (x+1, a function call, a literal) there is no index to provide.

func TestEndToEnd_Increment(t *testing.T) {
    src := `
        export fn count_up(): int {
            let i: int = 0;
            i++;
            i++;
            i++;
            return i;    // 3
        }
        export fn count_in_loop(n: i64): i64 {
            let i: i64 = 0;
            while i < n { i++; }
            return i;    // n
        }
    `
    runOne(t, src, "count_up", nil, 3)
    runOne(t, src, "count_in_loop", []uint64{10}, 10)
}

func TestEndToEnd_Decrement(t *testing.T) {
    src := `
        export fn count_down(n: i64): i64 {
            let i: i64 = n;
            while i > 0 { i--; }
            return i;    // 0
        }
    `
    runOne(t, src, "count_down", []uint64{5}, 0)
}

The count_in_loop case is the key one: it replaces the i = i + 1; pattern used in many earlier tests with the idiomatic i++. If the result is correct, the read-modify-write sequence works.

Going Further

To support arr[i]++ or p.x++, you'd need array-write or struct-write logic alongside the read. The pattern is the same (read, compute, write back), but you'd use local.tee on a synthetic pointer local to avoid walking the address expression twice. That's left as a future extension.
