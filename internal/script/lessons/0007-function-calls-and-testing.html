Lesson 7 – Function Calls and Testing the Compiler

Your compiler can already produce valid WAT for arithmetic, control flow, and function declarations. But it still can't call a function from another function — the most fundamental building block of any real program. That's what this lesson covers.

We'll also write the first compiler test so you can verify the output without manually inspecting a .wat file every time.

1. The WASM call instruction

WebAssembly's calling convention is completely stack-based. To call a function you:

  1. Push each argument onto the stack (in order, left to right).
  2. Emit call $funcname. The runtime pops the arguments, runs the function, and pushes the return value (if any) back onto the stack.

So calling add(1.0, 2.0) compiles to:

f64.const 1
f64.const 2
call $add     ;; pops 2 args, pushes result

That's it. Arguments are evaluated in order, and the stack does the rest. This is postorder traversal again — same rule that made binary expressions work: emit the operands first, then the operation.

Why the order matters

WASM is strictly typed and strictly ordered. If you emit arguments in the wrong order, the function gets the wrong values. If you emit the wrong number, the validator rejects the module. Your compiler already enforces this naturally by compiling args in a loop — left to right is the correct order for WASM.

2. What a FunctionCall node looks like

From internal/script/ast_nodes.go:

type FunctionCall struct {
    Callee AstNode   // usually an *Identifier (the function name)
    Args   []AstNode // the argument expressions
}

The callee is an AstNode — not just a string — because plex could eventually support first-class functions (f(g)(x)). For now, every direct call has a plain *Identifier as the callee. Use a type switch to extract the name and fall through to an error for anything you don't handle yet.

3. Implementation

Task A — Add *script.FunctionCall to the compiler

In internal/script/compiler/compiler.go, add a new case to the Compile switch. The logic is:

  1. Loop over n.Args and Compile each one (pushes args onto the stack).
  2. Type-switch on n.Callee. For *script.Identifier, emit call $name. For anything else, return an error.

Sketch:

case *script.FunctionCall:
    for _, arg := range n.Args {
        if err := c.Compile(arg); err != nil {
            return err
        }
    }
    switch callee := n.Callee.(type) {
    case *script.Identifier:
        c.emit("call $" + callee.Value)
    default:
        return fmt.Errorf("compile: unsupported callee %T", n.Callee)
    }

Test it by hand first

Update cmd/plexc/test.plex:

fn add(a: int, b: int): int {
    return a + b;
}

fn double(x: int): int {
    return add(x, x);
}

Run go run ./cmd/plexc/ -file cmd/plexc/test.plex and look at the generated test.wat. You should see a call $add inside double's body.

4. Testing the compiler in Go

Manual inspection doesn't scale. Let's write a proper test.

A compiler test has a different shape than an interpreter test:

  • Interpreter test: run the program, assert on the output value.
  • Compiler test: compile the program, assert on the generated text.

Both are valid. For a WAT compiler, checking the output string is straightforward and reliable — if the WAT is structurally wrong, wat2wasm will reject it anyway.

Task B — Write internal/script/compiler/compiler_test.go

Create the test file with one test that compiles a plex program and checks the WAT output contains the expected instructions. Use strings.Contains for the checks — you don't want to assert exact whitespace.

package compiler_test

import (
    "strings"
    "testing"

    "github.com/VisualSource/plex/internal/script"
    "github.com/VisualSource/plex/internal/script/compiler"
)

func TestCompileFunctionCall(t *testing.T) {
    src := `
        fn add(a: int, b: int): int { return a + b; }
        fn double(x: int): int { return add(x, x); }
    `
    tokens, err := script.NewTokenizer(strings.NewReader(src)).Tokenize()
    if err != nil {
        t.Fatal(err)
    }
    ast, err := script.NewParser(tokens).Parse()
    if err != nil {
        t.Fatal(err)
    }

    wat, err := compiler.CompileProgram(ast.(*script.Program))
    if err != nil {
        t.Fatal(err)
    }

    checks := []string{
        "(func $add",
        "(func $double",
        "call $add",
        "(export \"add\"",
        "(export \"double\"",
        "f64.add",
    }
    for _, want := range checks {
        if !strings.Contains(wat, want) {
            t.Errorf("WAT missing %q\n\nGot:\n%s", want, wat)
        }
    }
}

Run it with go test ./internal/script/compiler/.

5. Running the WASM for real

You have wat2wasm installed, and Node.js supports WASM natively. That means you can run your compiled code right now without adding any Go dependency.

Step 1 — compile to binary:

wat2wasm test.wat -o test.wasm

Step 2 — run with Node.js. Create cmd/plexc/run.mjs:

import { readFileSync } from "fs";

const bytes = readFileSync("test.wasm");
const { instance } = await WebAssembly.instantiate(bytes);

console.log(instance.exports.add(3, 4));    // expect 7
console.log(instance.exports.double(5));    // expect 10

node cmd/plexc/run.mjs

Why is Node happy with f64 params even though we pass integers?

JavaScript automatically coerces numbers to the right WASM type when calling exports. 3 becomes 3.0 (f64). The result comes back as a JS number, which prints without a decimal point if it's whole. No special handling needed on the JS side.

6. What you've built

Your compiler now has a complete pipeline:

plex source
    → tokenizer
    → parser (AST)
    → compiler (WAT text)
    → wat2wasm (WASM binary)
    → WebAssembly runtime (executed)

This is the same pipeline used by production compilers — the stages are identical, just with more complexity in each one. You've closed the loop from source text to running machine instructions.
