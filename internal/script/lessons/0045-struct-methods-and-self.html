Lesson 45 – Struct Methods and the Implicit Self

Goal: compile p.distance_squared() to a call into a struct method. Most of the work is already done — the surprise of this lesson is how little new code you need.

Files you'll touch: body.go · end_to_end_test.go

The Surprise

Read these three facts and notice what they imply:

  1. helpers.go:32-65 — collectSignatures already iterates *script.StructImplStatement, calls signatureOf with an implName, and emits one funcSig per method.
  2. helpers.go:67-93 — signatureOf with a non-empty implName:
    • Prepends ValI32 (the implicit self: i32) to the params byte vector.
    • Mangles the function name to __StructName__methodName.
    • Sets isMethod = true.
  3. body.go:27-38 — newBodyEncoder already inspects sig.isMethod and assigns b.locals["self"] = 0 before walking the params.

The combined effect: methods are already being compiled as fully-formed WASM functions. They have their proper signatures ((i32, params...) → result), they have self as local 0, their bodies are walked by the same encoder that walks any function. Inside a method body, self is just a local; self.x is the bare MemberAccess case from lesson 44.

The only missing piece is the call site. When source says p.distance_squared(), the parser produces:

FunctionCall ├── Callee: MemberAccess │ ├── Object: Identifier "p" ; type: Struct{Point} │ └── Field: "distance_squared" └── Args: []

And the binary backend's FunctionCall.Callee = MemberAccess arm currently only handles String.len() and Array.len(). The struct case errors with "method calls on Struct not supported".

This is what "infrastructure pays off" looks like. Every previous lesson added a tiny piece: signature mangling (collectSignatures), self in scope (newBodyEncoder), field access (lesson 44). None of those changes were specifically about methods. But each one was *method-shaped* — designed to compose. Today you write maybe 15 lines and everything snaps together.

The Call-Site Codegen

Method dispatch is "function call with a receiver argument prepended". The bytecode shape:

; p.distance_squared(other) for some method (self: i32, other: i32) → f64 walk(p) ; → i32 self stack: [self] walk(other) ; → i32 other stack: [self, other] 10 idx ; call idx (mangled "__Point__distance_squared")

The order matches the signature: implicit self first, then explicit args. No new opcode, no allocator trick — just OpCall with the mangled-name funcidx.

Implementation

Step 1 — Add a struct arm under MemberAccess

In body.go, find the case *script.MemberAccess: branch inside FunctionCall's callee type-switch. After the TypeKind_String and TypeKind_Array cases, add:

case script.TypeKind_Struct:
    // Method dispatch: push receiver, then args, then call __Struct__method.
    if err := b.walk(callee.Object); err != nil {
        return err
    }
    for _, arg := range n.Args {
        if err := b.walk(arg); err != nil {
            return err
        }
    }
    mangled := fmt.Sprintf("__%s__%s", objType.Struct, callee.Field)
    idx, ok := b.funcIndices[mangled]
    if !ok {
        return fmt.Errorf("struct %s has no method %s", objType.Struct, callee.Field)
    }
    b.buf = append(b.buf, OpCall)
    b.buf = AppendULEB128(b.buf, idx)
    return nil
Watch the args loop. The existing FunctionCall case currently walks args at the top of the arm (before the type-switch on callee). For the struct-method dispatch you need the args walked after the receiver — which means you either need a different code path (the one above, which walks args itself), or you have to be careful that the top-of-arm loop doesn't double-walk. Check your FunctionCall case carefully: if args are walked once before the type switch, remove the inner loop in the struct arm above. Conversely, if you delete the top loop, every callee branch needs to walk args itself. The clean shape is "each branch handles its own argument walking".

Step 2 — Test

func TestEndToEnd_StructMethods(t *testing.T) {
    src := `
        struct Point {
            x: f64;
            y: f64;
        }
        impl Point {
            fn distance_squared(): f64 {
                return self.x * self.x + self.y * self.y;
            }
            fn scale(factor: f64): f64 {
                return self.x * factor + self.y * factor;
            }
        }
        fn d_sq(): f64 {
            let p = Point(3.0, 4.0);
            return p.distance_squared();  // 9 + 16 = 25
        }
        fn scaled(): f64 {
            let p = Point(2.0, 3.0);
            return p.scale(10.0);          // 20 + 30 = 50
        }
    `
    runOne(t, src, "d_sq",   nil, api.EncodeF64(25.0))
    runOne(t, src, "scaled", nil, api.EncodeF64(50.0))
}

What You Just Pulled Together

Five distinct subsystems collaborated to produce p.distance_squared():

SubsystemDid what
ParserRecognised impl Point { fn ... } as StructImplStatement; p.method() as FunctionCall{Callee: MemberAccess}.
TypecheckerTagged self with the struct's type inside the method's scope; tagged the call expression with the method's return type.
collectSignaturesMangled the method name to __Point__distance_squared, prepended i32 self-param, added to the function vec.
newBodyEncoderRegistered self as local 0 when sig.isMethod was true.
Today's codeLooked up the mangled name in funcIndices, emitted receiver-then-args-then-call.
This is one of the most satisfying shapes in compiler engineering. A feature that seems like it needs work across every stage instead turns out to be already-implemented except for one call-site arm. The previous lessons did the hard work; today just connects the wire. When a feature lands this small, it usually means previous design decisions were good — the abstractions were carved at the right joints.

Knowledge Check

Quiz

1. Why is self at local index 0 inside every method body?

2. The method's callee is a MemberAccess, but the compiled call uses an absolute funcidx via OpCall (0x10). Why not a more dynamic dispatch?

3. self.x inside a method body works through which lesson's code?

4. Why is __Point__distance_squared name-mangled this way, instead of using e.g. a struct-method table or a separate namespace?

What's Next

  • Methods that mutate the struct. fn move(dx: f64) { self.x = self.x + dx; } — should work today since self is an i32 pointer and self.x = ... is just a `MemberAssignment` lesson 44 already handles. Write a test to confirm.
  • Methods calling methods. self.helper() dispatches the same way as p.helper() — the receiver is just whichever expression is on the left of the dot. Test it with a chained call.
  • Factor the heap-allocator pattern. Four sites now (strings, arrays, structs, plus any future closure environments). When you find a fourth-shape variant, pull (b *bodyEncoder).emitHeapAlloc(size uint32) (tmp uint32) into a helper.
  • Bounds-check elimination, alignment padding, sorting algorithms. Backlog items from earlier lessons. All compile-time-only work; none changes the language surface.
