Lesson 34 – Short-Circuit &&/|| and If-as-Expression

Goal: make || and && truly lazy. Today, false && (10 / 0 == 0) would trap your program even though the answer is provably false. By the end, the RHS only runs when it has to.

Files you'll touch: body.go · opcodes.go · end_to_end_test.go

The Bug You Already Wrote

Look at how && and || compile right now. The *script.BinaryExpression case in body.go walks both sides, then dispatches an opcode. For AND, that opcode is i32.and; for OR it's i32.or — both bitwise, both eager:

; a || b — current encoding walk(a) ; → i32 (0 or 1) walk(b) ; ← evaluated even if a was true! 72 ; i32.or → i32 (0 or 1)

Add this test to end_to_end_test.go — it should pass after today's work:

func TestEndToEnd_ShortCircuitOr(t *testing.T) {
    src := `
        fn safe_or(a: bool, b: i64): bool {
            return a || (10 / b) > 0;
        }
    `
    // a=true: RHS must not be evaluated, even though 10/0 would trap
    runOne(t, src, "safe_or", []uint64{1, 0}, 1)

    // a=false: RHS runs. 10/5 = 2, 2 > 0 = true
    runOne(t, src, "safe_or", []uint64{0, 5}, 1)

    // a=false: RHS runs. 10/100 = 0, 0 > 0 = false
    runOne(t, src, "safe_or", []uint64{0, 100}, 0)
}

Run it now:

go test ./internal/script/compiler/binary/... -run TestEndToEnd_ShortCircuitOr -v

You'll see the a=true, b=0 case panic the runtime: i64.div_s traps on division by zero. Wazero will report something like wasm error: integer divide by zero. The fact that a was already true makes no difference — the current compiler evaluates both sides unconditionally.

Why this matters beyond traps. Once plex grows side effects — prints, mutation, system calls — eagerness will become silently wrong, not loudly wrong. Today's div-by-zero is a free test oracle: a divergence between eager and lazy semantics that you can observe right now, without needing any new runtime features.

The WASM Tool for the Job: if as an Expression

You already use if as a statement in lesson 30. It has a hidden second mode: when given a non-empty block type, the if instruction produces a value.

if as statement (you have this)

04 40       ; if <empty>
  ...        ; body pushes nothing
05          ; else
  ...
0B          ; end → stack unchanged

if as expression (today's new tool)

04 7F       ; if (result i32)
  ...        ; body must push 1 i32
05          ; else
  ...        ; else branch must also push 1 i32
0B          ; end → stack +1 i32

The byte 0x7F is the same one your types.go calls ValI32 — see types.go:6. Block types and value types share the encoding by design: block type is either 0x40 (empty), a single byte for a value type, or a positive type index for multi-result blocks (which we don't need).

Both branches must produce the result. The validator does not let one branch push and the other not. If you write if (result i32) ... else ... end, both ... arms must leave exactly one i32 on the stack. This is what makes the rewrite below balanced.

The Rewrite

Compile a && b and a || b using if as an expression:

a && b

walk(a)
04 7F       ; if (result i32)
  walk(b)    ; result = b only if a
05          ; else
  41 00     ; i32.const 0
0B          ; end

a || b

walk(a)
04 7F       ; if (result i32)
  41 01     ; i32.const 1   (a was true)
05          ; else
  walk(b)    ; result = b only if !a
0B          ; end

Read both columns once and notice the symmetry: AND is "if true, then RHS, else false"; OR is "if true, then true, else RHS". The RHS appears in exactly the branch where it actually matters.

Implementation

Step 1 — Special-case in BinaryExpression

The current *script.BinaryExpression arm walks both sides before dispatching the opcode. For AND/OR we must not walk the right side first. Branch on the operator at the top of the case:

case *script.BinaryExpression:
    if n.Operator == script.TokenType_AND || n.Operator == script.TokenType_OR {
        return b.walkShortCircuit(n)
    }
    if err := b.walk(n.Left); err != nil { return err }
    if err := b.walk(n.Right); err != nil { return err }
    // ... unchanged ...

Step 2 — The helper

Add walkShortCircuit as a method on bodyEncoder. It opens an if (result i32), picks which side gets the constant short-circuit value, and emits end. Remember to bump blockDepth so any break/continue nested inside computes the right label depth:

func (b *bodyEncoder) walkShortCircuit(n *script.BinaryExpression) error {
    if err := b.walk(n.Left); err != nil {
        return err
    }
    b.buf = append(b.buf, OpIf, ValI32)
    b.blockDepth++

    if n.Operator == script.TokenType_AND {
        // a && b  →  if a then b else 0
        if err := b.walk(n.Right); err != nil {
            return err
        }
        b.buf = append(b.buf, OpElse)
        b.buf = append(b.buf, OpI32Const, 0)
    } else {
        // a || b  →  if a then 1 else b
        b.buf = append(b.buf, OpI32Const, 1)
        b.buf = append(b.buf, OpElse)
        if err := b.walk(n.Right); err != nil {
            return err
        }
    }

    b.buf = append(b.buf, OpEnd)
    b.blockDepth--
    return nil
}
Why blockDepth++/--? Same reason as the if-statement case from lesson 31: an if opens a label level. If a break or continue appears inside the short-circuited RHS (rare but possible), its emitted depth must account for the extra enclosing block. You already paid for this insight; you may as well honour it.

Step 4 — Symmetry test (optional but satisfying)

Add an AND counterpart so both directions are pinned:

func TestEndToEnd_ShortCircuitAnd(t *testing.T) {
    src := `
        fn safe_and(a: bool, b: i64): bool {
            return a && (10 / b) > 0;
        }
    `
    // a=false: short-circuit avoids the divide
    runOne(t, src, "safe_and", []uint64{0, 0}, 0)
    runOne(t, src, "safe_and", []uint64{1, 5},   1) // true && (10/5 > 0) = true
    runOne(t, src, "safe_and", []uint64{1, 100}, 0) // true && (10/100 > 0) = false
}

What You Quietly Unlocked

This lesson introduced the if-as-expression pattern, which is the bedrock of a lot more than short-circuit:

  • Ternaries (cond ? a : b) compile to the exact same shape — and plex already has a ternary statement in lesson 19 of the WAT backend.
  • Multi-result blocks (block type as type index) generalise this further — the foundation for returning tuples in a future plex.
  • Type-directed result encoding: the block-type byte will be ValI64 or ValF64 when the result is i64/f64 instead of bool. The current implementation hardcodes ValI32 because AND/OR is always bool — fine for now, but worth noticing it's a special case of a general pattern.

Knowledge Check

Quiz

2. What is the meaning of the second byte (0x7F) immediately after 0x04 in the encoding 04 7F ... 05 ... 0B?

3. What does the validator require about the else branch of if (result i32) ... else ... end?

4. Why does the helper bump blockDepth when emitting the if?

What's Next

  • Unary operators (!x, unary -x) — currently no *script.UnaryExpression case exists in body.go. The fixes are tiny: ! is i32.eqz (already in opcodes); unary minus on i64 is i64.const 0; (operand); i64.sub or for f64 the dedicated f64.neg.
  • Fill out comparisons — i32 is missing < > ≤ ≥ (only eq/ne today); f64 has no comparisons at all. Once they land, comparisons across all primitive types are uniform.
  • Linear memory — the gateway to strings, then arrays, then structs.
