Lesson 37 – String Length, i32.load, and the memarg Encoding

Goal: compile "hello".len() to 5. One opcode that already exists in your file (OpI32Load), one new opcode (OpI64ExtendI32S), and one new AST shape to walk (method-call-as-FunctionCall-over-MemberAccess).

Files you'll touch: opcodes.go · body.go · end_to_end_test.go

The Shape You're Compiling

In plex, s.len() is parsed as a FunctionCall whose Callee is a MemberAccess:

FunctionCall ├── Callee: MemberAccess │ ├── Object: Identifier "s" ; type: string │ └── Field: "len" └── Args: []

The typechecker already gives the whole expression the type Int (see typecheck.go:373-382), so the binary section will declare the return type as i64. The codegen just needs to produce an i64 on the stack.

Right now your encoder rejects this shape — see [body.go]'s FunctionCall case, which only handles *script.Identifier callees:

switch callee := n.Callee.(type) {
case *script.Identifier:
    // emits OpCall + funcidx
default:
    return fmt.Errorf("unsupported callee type %T", n.Callee)
}

Today you add a *script.MemberAccess arm.

What i32.load Actually Encodes

The pointer is already a plain i32 — you push it with walk(callee.Object), same path as a string literal. Then i32.load reads the first four bytes at that address. For your string layout, those four bytes are the length.

05@0
00@1
00@2
00@3
'h'@4
'e'@5
'l'@6
'l'@7
'o'@8

The boxed cells are what i32.load reads. The pointer on the stack was the address of the first one; after the load, the stack has the integer 5.

The memarg

Every WASM memory instruction (i32.load, i64.store, etc.) is followed by a memarg — two ULEB128s:

FieldEncodingMeaning
alignULEB128Alignment hint as an exponent. 0=byte, 1=halfword, 2=word, 3=doubleword.
offsetULEB128Constant offset added to the i32 popped from the stack.
Alignment is a hint, not a constraint. The validator rejects only the upper bound — align must not exceed the natural alignment of the access. For i32.load the natural alignment is 4 bytes, so align ≤ 2 (i.e., 2² = 4). Engines may use the hint to skip alignment checks for faster code paths. Mismatched alignment is a performance issue, never a correctness one — the actual address can be any byte.

For loading the length prefix you'll pass align=2 (the natural 4-byte alignment) and offset=0:

28 02 00 ; i32.load align=2 offset=0

Why the i32 → i64 extend?

The typechecker says s.len() is Int — which your types.go maps to i64. But i32.load pushes an i32. The validator counts types, so leaving an i32 on the stack when the caller expects i64 is rejected. WASM has explicit conversion opcodes:

OpcodeByteBehaviour
i64.extend_i32_s0xACSign-extend i32 to i64. Negative i32s become negative i64s.
i64.extend_i32_u0xADZero-extend i32 to i64. Treats the i32 as unsigned.

String lengths are non-negative, but the WAT compiler uses i64.extend_i32_s (see compiler.go:673) — match that for consistency. The two behaviours coincide for values that fit in 31 bits, which any sane string length will.

Implementation

Step 1 — Opcodes

Add to opcodes.go:

OpI64ExtendI32S byte = 0xAC

OpI32Load = 0x28 is already there from lesson 36.

Step 2 — Handle *script.MemberAccess in FunctionCall

Extend the type-switch on n.Callee in [body.go]'s FunctionCall arm. Walk the object first (it pushes the i32 pointer), then dispatch by the object's type + field:

switch callee := n.Callee.(type) {
case *script.Identifier:
    // ... existing direct-call logic ...
case *script.MemberAccess:
    objExpr, ok := callee.Object.(script.Expression)
    if !ok {
        return fmt.Errorf("member access object has no type")
    }
    objType := objExpr.GetType()
    if objType == nil {
        return fmt.Errorf("member access object type not set")
    }

    switch objType.Kind {
    case script.TypeKind_String:
        switch callee.Field {
        case "len":
            if err := b.walk(callee.Object); err != nil {
                return err
            }
            b.buf = append(b.buf, OpI32Load)
            b.buf = AppendULEB128(b.buf, 2) // align = 2 (natural i32 alignment)
            b.buf = AppendULEB128(b.buf, 0) // offset = 0
            b.buf = append(b.buf, OpI64ExtendI32S)
            return nil
        default:
            return fmt.Errorf("string has no method %s", callee.Field)
        }
    default:
        return fmt.Errorf("method calls on %s not supported", objType.Kind)
    }
default:
    return fmt.Errorf("unsupported callee type %T", n.Callee)
}
Args are ignored for len. The plex grammar still permits arguments syntactically, but len takes none. If you want to be strict, check len(n.Args) == 0 here. If you want to be lenient (and let the typechecker catch the mistake earlier), don't bother. The current typechecker doesn't enforce arity on builtin methods either — flag for a future cleanup pass.

func TestEndToEnd_StringLen(t *testing.T) {
    src := `

    runOne(t, src, "measure",       nil, 5)
    runOne(t, src, "measure_world", nil, 9)
    runOne(t, src, "measure_empty", nil, 0)
}

If your existing runOne takes []uint64 as the args slice, passing nil is valid (length 0). Run:

go test ./internal/script/compiler/binary/... -run TestEndToEnd_StringLen -v

Three subcases. The empty-string case is a nice corner — it tests that a length-prefix of 0 still loads correctly (0 bytes following).

What This Lesson Adds to Your Vocabulary

  • Method-call AST shape — FunctionCall.Callee can be a MemberAccess, not just an Identifier. This same arm will host array .len(), string indexing, and (eventually) struct method dispatch.
  • The memarg encoding — every memory op carries align+offset. The two ULEBs are easy to forget; mismatched encoding produces validator errors of the form "out of bounds memory access" or "alignment must not be larger than natural".
  • Sign-extension as type bridging — WASM has a small zoo of conversion opcodes (extend, wrap, trunc, convert). They're not "casts" in the language sense; they're how the stack machine reconciles types when one op produces a different width than the next consumes.
