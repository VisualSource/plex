Operator Precedence

Why 1 + 2 * 3 is a grammar problem, and how grammar solves it

The Problem You Already Have

Your current parser handles +. Now add * to parseExpression alongside it. What happens with 1 + 2 * 3?

BinaryExpression (+)
├── NumberLiteral(1)
└── BinaryExpression (*)
    ├── NumberLiteral(2)
    └── NumberLiteral(3)

That's wrong. * binds tighter than +, so the correct tree is:

BinaryExpression (+)
├── NumberLiteral(1)
└── BinaryExpression (*)
    ├── NumberLiteral(2)
    └── NumberLiteral(3)

Wait — those are the same tree. But what if we add both operators flat in parseExpression? The parser reads left-to-right, so 1 + 2 * 3 becomes (1 + 2) * 3 = 9 instead of 1 + (2 * 3) = 7. The grammar needs to encode precedence.

The Solution: Stratify By Precedence Level

The insight is that lower-precedence operators sit higher in the grammar. A rule can only delegate downward to higher-precedence rules, so higher-precedence operators always bind first.

The Rule
A grammar rule handles its own operators, then delegates to the rule one level higher in precedence for its operands. Lower precedence = higher up the grammar chain. Higher precedence = deeper in the call stack = binds tighter.

Here's plex's full expression grammar, ordered from lowest to highest precedence:

expression ::= assignment
assignment ::= IDENT "=" expression | ternary
ternary    ::= logicOr ( "?" expression ":" expression )?
logicOr   ::= logicAnd ( "||" logicAnd )*
logicAnd  ::= equality ( "&&" equality )*
equality  ::= comparison ( ( "==" | "!=" ) comparison )*
comparison ::= term ( ( "<" | ">" | "<=" | ">=" ) term )*
term       ::= factor ( ( "+" | "-" ) factor )*
factor     ::= unary ( ( "*" | "/" | "%" ) unary )*
unary      ::= ( "-" | "+" ) unary | primary
primary    ::= NUMBER | STRING | IDENT | "(" expression ")"

Tracing Through an Example

Let's trace 1 + 2 * 3 through the stratified grammar to see why it works.

parseExpression → parseTerm (handles +/-). parseTerm calls parseFactor for its left operand. parseFactor sees 1, not * or /, so it returns NumberLiteral(1) immediately. Back in parseTerm, peek is + — consume it. Now call parseFactor for the right operand. parseFactor sees 2, then peeks * — it loops, consuming 2 * 3 into BinaryExpression(*). That node returns to parseTerm as the right side of +. Result:

BinaryExpression (+)
├── NumberLiteral(1)
└── BinaryExpression (*)
    ├── NumberLiteral(2)
    └── NumberLiteral(3)

Correct. The call stack enforced the precedence — parseFactor ran deeper so it bound tighter.

The Go Implementation

Your existing parseExpression becomes parseTerm. Your parseTerm becomes parsePrimary. Then add the missing levels.

The pattern is mechanical — each level looks almost identical:

// factor ::= unary ( ("*" | "/" | "%") unary )*
func (p *Parser) parseFactor() (AstNode, error) {
    left, err := p.parseUnary()
    if err != nil {
        return nil, err
    }
    for {
        tt := p.peek().IsToken()
        if tt != TokenType_Star && tt != TokenType_Div && tt != TokenType_Mod {
            break
        }
        op := p.advance()
        right, err := p.parseUnary()
        if err != nil {
            return nil, err
        }
        start, _ := left.Range()
        _, end := right.Range()
        left = &BinaryExpression{Start: start, End: end, Left: left, Right: right, Operator: op.IsToken()}
    }
    return left, nil
}

// unary ::= ("-" | "+") unary | primary
func (p *Parser) parseUnary() (AstNode, error) {
    tt := p.peek().IsToken()
    if tt == TokenType_Minus || tt == TokenType_Plus {
        op := p.advance()
        operand, err := p.parseUnary() // right-recursive for chains: --x
        if err != nil {
            return nil, err
        }
        start, _ := op.Range()
        _, end := operand.Range()
        return &UnaryExpression{Start: start, End: end, Operator: op.IsToken(), Operand: operand}, nil
    }
    return p.parsePrimary()
}

The existing UnaryExpression in ast_nodes.go has no fields beyond position. You'll need to add Operator TokenType and Operand AstNode fields, plus a Range() method.

Assignment: right-associative

Assignment is interesting — a = b = 1 should parse as a = (b = 1), not (a = b) = 1. That means it's right-associative. The grammar handles this naturally: instead of a * loop (left-associative), use a single right-recursive call:

// assignment ::= IDENT "=" expression | ternary
func (p *Parser) parseAssignment() (AstNode, error) {
    // try IDENT "=" — look two tokens ahead
    if p.peek().IsToken() == TokenType_Ident && p.peekN(1).IsToken() == TokenType_Equal {
        name := p.advance().(*ValueToken)
        p.advance() // consume "="
        value, err := p.parseExpression() // right-recursive
        if err != nil {
            return nil, err
        }
        _, end := value.Range()
        return &AssignmentExpression{Start: name.Start, End: end, Name: name.Value, Value: value}, nil
    }
    return p.parseTernary()
}

You'll also need a peekN(n int) helper that returns the token n positions ahead without consuming anything.
