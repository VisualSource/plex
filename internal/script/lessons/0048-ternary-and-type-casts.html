Lesson 48 – Ternary Expressions and Type Casts

Previous: Lesson 47 – Arrays of Structs

The binary backend now handles structs, arrays, strings, methods, and all control flow. Two expression forms are still missing: the ternary (cond ? a : b) and the type cast (x as f64). Neither requires new memory tricks. They're both single opcode-sequence changes — but each introduces a concept that doesn't exist anywhere else in the backend yet.

Part 1 — The Ternary: if as an Expression

In the text backend (lesson 19) a ternary compiles to a WASM if with a result type: 

;; cond ? a : b  where result type is i64
local.get $cond
if (result i64)
  ;; push a
else
  ;; push b
end

The text form makes it look special with (result i64), but in the binary encoding it's just the block type byte that changes.

Block type bytes

Every structured control instruction (if, block, loop) takes one byte immediately after its opcode to describe the stack signature:

ByteMeaning
0x40BlockTypeEmpty — takes nothing, leaves nothing (already in opcodes.go)
0x7Ftakes nothing, leaves one i32 on the stack
0x7Etakes nothing, leaves one i64 on the stack
0x7Ctakes nothing, leaves one f64 on the stack

You already have these as ValI32, ValI64, ValF64 in types.go, and a helper valType(t *script.Type) byte that maps a plex type to the right byte.

Key insight: Every block type byte that represents a value type is the same byte as that type's WASM encoding (0x7F = i32, 0x7E = i64…). The 0x40 empty type is the odd one out — it sits in the same byte slot but means "nothing" rather than a value type. There is no ambiguity because 0x40 is not a legal value type.

Encoding plan for ternary

The sequence to emit for cond ? trueExpr : falseExpr:

walk(condition) → i32 on stack (all conditions are bool/i32) 0x04 valType(result) → OpIf + result type (not 0x40!) walk(trueExpr) → value on stack 0x05 → OpElse walk(falseExpr) → value on stack 0x0B → OpEnd — leaves exactly one value of result type

Notice that blockDepth does not need to change here — ternary is an expression, not a statement. The depth tracking matters for break/continue label resolution; since a ternary cannot contain a break, no adjustment is needed.

Part 2 — Type Casts: Numeric Conversion Opcodes

Plex's as keyword (x as f64) maps to WASM's numeric conversion instructions. These are single-byte opcodes that consume one value and produce another of a different type.

The conversion table

FromToWASM instructionByteStatus
i64i32i32.wrap_i640xA7Already in opcodes.go
i32i64i64.extend_i32_s0xACAlready in opcodes.go
i64f64f64.convert_i64_s0xB9Missing — add this
i32f64f64.convert_i32_s0xB7Missing — add this
f64i64i64.trunc_f64_s0xB0Missing — add this
f64i32i32.trunc_f64_s0xAAMissing — add this

The naming pattern reveals the design: i64.trunc_f64_s means "produce an i64 by truncating an f64 signed." The destination type is the prefix; the source and rounding mode follow.

Why trunc? WASM doesn't have a "round to nearest" float-to-int. All float→integer conversions truncate toward zero (C-style cast semantics). If the float is out of range or NaN, the instruction traps. There are saturating variants (i64.trunc_sat_f64_s) that clamp instead of trapping, but plex uses the trapping form.

Type normalisation

Plex has aliases: int = i64, float = f64. Before looking up the conversion opcode, normalise both sides so that int as f64 and i64 as f64 hit the same table entry. 

func normKind(k script.TypeKind) script.TypeKind {
    switch k {
    case script.TypeKind_Int:   return script.TypeKind_I64
    case script.TypeKind_Float: return script.TypeKind_F64
    default:                   return k
    }
}

A same-type cast is a no-op: emit nothing. This happens when the typechecker inserts an implicit coercion that the binary encoder doesn't need (or when the user writes x as int where x is already int).

Implementation Task

Task — four additions, two new cases

1. opcodes.go — add the four missing constants:

OpF64ConvertI64S byte = 0xB9
OpF64ConvertI32S byte = 0xB7
OpI64TruncF64S   byte = 0xB0
OpI32TruncF64S   byte = 0xAA

2. opcodes.go — add a castOpcode helper:

func castOpcode(from, to *script.Type) (byte, bool) {
    fk := normKind(from.Kind)
    tk := normKind(to.Kind)
    if fk == tk {
        return 0, true  // no-op, same type after normalisation
    }
    type pair struct{ f, t script.TypeKind }
    table := map[pair]byte{
        {script.TypeKind_I64, script.TypeKind_I32}: OpI32WrapI64,
        {script.TypeKind_I32, script.TypeKind_I64}: OpI64ExtendI32S,
        {script.TypeKind_I64, script.TypeKind_F64}: OpF64ConvertI64S,
        {script.TypeKind_I32, script.TypeKind_F64}: OpF64ConvertI32S,
        {script.TypeKind_F64, script.TypeKind_I64}: OpI64TruncF64S,
        {script.TypeKind_F64, script.TypeKind_I32}: OpI32TruncF64S,
    }
    op, ok := table[pair{fk, tk}]
    return op, ok
}

3. body.go — add the ternary case (inside walk):

case *script.TernaryExpression:
    t := n.GetType()
    if t == nil {
        return fmt.Errorf("ternary: no type")
    }
    if err := b.walk(n.Condition); err != nil { return err }
    b.buf = append(b.buf, OpIf, valType(t))
    if err := b.walk(n.TrueBlock); err != nil  { return err }
    b.buf = append(b.buf, OpElse)
    if err := b.walk(n.FalseBlock); err != nil { return err }
    b.buf = append(b.buf, OpEnd)
    return nil

4. body.go — add the cast case:

case *script.CastExpression:
    if err := b.walk(n.Expr); err != nil { return err }
    from := n.Expr.(script.Expression).GetType()
    to   := n.GetType()
    op, ok := castOpcode(from, to)
    if !ok {
        return fmt.Errorf("no cast from %s to %s", from.Kind, to.Kind)
    }
    if op != 0 {
        b.buf = append(b.buf, op)
    }
    return nil

func TestEndToEnd_Ternary(t *testing.T) {
    src := `
        fn pick(cond: bool, a: i64, b: i64): i64 {
            return cond ? a : b;
        }
        fn ternary_arithmetic(x: i64): i64 {
            return (x > 0 ? x : -x) * 2;
        }
    `
    runOne(t, src, "pick", []uint64{1, 10, 20}, 10)   // true  → a
    runOne(t, src, "pick", []uint64{0, 10, 20}, 20)   // false → b
    runOne(t, src, "ternary_arithmetic", []uint64{api.EncodeI64(-5)}, 10)
    runOne(t, src, "ternary_arithmetic", []uint64{3}, 6)
}

func TestEndToEnd_TypeCast(t *testing.T) {
    src := `
        fn i64_to_f64(x: i64): f64 { return x as f64; }
        fn f64_to_i64(x: f64): i64 { return x as i64; }
        fn i64_to_i32(x: i64): i32 { return x as i32; }
    `
    runOne(t, src, "i64_to_f64", []uint64{7},                     api.EncodeF64(7.0))
    runOne(t, src, "f64_to_i64", []uint64{api.EncodeF64(3.9)},    3)    // truncates
    runOne(t, src, "f64_to_i64", []uint64{api.EncodeF64(-2.7)},   api.EncodeI64(-2))
    runOne(t, src, "i64_to_i32", []uint64{42},                    42)
}
Watch out: ternary_arithmetic uses a nested ternary as a sub-expression. The if/else/end block it emits sits inside a larger expression — the multiplied result is still on the stack when OpI64Mul fires. WASM's structured control flow is designed so that the net stack effect of an if is exactly what the block type declares: one value in, one value out. As long as both branches push exactly one i64, the surrounding arithmetic works seamlessly.

Why the Ternary isn't Special

At the stack-machine level, WASM's if with a result type is not a new instruction — it's the same 0x04 opcode with a different block type byte. The validator ensures both branches leave the declared type on the stack. The plex typechecker already ensured both branches have the same type (that's what n.GetType() reflects). So the binary encoder simply trusts what the typechecker proved and emits the correct block type byte.

This is a recurring theme in compiler construction: later passes trust earlier passes. The typechecker does the hard reasoning. The binary encoder just emits bytes.
