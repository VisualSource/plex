Lesson 35 – Unary Operators: The Missing Negate

Goal: handle -x and +x in the binary backend, and learn something quietly surprising about WASM's instruction set on the way.

Files you'll touch: opcodes.go · body.go · end_to_end_test.go

The Failing Test

Add this — it currently dies in the encoder with "unhandled AST node *script.UnaryExpression":

func TestEndToEnd_UnaryMinus(t *testing.T) {
    src := `
        fn neg_then_add(x: i64, y: i64): i64 {
            return -x + y;
        }
        fn double_neg(x: i64): i64 {
            return -(-x);          // should equal x
        }
        fn unary_plus(x: i64): i64 {
            return +x;             // no-op
        }
    `
    runOne(t, src, "neg_then_add", []uint64{10, 3}, uint64(-7))
    runOne(t, src, "double_neg",    []uint64{42},     42)
    runOne(t, src, "unary_plus",    []uint64{7},      7)
}
go test ./internal/script/compiler/binary/... -run TestEndToEnd_UnaryMinus -v
Note on uint64(-7). Go's two's complement encoding means uint64(-7) is 0xFFFFFFFFFFFFFFF9. That is the exact same 64-bit pattern WASM's i64.sub produces for 0 - 7, so the comparison succeeds. The host treats the result as unsigned; the inside of the function treats it as signed. Both views of the same bytes.

The Surprise: WASM Has No Integer Negate

Open the spec's numeric instruction table. Scroll the i32 and i64 sections. You will find add, sub, mul, div_s, div_u, and, or, xor, shl, shr_s… and no neg.

Float types do have one:

TypeNegation opcode
f32.neg0x8C
f64.neg0x9A
i32.neg— does not exist
i64.neg— does not exist
Why the asymmetry? Floating-point negation flips a single sign bit — a primitive hardware operation distinct from subtraction. Integer negation, by contrast, is exactly 0 - x on a two's complement machine; there's no cheaper hardware path. WASM's design philosophy is "one opcode per primitive operation, not per syntactic convenience" — so neg exists where it is its own thing, and otherwise you compose. The same philosophy is why there's no i32.inc or i64.dec.

So the compiler does the composition itself:

-x for integers

i64.const 0
walk(x)
i64.sub

-x for floats

walk(x)
f64.neg
Stack order matters. i64.sub pops the top value as the right operand and the next as the left. To compute 0 - x you must push 0 first, then x. Reversing it gives x - 0 = x — a silent no-op that is hard to spot in failing tests.

Implementation

Step 1 — Add f64.neg

In opcodes.go, add the one missing opcode:

OpF64Neg byte = 0x9A

Step 2 — Handle *script.UnaryExpression

Add a case in bodyEncoder.walk. Plex's parser only produces unary + and unary - (see ast.go:318-340) — no ! yet, no prefix ++/--, so we only need two arms. The operand type is the operand's own type, not the unary node's:

case *script.UnaryExpression:
    if n.Operator == script.TokenType_Plus {
        return b.walk(n.Operand)   // unary + is a no-op
    }
    if n.Operator != script.TokenType_Minus {
        return fmt.Errorf("unsupported unary operator %v", n.Operator)
    }

    t := n.Operand.GetType()
    if t == nil {
        return fmt.Errorf("no type on unary operand")
    }

    switch t.Kind {
    case script.TypeKind_F64, script.TypeKind_Float:
        if err := b.walk(n.Operand); err != nil { return err }
        b.buf = append(b.buf, OpF64Neg)
        return nil
    case script.TypeKind_I64, script.TypeKind_Int:
        b.buf = append(b.buf, OpI64Const)
        b.buf = AppendSLEB128(b.buf, 0)
        if err := b.walk(n.Operand); err != nil { return err }
        b.buf = append(b.buf, OpI64Sub)
        return nil
    case script.TypeKind_I32:
        b.buf = append(b.buf, OpI32Const)
        b.buf = AppendSLEB128(b.buf, 0)
        if err := b.walk(n.Operand); err != nil { return err }
        b.buf = append(b.buf, OpI32Sub)
        return nil
    default:
        return fmt.Errorf("unary minus not supported for type %v", t.Kind)
    }
Note the operand-vs-result echo. Just like the binary-expression fix in lesson 34, you read the operand's type — not the unary node's GetType() — for opcode dispatch. For unary, they happen to be the same today (negation preserves type), but the principle is the same: the type that selects the opcode is the type of the value being consumed.

Aside: Why ! Isn't in This Lesson

The plex parser currently does not produce a unary ! — only + and - are recognised in parseUnary. Logical not is therefore not yet expressible in the source language. When you do add it, the codegen will be a single opcode: i32.eqz (already defined as OpI32Eqz in opcodes.go:32). Two-line lesson, two-line implementation — file under "tomorrow".

Knowledge Check

Quiz

1. Why does WASM provide f64.neg but not i64.neg?

2. To compile -x as 0 - x, in what order do you push the operands?

3. Why does the implementation read n.Operand.GetType() rather than n.GetType()?

4. unary_plus(x) → x is implemented as just walk the operand — no opcode emitted for the +. Why is that correct?

What's Next

  • Fill out comparisons. i32 is missing < > ≤ ≥ (only eq/ne today); f64 has no comparison opcodes at all. Mechanical but worth doing before linear memory lands.
  • Postfix ++ and --. The WAT compiler already handles these as a load-load-const-1-add-store sequence (see compiler.go:127-162). Direct port to the binary backend.
  • Linear memory. The big one. Memory section + data section + i32.load/i32.store family — the gateway to strings, arrays, and structs in the binary backend.
