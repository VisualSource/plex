Lesson 58 – String Indexing (s[i])

Previous: Lesson 57 – Increment and Decrement

s[i] is already parsed — the parser produces an ArrayAccess node. But there are two bugs: the typechecker returns the wrong type for the result, and the binary backend uses array addressing instead of byte addressing. This lesson fixes both and introduces walkStringIndex.

Bug 1: Typechecker Returns Wrong Type

In typecheck.go, the ArrayAccess case dispatches on the target's type. For a string identifier it currently does: 

case script.TypeKind_String:
    n.SetType(i)   // sets element type to TypeKind_String — wrong
    return i

s[i] should yield the byte value at position i — a number, not a string. The correct fix: 

case script.TypeKind_String:
    result := &script.Type{Kind: script.TypeKind_Int}
    n.SetType(result)
    return result

Bug 2: Array vs String Memory Layout

Strings and arrays look alike in memory — both start with a 4-byte length header — but their element size is different:

Length headerElement sizeAddress of element i
int[]4 bytes (i32)8 bytes (i64)base + 4 + i × 8
f64[]4 bytes (i32)8 bytes (f64)base + 4 + i × 8
string4 bytes (i32)1 byte (ASCII)base + 4 + i

The existing ArrayAccess handler in body.go multiplies the index by elemSizeOf(elemType.Kind). After the typechecker fix, elemType for s[i] becomes TypeKind_Int — which has element size 8. That would be wrong: it would read 8 bytes at an 8× offset instead of 1 byte at a 1× offset.

Same AST node, two code paths. arr[i] and s[i] both parse to ArrayAccess. The codegen must dispatch on the target's type (not the element type) to know which addressing to use. This is type-directed dispatch — the same pattern used for string + and ==.

The Fix: walkStringIndex

At the top of the ArrayAccess case in body.go, check whether the target is a string and divert to a new method: 

case *script.ArrayAccess:
    // Type-directed dispatch: strings use byte addressing, arrays use elem-size addressing.
    if targetExpr, ok := n.Target.(script.Expression); ok {
        tt := targetExpr.GetType()
        if tt != nil && tt.Kind == script.TypeKind_String {
            return b.walkStringIndex(n)
        }
    }

    // ... existing array logic unchanged ...

Implementing walkStringIndex

The structure mirrors array indexing: save the pointer and index to synthetic locals, bounds-check, then load. The difference is in the final load instruction and address calculation.

; s[i] — string at strBase, index in strIdx local.get strBase [strBase] local.get strIdx [strBase, strIdx] i32.add [strBase + strIdx] i32.load8_u align=0 offset=4 [byte at strBase+4+strIdx] ← 1 byte, zero-extended i64.extend_i32_s [i64 byte value]

The offset=4 in i32.load8_u is the static offset baked into the instruction — it skips the 4-byte length header without needing a separate i32.const 4; i32.add on the stack. The final i64.extend_i32_s widens the byte value to a plex int. 

func (b *bodyEncoder) walkStringIndex(n *script.ArrayAccess) error {
    strBase := b.addSyntheticLocal(ValI32)
    strIdx  := b.addSyntheticLocal(ValI32)

    // save string pointer
    if err := b.walk(n.Target); err != nil { return err }
    b.buf = append(b.buf, OpLocalSet)
    b.buf = AppendULEB128(b.buf, strBase)

    // save index (i64 → i32)
    if err := b.walk(n.Index); err != nil { return err }
    b.buf = append(b.buf, OpI32WrapI64, OpLocalSet)
    b.buf = AppendULEB128(b.buf, strIdx)

    // bounds check: strIdx >= string.len → unreachable
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, strIdx)
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, strBase)
    b.buf = append(b.buf, OpI32Load)
    b.buf = AppendULEB128(b.buf, 2)   // align=2 (4-byte length field)
    b.buf = AppendULEB128(b.buf, 0)   // offset=0
    b.buf = append(b.buf, OpI32GeU, OpIf, BlockTypeEmpty)
    b.blockDepth++
    b.buf = append(b.buf, OpUnreachable, OpEnd)
    b.blockDepth--

    // load byte: base + 4 + idx
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, strBase)
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, strIdx)
    b.buf = append(b.buf, OpI32Add, OpI32Load8U)
    b.buf = AppendULEB128(b.buf, 0)   // align=0 (byte)
    b.buf = AppendULEB128(b.buf, 4)   // offset=4 (skip length header)

    // widen to i64 (plex int)
    b.buf = append(b.buf, OpI64ExtendI32S)
    return nil
}

Comprehension Check

Why can't the existing ArrayAccess handler be used unchanged after the typechecker fix?

After the typechecker fix, the element type is TypeKind_Int (size 8). The array handler would multiply the index by 8 and use i64.load — loading 8 bytes at an 8× offset. String chars are 1 byte at a 1× offset. The target type dispatch is what separates the two paths.

What is offset=4 doing in the i32.load8_u align=0 offset=4 instruction?

WASM load instructions have an immediate offset added to the address on the stack. offset=4 adds 4 to (strBase + strIdx), giving strBase + strIdx + 4 — past the 4-byte length header. This avoids a separate i32.const 4; i32.add instruction.

Why is i32.load8_u used rather than i32.load?

String characters are stored as raw bytes (1 byte each). i32.load reads 4 consecutive bytes and interprets them as an i32 — that would read the current character plus the next three. load8_u reads exactly 1 byte and zero-extends it to 32 bits.

The dispatch in ArrayAccess checks the target's type, not the element type. Why?

After fixing the typechecker, s[i] and int_arr[i] both have element type TypeKind_Int. To tell them apart in codegen you must look at what is being indexed — the target's type (TypeKind_String vs TypeKind_Array).

func TestEndToEnd_StringIndex(t *testing.T) {
    src := `
        export fn first_byte(): int { return "hello"[0]; }   // 'h' = 104
        export fn last_byte():  int { return "hello"[4]; }   // 'o' = 111
        export fn from_var(): int {
            let s: string = "hello";
            return s[1];  // 'e' = 101
        }
        export fn sum_bytes(): int {
            let s: string = "AB";  // 'A'=65, 'B'=66
            return s[0] + s[1];  // 131
        }
    `
    runOne(t, src, "first_byte", nil, 104)
    runOne(t, src, "last_byte",  nil, 111)
    runOne(t, src, "from_var",   nil, 101)
    runOne(t, src, "sum_bytes",  nil, 131)
}

The sum_bytes case is the most valuable: it verifies that two back-to-back s[i] accesses return independent integer values that can be used in arithmetic — confirming the type is genuinely int, not something that happens to work once.
