Lesson 15 — Type-Directed Code Generation

compilerWATannotated ASTsnapshot testing

Your typechecker now annotates every node in the AST with a type. That information is there for a reason: the compiler is supposed to use it. When it doesn't, the generated code is wrong — not "prints an error" wrong, but "silently produces invalid WebAssembly" wrong.

This lesson tracks down exactly that class of bug in compiler.go, explains why it happens, and teaches you how to fix it systematically.

1. The Flow: Annotated AST → Code Gen

Remind yourself of what the compiler pipeline looks like after adding the typechecker:

Source text
→
Parser
builds AST
→
Typechecker
annotates AST
→
Compiler
reads annotations
→
WAT output

The typechecker calls n.SetType(t) on each AST node. The compiler calls n.GetType() to retrieve it. This is the contract: typechecker provides, compiler consumes.

When the compiler ignores GetType() and hardcodes an instruction instead, it has broken that contract.

2. The Bug: Arrays with Hardcoded f64

Look at the array literal code in compiler.go:

case *script.ArrayLiteral:
    // ...
    elemSize := 8 // f64 element size in bytes
    totalSize := 4 + len(n.Elements)*elemSize

    // ...allocate, store length...

    for i, v := range n.Elements {
        offset := 4 + i*elemSize
        // ...emit address arithmetic...
        if err := c.Compile(v); err != nil {
            return err
        }
        c.emit("f64.store")  // ← HARDCODED
    }

And the array access code:

case *script.ArrayAccess:
    // ...address arithmetic...
    c.emit("i32.const 8")   // ← HARDCODED size
    c.emit("i32.mul")
    c.emit("i32.add")
    c.emit("f64.load")      // ← HARDCODED

Now watch what the compiler produces for int[]:

let a: int[] = [1, 2];

Integer literals are typed as TypeKind_Int, which maps to i64 in WAT. But the compiler emits:

i64.const 1      ;; ✅ correct: element is i64
f64.store        ;; ❌ wrong: can't store i64 as f64

WebAssembly is strongly typed at the instruction level. A f64.store instruction expects an f64 value on the stack. Pushing an i64 and then calling f64.store is a type error that WebAssembly runtimes will reject at validation time. The program won't even start.

Silent wrongness: The typechecker caught this at the plex level. But the compiler lost the information on the way to WAT. Without running the WAT through a validator, this bug is invisible — the output is text, it looks plausible, and no Go test catches it until you validate or execute the WAT.

3. The Fix: Ask the Type

The information you need is already there. After the typechecker runs, n.GetType() on an ArrayLiteral returns a *Type with Kind == TypeKind_Array and Element set to the element type. The element type is exactly what you need to pick the right store instruction.

The pattern is:

case *script.ArrayLiteral:
    t := n.GetType()           // *Type{Kind: Array, Element: *Type{Kind: Int}}
    if t == nil {
        return fmt.Errorf("array literal has no type")
    }
    wasmElem := getWasmType(t.Element)   // "i64"
    elemSize := sizeOf(wasmElem)         // 8

    // ... then use wasmElem + ".store" instead of "f64.store" ...

And for access:

case *script.ArrayAccess:
    t := n.GetType()           // element type (already unwrapped by typechecker)
    if t == nil {
        return fmt.Errorf("array access has no type")
    }
    wasmElem := getWasmType(t)
    elemSize := sizeOf(wasmElem)

    // ... use elemSize for stride, wasmElem + ".load" instead of "f64.load" ...
General principle: Any time you see a hardcoded WAT type string ("f64.store", "i32.const 8") in code that handles heterogeneous data, ask: "should this be driven by a call to getWasmType?" The typechecker did the work of figuring out the type. The compiler should use it.

4. Snapshot Testing in Compilers

Three of the four compiler tests use snapshot files — they compile a program and check the output matches a saved .wat file. This is called snapshot testing (sometimes "golden file testing").

It's popular in compilers because the output can be large and changing it manually is tedious. Instead of writing expected output by hand, you:

  1. Run the compiler once to produce output you believe is correct
  2. Save it as the snapshot
  3. From then on, the test fails if the output ever changes unexpectedly

The workflow when you change the compiler intentionally:

  1. Make the change
  2. Run the tests — they fail (snapshot is stale)
  3. Inspect the diff: is the new output correct?
  4. If yes: regenerate the snapshot and commit it
  5. If no: fix the compiler, repeat

The current state in plex is messier: TestAlloc and TestArray both compare against testdata/struct.wat, which is a copy-paste error. They each need their own snapshot file. And TestStructGenAndCtor fails because its snapshot is missing a trailing newline.

When to update vs when to fix

SituationAction
You changed the compiler intentionally and the output is correctUpdate the snapshot
A refactor changed formatting but not semanticsUpdate the snapshot
The output changed and you're not sure whyInvestigate before updating
The output is semantically wrong (wrong WAT type)Fix the compiler, then update the snapshot
The snapshot file doesn't even match the testFix the test, create the right snapshot

Check Your Understanding

1. After the typechecker runs, what does n.GetType() return on an ArrayLiteral node for [1, 2, 3]?

✅ &Type{Kind: TypeKind_Array, Element: &Type{Kind: TypeKind_Int}}. The typechecker sets the type on the ArrayLiteral node itself. The element type is in .Element. For array access nodes, GetType() returns the element type directly (already unwrapped).

2. Why does f64.store on an i64 value cause a WebAssembly validation error?

✅ Every WAT store instruction is typed. f64.store pops an address (i32) and a value (f64) from the stack. Pushing an i64 and then calling f64.store is a static type error that the WASM validator rejects before execution.

3. You fix the array bug and the snapshot test fails. Is that expected?

✅ Expected. The snapshot captured the buggy output. Now that the compiler emits the correct instructions, the output differs. Your job is to inspect the new output, confirm it's correct, and update the snapshot file.
