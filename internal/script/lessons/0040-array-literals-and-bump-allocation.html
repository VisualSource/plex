Lesson 40 – Array Literals and the Inline Bump Allocator

Goal: compile [10, 20, 30] into a heap-allocated array. The function returns an i32 pointer; the host reads the bytes back. Lesson 39's __heap_ptr finally gets used.

Files you'll touch: opcodes.go · body.go · helpers.go · module.go · end_to_end_test.go

Array Memory Layout

Same shape as strings, but with typed elements: a 4-byte little-endian length followed by the elements packed at element-sized offsets. For [10, 20, 30] as an i64 array, starting at heap offset 0:

03@0
00@1
00@2
00@3
i64 = 10@4..@11
i64 = 20@12..@19
i64 = 30@20..@27

The "value" of the array at the WASM level is the i32 pointer to the length prefix — exactly like strings.

Element typeBytes per elementStore opcode
i324i32.store (0x36)
i64 / int8i64.store (0x37)
f64 / float8f64.store (0x39)

The Inline Bump Allocator

"Bump allocator" is grand-sounding for what's actually six instructions. Each array-literal site embeds a tiny prologue that claims N bytes from the heap:

; claim N bytes; leave base ptr in stack and in local 'arrTmp' 23 00 ; global.get __heap_ptr stack: [ptr] 22 LL ; local.tee arrTmp stack: [ptr], arrTmp=ptr 41 NN ; i32.const N stack: [ptr, N] 6A ; i32.add stack: [ptr+N] 24 00 ; global.set __heap_ptr stack: [] (heap advanced)

After this prologue, the freshly-allocated base address lives in arrTmp and the heap pointer is N bytes ahead. Each element then gets stored at a constant offset from the base:

; store length at base+0 20 LL ; local.get arrTmp stack: [base] 41 03 ; i32.const 3 stack: [base, 3] 36 02 00 ; i32.store align=2 offset=0 *base = 3, stack: [] ; store element 0 at base+4 20 LL ; local.get arrTmp stack: [base] 42 0A ; i64.const 10 stack: [base, 10] 37 03 04 ; i64.store align=3 offset=4 *(base+4) = 10 ; store element 1 at base+12, element 2 at base+20...
memarg's offset field is doing the array-indexing work. The store opcode pops (address, value), then writes to address + offset. So you don't compute base + 4 + i*elemSize in the WASM stack at all — you encode that displacement inline in the memarg. Two ULEBs (align, offset) per store, no i32.add instructions needed. Lesson 37 already used this for i32.load align=2 offset=0; today's lesson exploits its real power.

And at the end, the parent (a return, a let, a FunctionCall argument) wants the base pointer on the stack:

20 LL ; local.get arrTmp stack: [base]

The Heap Emission Gate

Currently module.go emits memory + global + data sections only when len(strings.entries) > 0. Arrays also need memory and the heap pointer, even when no strings exist. The gate needs to widen to "any heap allocation in the program":

needsHeap := len(strings.entries) > 0 || programHasArrays(node)

if needsHeap {
    exports = append(exports, exportEntry{name: "memory", kind: ExportMemory, idx: 0})
    exports = append(exports, exportEntry{name: "__heap_ptr", kind: ExportGlobal, idx: 0})
}

programHasArrays is a tiny AST walker — same shape as collectStrings but answering yes-or-no:

func programHasArrays(p *script.Program) bool {
    found := false
    var walk func(script.AstNode)
    walk = func(n script.AstNode) {
        if found { return }
        switch v := n.(type) {
        case *script.ArrayLiteral:
            found = true
        case *script.Program:
            for _, s := range v.Stmts { walk(s) }
        case *script.FunctionDeclaration:
            walk(v.Body)
        case *script.Block:
            for _, s := range v.Stmts { walk(s) }
        case *script.ReturnStatement:
            if v.Value != nil { walk(v.Value) }
        case *script.VariableDeclaration:
            if v.Init != nil { walk(v.Init) }
        case *script.BinaryExpression:
            walk(v.Left); walk(v.Right)
        case *script.IfStatement:
            walk(v.Condition); walk(v.Body)
            if v.Else != nil { walk(v.Else) }
        case *script.WhileStatement:
            walk(v.Condition); walk(v.Body)
        case *script.FunctionCall:
            walk(v.Callee)
            for _, a := range v.Args { walk(a) }
        case *script.MemberAccess:
            walk(v.Object)
        }
    }
    walk(p)
    return found
}
The collector-emitter invariant strikes again. Same lesson as 37: any AST shape walk recurses into during codegen, the heap-detection pass must recurse into too. The shapes covered here mirror what collectStrings walks — keep them in sync.

Synthesising Locals at Codegen Time

The bump allocator needs a temporary i32 to hold arrTmp. It doesn't come from plex source — the compiler invents it. collectLocals in lesson 31 only walks VariableDeclaration nodes from source; synthetic locals need a different mechanism.

Add a method on bodyEncoder:

func (b *bodyEncoder) addSyntheticLocal(vt byte) uint32 {
    idx := uint32(len(b.locals) + len(b.params) /* if you track them separately; otherwise just len(b.locals) */)
    b.localTypes = append(b.localTypes, vt)
    // Synthetic locals don't need an entry in b.locals (the name→index map)
    // — the caller holds the index directly.
    return idx
}

Check the actual bodyEncoder shape in body.go — your locals map already includes params with indices assigned in newBodyEncoder. The synthetic local just appends to localTypes and bumps the running index; the caller stores the returned index in a Go variable for the duration of the emission.

Implementation

Step 1 — Opcodes

In opcodes.go:

OpI32Store byte = 0x36  // already present
OpI64Store byte = 0x37
OpF64Store byte = 0x39

Step 2 — Element-size and store-opcode helpers

In helpers.go, add two small lookups:

func elemSizeOf(k script.TypeKind) uint32 {
    switch k {
    case script.TypeKind_I32:
        return 4
    case script.TypeKind_I64, script.TypeKind_Int,
         script.TypeKind_F64, script.TypeKind_Float:
        return 8
    default:
        return 4 // pointers (strings, arrays, structs)
    }
}

func storeOpcode(k script.TypeKind) (op byte, align uint32) {
    switch k {
    case script.TypeKind_I32:
        return OpI32Store, 2
    case script.TypeKind_I64, script.TypeKind_Int:
        return OpI64Store, 3
    case script.TypeKind_F64, script.TypeKind_Float:
        return OpF64Store, 3
    default:
        return OpI32Store, 2 // pointer-as-i32
    }
}

Step 3 — Wire *script.ArrayLiteral in walk

The whole case as one block — read it through once before typing it in:

case *script.ArrayLiteral:
    t := n.GetType()
    if t == nil || t.Element == nil {
        return fmt.Errorf("array literal missing element type")
    }

    elemSize := elemSizeOf(t.Element.Kind)
    storeOp, storeAlign := storeOpcode(t.Element.Kind)
    totalSize := uint32(4) + uint32(len(n.Elements))*elemSize

    arrTmp := b.addSyntheticLocal(ValI32)

    // bump: arrTmp = heapPtr; heapPtr += totalSize
    b.buf = append(b.buf, OpGlobalGet); b.buf = AppendULEB128(b.buf, 0)
    b.buf = append(b.buf, OpLocalTee);  b.buf = AppendULEB128(b.buf, arrTmp)
    b.buf = append(b.buf, OpI32Const);  b.buf = AppendSLEB128(b.buf, int64(totalSize))
    b.buf = append(b.buf, OpI32Add)
    b.buf = append(b.buf, OpGlobalSet); b.buf = AppendULEB128(b.buf, 0)

    // store length at base+0
    b.buf = append(b.buf, OpLocalGet);  b.buf = AppendULEB128(b.buf, arrTmp)
    b.buf = append(b.buf, OpI32Const);  b.buf = AppendSLEB128(b.buf, int64(len(n.Elements)))
    b.buf = append(b.buf, OpI32Store); b.buf = AppendULEB128(b.buf, 2); b.buf = AppendULEB128(b.buf, 0)

    // store each element at base + 4 + i*elemSize
    for i, el := range n.Elements {
        offset := uint32(4) + uint32(i)*elemSize
        b.buf = append(b.buf, OpLocalGet); b.buf = AppendULEB128(b.buf, arrTmp)
        if err := b.walk(el); err != nil {
            return err
        }
        b.buf = append(b.buf, storeOp)
        b.buf = AppendULEB128(b.buf, storeAlign)
        b.buf = AppendULEB128(b.buf, offset)
    }

    // leave the base ptr on the stack for the parent
    b.buf = append(b.buf, OpLocalGet); b.buf = AppendULEB128(b.buf, arrTmp)
    return nil

Step 4 — Test

The function returns an array; the host reads memory at the returned pointer:

func TestEndToEnd_ArrayLiteral(t *testing.T) {
    src := `
        fn make_arr(): int[] {
            return [10, 20, 30];
        }
    `
    ast, err := script.Parse(strings.NewReader(src))
    if err != nil { t.Fatal(err) }
    wasm, err := binary_wasm.CompileProgram(ast)
    if err != nil { t.Fatal(err) }

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)
    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    got, err := mod.ExportedFunction("make_arr").Call(ctx)
    if err != nil { t.Fatalf("call: %v", err) }

    ptr := api.DecodeU32(got[0])
    mem := mod.Memory()

    n, _ := mem.ReadUint32Le(ptr)
    if n != 3 { t.Fatalf("length = %d, want 3", n) }

    want := []uint64{10, 20, 30}
    for i, w := range want {
        v, _ := mem.ReadUint64Le(ptr + 4 + uint32(i)*8)
        if v != w {
            t.Fatalf("arr[%d] = %d, want %d", i, v, w)
        }
    }
}

If anything fails, the first place to look is the heap pointer: if your test program is the only one using memory (no strings), the array lives at offset 0 and you should see got[0] == 0. The heap pointer global should advance to 28 (= 4 + 3*8) after the call.

What This Lesson Showed

  • The bump allocator is six instructions. No allocator library, no helper function — the prologue inlines wherever an array is constructed. Cheap if arrays are rare; pricier (code-size) if they're everywhere.
  • memarg offsets are the array-store/load arithmetic. Each store carries its own constant displacement, so a sequence of element stores produces no i32.add bytecode at all. This is one of the WASM spec's quiet design choices that pays off in dense, fast bytecode.
  • Synthetic locals are normal. localTypes is just a vector; appending an entry creates a new local at the next index. Source-driven and codegen-driven locals coexist in the same vec.
  • The "needs memory" gate has widened. Strings used to be the only trigger; now arrays count too. Future shapes (struct literals, dynamic strings) will join the list and the gate logic will keep generalising.

Knowledge Check

Quiz

1. What's the role of memarg's offset field in array-element stores?

2. Why does the array literal emit local.tee for arrTmp after global.get __heap_ptr instead of just local.set?

3. Suppose a function builds [1, 2], then [3, 4, 5]. Why is each array safe to inhabit consecutive heap regions despite both being "allocated at heapPtr"?

4. The bump allocator never frees memory. What's the consequence — and is it OK for a toy language?

What's Next

  • Array length and access. arr.len() is i32.load align=2 offset=0 at the array pointer, then i64.extend_i32_s — same shape as s.len() from lesson 37. arr[i] is base + 4 + i*elemSize followed by an element-typed load.
  • Heap alignment. If any future element type is f64 (8-byte natural), the heap should start 8-byte-aligned. Easy patch: (strings.next + 7) & ~7 as the global's initialiser.
  • Struct literals. Same allocator pattern; the per-field offsets come from a struct layout table instead of i * elemSize.
