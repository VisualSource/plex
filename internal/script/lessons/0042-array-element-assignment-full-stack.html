Lesson 42 – Array Element Assignment, Across the Whole Compiler

Goal: make arr[i] = x work end-to-end. Every prior binary-backend lesson has touched one file. Today touches four — parser, AST, typechecker, codegen — because a real language feature has to land in every stage that touches a program.

Files you'll touch: ast_nodes.go · ast.go · typecheck.go · body.go · end_to_end_test.go

Why This Is the Right Shape of Lesson

Every binary-backend lesson so far has assumed the AST and typechecker were ready and only added codegen. Today's task isn't possible that way — the parser doesn't even accept arr[i] = x as syntax. Try it now:

let arr = [1, 2, 3];
arr[0] = 99;   // parse error: invalid assignment target

Look at ast.go's parseAssignment (around line 500). It type-switches the LHS of an = and only accepts *Identifier and *MemberAccess. *ArrayAccess falls through to the "invalid assignment target" error.

This is the natural shape of "add a feature to a compiler". A language feature is a coordinated change across every stage that sees it. New syntax needs new parsing. New AST needs new types. New typed expressions need new checking. New checked expressions need new codegen. Each stage's change is small; the discipline is making them consistent.

Stage 1 — AST

Define the new node first. Everything downstream depends on its shape.

In ast_nodes.go, add a new node next to MemberAssignment (around line 386). It mirrors that node, but the LHS carries an index expression instead of a field name:

type ArrayAssignment struct {
    Start, End Position
    Target     *ArrayAccess  // the arr[i] being assigned to
    Value      AstNode
}

func (a *ArrayAssignment) Range() (Position, Position) {
    return a.Start, a.End
}
Why not reuse MemberAssignment? The shapes differ: MemberAssignment has a string Field, while array assignment has a runtime-computed Index. Forcing one node to hold either would mean nullable fields and switchy codegen. Two clean nodes beat one Frankenstein.

Stage 2 — Parser

Teach parseAssignment to recognise ArrayAccess on the left of =.

In ast.go, extend the type switch in parseAssignment:

switch target := expr.(type) {
case *Identifier:
    // ... existing AssignmentExpression branch ...
case *MemberAccess:
    // ... existing MemberAssignment branch ...
case *ArrayAccess:
    return &ArrayAssignment{
        Start:  start,
        End:    end,
        Target: target,
        Value:  value,
    }, nil
default:
    return nil, fmt.Errorf("invalid assignment target")
}

That's it for the parser. The parseAssignment path already had the precedence right (assignment as a right-associative tail of parseTernary) — we just teach it about one more LHS shape.

Stage 3 — Typechecker

The new node must type-check: target's element type must match value's type.

In typecheck.go, add a case next to *script.MemberAssignment (around line 636). The shape:

case *script.ArrayAssignment:
    // Type-check the array access as if reading from it; this populates
    // n.Target.type_ with the element type.
    elemType := c.checkExpression(n.Target)
    if elemType == nil {
        return nil
    }

    valType := c.checkExpression(n.Value.(script.Expression))
    if valType == nil {
        return nil
    }

    if !isSameType(elemType, valType) {
        c.error(n, fmt.Errorf("array element type %s does not match assigned value type %s", elemType.Kind, valType.Kind))
        return nil
    }

    return valType

You'll also need a tiny dispatch entry — the checkStmt function near line 600 has a switch that routes statement nodes to checkExpression. Add an arm for *script.ArrayAssignment right next to the existing *script.MemberAssignment arm if it exists; otherwise just let it fall through to the catch-all. Run the typechecker tests after to see where coverage stopped.

Don't try to be clever about n.Target's walk. Calling checkExpression(n.Target) populates the inner ArrayAccess's type_ field with the element type. The binary backend will read that via n.Target.GetType(). If you short-circuit this step, codegen later won't know the element type.

Stage 4 — Binary Backend (codegen)

Compute the address — exactly like arr[i] — but emit a store instead of a load.

In body.go, add a case to walk:

case *script.ArrayAssignment:
    elemType := n.Target.GetType()
    if elemType == nil {
        return fmt.Errorf("array assignment target has no element type")
    }

    elemSize := elemSizeOf(elemType.Kind)
    storeOp, storeAlign := storeOpcode(elemType.Kind)

    // 1. push the base address (the array pointer)
    if err := b.walk(n.Target.Target); err != nil {
        return err
    }
    // 2. push the index, narrowed to i32 for address math
    if err := b.walk(n.Target.Index); err != nil {
        return err
    }
    b.buf = append(b.buf, OpI32WrapI64)

    // 3. multiply by elemSize
    b.buf = append(b.buf, OpI32Const)
    b.buf = AppendSLEB128(b.buf, int64(elemSize))
    b.buf = append(b.buf, OpI32Mul)

    // 4. add to base → target address (still missing +4, comes from memarg)
    b.buf = append(b.buf, OpI32Add)

    // 5. push the value
    if err := b.walk(n.Value); err != nil {
        return err
    }

    // 6. typed store at +4 (skip length prefix)
    b.buf = append(b.buf, storeOp)
    b.buf = AppendULEB128(b.buf, storeAlign)
    b.buf = AppendULEB128(b.buf, 4)
    return nil
This mirrors ArrayAccess point-for-point. Same address arithmetic, same +4-via-memarg trick, same element-type dispatch. The only differences: push the value before the store, emit storeOp instead of loadOp, return without pushing anything (assignment is a statement-shaped expression that produces no result).

Statement-position drop. Lesson 33's Block arm drops the result of any expression-typed statement that isn't a known consumer. ArrayAssignment as a statement should produce nothing on the stack — which the code above already achieves (the store consumes both the address and the value, pushing nothing). If the AST node satisfies script.Expression with a non-void type, lesson 33's drop logic would emit a stray drop. Either: (a) don't implement GetType/SetType on ArrayAssignment (it's a statement, not an expression), or (b) make GetType return a Void type. The cleaner choice is (a) — the node simply isn't an Expression.

Test

The end-to-end win — write to an element, read it back, prove the change persisted:

func TestEndToEnd_ArrayAssignment(t *testing.T) {
    src := `
        fn write_then_read(): int {
            let arr = [10, 20, 30];
            arr[1] = 99;
            return arr[1];
        }
        fn rotate(): int {
            let arr = [1, 2, 3, 4, 5];
            arr[0] = arr[4];
            arr[4] = 1;
            return arr[0] + arr[4]; // 5 + 1 = 6
        }
        fn sort_two(): int {
            let arr = [20, 10];
            if arr[0] > arr[1] {
                let tmp = arr[0];
                arr[0] = arr[1];
                arr[1] = tmp;
            }
            return arr[0] * 10 + arr[1]; // 10*10 + 20 = 120
        }
    `
    runOne(t, src, "write_then_read", nil, 99)
    runOne(t, src, "rotate",          nil, 6)
    runOne(t, src, "sort_two",        nil, 120)
}
go test ./internal/script/compiler/binary/... -v

sort_two is the canary case — it tests that assignment composes with reads inside a conditional. If only write_then_read passed, you'd suspect a subtle ordering bug; sort_two covers the realistic pattern.

What You Just Learned About Compiler Stages

This lesson's shape is the lesson — not any individual stage's code. Notice:

  • Each stage's change was tiny. One struct in the AST, one switch arm in the parser, one case in the typechecker, one case in codegen. None of them required new infrastructure.
  • The stages depend on each other strictly downstream. Parser depends on AST. Typechecker depends on parsed-and-typed AST. Codegen depends on type-checked AST. Skipping a stage upstream makes the next stage's work harder or impossible.
  • The hardest part is consistency, not code. The bugs in features like this come from a stage doing something almost right but inconsistent with another stage — typechecker assigning the wrong type, codegen reading from a different field, parser producing an unexpected variant. The fix is usually three lines spread across two files.
Every "add a language feature" task has this shape. Imports, modules, generics, async/await, pattern matching, traits — all of them eventually decompose into "new node in AST + parse rule + check rule + emit rule". The cross-stage discipline you exercised today is the actual skill of compiler engineering.

Knowledge Check

Quiz

1. Why does ArrayAssignment warrant its own AST node rather than reusing MemberAssignment?

2. Why does the typechecker call checkExpression(n.Target) even though it's about to overwrite the result?

3. Why does the codegen mirror ArrayAccess almost exactly?

4. Should ArrayAssignment implement script.Expression (i.e. have GetType/SetType methods)?

What's Next

  • Bounds checks for arr[i] and arr[i] = x. Same shape on both sides: load the length, compare against the (wrapped) index, trap if out of bounds. Three instructions per access — cheap.
  • Struct literals and field access. Same heap-allocator pattern as arrays; field offsets come from a per-struct layout table instead of i * elemSize.
  • String byte-at indexing. Reconcile the typechecker's "string-of-string" view with a useful byte-indexing operation. Smaller scope than today; mostly a typechecker decision.
  • Sorting algorithms in plex. You can now write bubble sort, selection sort, insertion sort. None of them need any new language features — they're a fun consolidation exercise.
