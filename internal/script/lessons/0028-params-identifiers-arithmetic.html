2. Stack discipline

WebAssembly is a stack machine. Every instruction either pushes values onto the operand stack, pops values off, or both. i64.const 42 pushes one i64. i64.add pops two i64s and pushes their sum. return pops the function's result value off the stack and exits.

Compiling an expression tree to a stack machine has one big simplification: walk the children left-to-right, then emit the operator. The natural recursion order produces the right operand order on the stack — no temporaries, no register allocation, no instruction scheduling.

A worked example — compiling a + b where a, b: i64 are params at indices 0 and 1:

step
emit
operand stack after
walk left (a)
local.get 0
[a]
walk right (b)
local.get 1
[a, b]
emit operator
i64.add
[a+b]

The return instruction then pops [a+b] and exits. Three opcodes, one expression — the recursion mirrors the AST exactly. (See spec §4.4 Instructions for the stack-effect notation each opcode uses.)

Stack vs register A register-based VM would have to choose where intermediate results live (r0 = a; r1 = b; r0 = r0 + r1). A stack VM elides that choice — the stack is the storage, and instruction order alone determines it. This is why WASM bytecode is so compact: no register operands ever appear in the encoding.

3. The local index space

WASM treats parameters and locals as one flat array, indexed by a single uleb128:

local 0 ... local (N-1)         ; the params, in declaration order
local N ... local (N+M-1)       ; then the body's declared locals

For now your binary backend has only params — locals come in lesson 29. So for fn add(a: i64, b: i64): i64:

idxnametype
0ai64
1bi64

For a method fn area(self, r: i64): i64 (one declared param plus implicit self):

idxnametype
0selfi32
1ri64

The Identifier case in bodyEncoder.walk needs a symbol table — a per-function map[string]uint32 from name → local index — built once when entering the function.

4. The new opcodes

Three groups: locals access (you already declared OpLocalGet in lesson 26), integer arithmetic, and float arithmetic. The pattern is "one opcode per (type, operator) pair" — there's no generic add.

ByteMnemonicDescription
0x20local.getPush local idx. Immediate: uleb128 local index.
0x6Ai32.addPop 2 i32, push i32 sum
0x6Bi32.subPop 2 i32, push i32 difference
0x6Ci32.mulPop 2 i32, push i32 product
0x6Di32.div_sPop 2 i32, push signed i32 quotient. Traps on /0.
0x6Fi32.rem_sPop 2 i32, push signed i32 remainder. Traps on /0.
0x7Ci64.addPop 2 i64, push i64 sum
0x7Di64.sub…
0x7Ei64.mul…
0x7Fi64.div_sPop 2 i64, push signed i64 quotient. Traps on /0.
0x81i64.rem_sPop 2 i64, push signed i64 remainder. Traps on /0.
0xA0f64.addPop 2 f64, push f64 sum
0xA1f64.sub…
0xA2f64.mul…
0xA3f64.divPop 2 f64, push f64 quotient. Does not trap — IEEE-754 yields ±Inf or NaN.
Three things to internalise
  • No generic add. The opcode encodes both the operation and the operand type. The type-checker pass guarantees both operands have the same type; the binary emitter just dispatches on that type.
  • Integer divide has signed and unsigned variants. div_s treats operands as two's complement; div_u treats them as unsigned. Plex doesn't (yet) have unsigned integers — always emit _s. Same for rem_s.
  • Float div does not trap on zero. Integer division by zero is a trap (the engine aborts execution). Float division by zero produces infinity or NaN — that's IEEE-754. If plex ever wants checked float division, you'll add that in the source language, not at the WASM level.

Task 2 — record method-ness on funcSig in structs.go

The bodyEncoder needs to know if it should reserve index 0 for an implicit self. Easiest path — add a flag at signature-collection time:

type funcSig struct {
    name     string
    params   []byte
    results  []byte
    isMethod bool     // ← new
}

Set it in helpers.go — signatureOf already takes implName; it can just write isMethod: implName != "" into the returned struct.

Task 3 — give bodyEncoder a symbol table in body.go 
type bodyEncoder struct {
    buf    []byte
    locals map[string]uint32     // ← new: name → local idx
}

func newBodyEncoder(f *script.FunctionDeclaration, sig funcSig) *bodyEncoder {
    b := &bodyEncoder{locals: map[string]uint32{}}
    var idx uint32
    if sig.isMethod {
        b.locals["self"] = idx
        idx++
    }
    for _, p := range f.Params {
        b.locals[p.Name] = idx
        idx++
    }
    return b
}
Task 4 — handle *script.Identifier in walk 
case *script.Identifier:
    idx, ok := b.locals[n.Value]
    if !ok {
        return fmt.Errorf("unknown identifier %q (only params resolvable so far; let-bindings arrive in lesson 29)", n.Value)
    }
    b.buf = append(b.buf, OpLocalGet)
    b.buf = AppendULEB128(b.buf, idx)
    return nil
Task 5 — handle *script.BinaryExpression in walk

Walk left, walk right, dispatch on (type, operator) to a single opcode. The result type lives on the BinaryExpression node itself (the typechecker filled it in).

case *script.BinaryExpression:
    if err := b.walk(n.Left);  err != nil { return err }
    if err := b.walk(n.Right); err != nil { return err }

    t := n.GetType()
    if t == nil {
        return fmt.Errorf("no type on binary expression")
    }

    op, err := arithOpcode(t.Kind, n.Operator)
    if err != nil { return err }
    b.buf = append(b.buf, op)
    return nil

And the dispatch table:

func arithOpcode(k script.TypeKind, op script.TokenType) (byte, error) {
    switch k {
    case script.TypeKind_I32:
        switch op {
        case script.TokenType_Plus:    return OpI32Add,  nil
        case script.TokenType_Minus:   return OpI32Sub,  nil
        case script.TokenType_Star:    return OpI32Mul,  nil
        case script.TokenType_Slash:   return OpI32DivS, nil
        case script.TokenType_Percent: return OpI32RemS, nil
        }
    case script.TypeKind_Int, script.TypeKind_I64:
        switch op {
        case script.TokenType_Plus:    return OpI64Add,  nil
        case script.TokenType_Minus:   return OpI64Sub,  nil
        case script.TokenType_Star:    return OpI64Mul,  nil
        case script.TokenType_Slash:   return OpI64DivS, nil
        case script.TokenType_Percent: return OpI64RemS, nil
        }
    case script.TypeKind_Float, script.TypeKind_F64:
        switch op {
        case script.TokenType_Plus:    return OpF64Add, nil
        case script.TokenType_Minus:   return OpF64Sub, nil
        case script.TokenType_Star:    return OpF64Mul, nil
        case script.TokenType_Slash:   return OpF64Div, nil
        // no f64.rem — IEEE-754 has no remainder opcode in WASM
        }
    }
    return 0, fmt.Errorf("no opcode for %s %v", k, op)
}
Task 6 — wire the new constructor through encodeCodeEntry

It needs both the function declaration and its signature now:

func encodeCodeEntry(f *script.FunctionDeclaration, sig funcSig) ([]byte, error) {
    var body []byte
    body = AppendULEB128(body, 0)   // locals vec still empty — lesson 29 fills it

    enc := newBodyEncoder(f, sig)   // ← uses sig.isMethod + f.Params
    if err := enc.walk(f.Body); err != nil {
        return nil, err
    }
    body = append(body, enc.buf...)
    body = append(body, OpEnd)

    var entry []byte
    entry = AppendULEB128(entry, uint32(len(body)))
    entry = append(entry, body...)
    return entry, nil
}

And update encodeCodeSection to walk both funcs and sigs in lockstep (they're collected in the same order, so indexing by i is safe).

6. Verification

Extend your end-to-end test with two cases — one for arithmetic on params, one for a slightly fancier expression to make sure the recursion order is right (subtraction is non-commutative; if you accidentally swap left/right the test will catch it).

Task 7 — add to end_to_end_test.go 
func TestEndToEnd_Add(t *testing.T) {
    src := `
        fn add(a: i64, b: i64): i64 {
            return a + b;
        }
    `
    runOne(t, src, "add", []uint64{7, 35}, 42)
}

func TestEndToEnd_Sub(t *testing.T) {
    src := `
        fn sub3(a: i64, b: i64, c: i64): i64 {
            return a - b - c;
        }
    `
    // (100 - 50) - 8 = 42; if left/right were swapped you'd get
    // 100 - (50 - 8) = 58 — useful canary for the walk order.
    runOne(t, src, "sub3", []uint64{100, 50, 8}, 42)
}

func runOne(t *testing.T, src, fn string, args []uint64, want uint64) {
    t.Helper()
    ast, err := script.Parse(strings.NewReader(src))
    if err != nil { t.Fatal(err) }
    wasm, err := binary_wasm.CompileProgram(ast)
    if err != nil { t.Fatal(err) }

    ctx := t.Context()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)
    mod, err := r.Instantiate(ctx, wasm)
    if err != nil { t.Fatalf("instantiate: %v", err) }

    got, err := mod.ExportedFunction(fn).Call(ctx, args...)
    if err != nil { t.Fatalf("call: %v", err) }
    if got[0] != want {
        t.Fatalf("%s%v = %d, want %d", fn, args, got[0], want)
    }
}

Run with -v for the full picture:

go test ./internal/script/compiler/binary/... -v

The disassembly of add should be:

000xx <add>:
 ...: 20 00      | local.get 0
 ...: 20 01      | local.get 1
 ...: 7c         | i64.add
 ...: 0f         | return
 ...: 0b         | end

Notice the byte sequence mirrors the recursion: walk-left (local.get 0), walk-right (local.get 1), emit operator (i64.add).
